※ 데이터 경계 전제: 사용자의 음원 파일과 원본 오디오는 사용자 기기를 떠나지 않는다. 분석은 로컬 에이전트가 수행하고 서버로는 취향 벡터와 특징 임베딩만
전송한다. 서버는 저작물을 애초에 보유하지 않는 구조로 설계한다. 이 원칙은 본 문서 전체를 관통하며, 어떤 기능도 이 경계를 넘지 않는다.

※ 코퍼스 전제: 개발용 코퍼스는 개발자 개인 보유 음원 1004곡(64.06시간, 9.29GB)이며 배포 대상이 아니다. 상용 음원이므로 서비스 코퍼스로 사용하지
않는다. 배포 시 참조가 필요한 경우 공개 라이선스 데이터셋(MTG-Jamendo, FMA)으로 교체하되, 로컬 에이전트 방식이므로 서비스 코퍼스 자체가 필수는 아니다.

※ 수치 표기 원칙: 본 문서의 수치는 인제스트·분석 산출물에서 코드로 재산출한 값이며 결정 기록마다 재현 명령이 붙는다 (D-0135). 미검증 항목은 **(실측
필요)**로 명시하며 추측으로 채우지 않는다(GR-0.5).

※ 문서 체계: 넷이다 (D-0186 ~ D-0189). 본 문서는 현재 · 단일 진실 공급원으로 "무엇이 참인가"를 쓴다. docs/PLAN.md가 미래,
docs/DECISIONS.md가 과거(추가 전용), README.md가 진입이다. 밖에 내는 기획서는 docs/proposal.docx — 시제 밖이며

후순위이며, 일정 계획에 이 제약을 반영한다.

1. 프로젝트 개요

항목내용
프로젝트 주제엣지 분석 기반 개인 취향 잠재 표현으로 조건화한 종단간 AI 음악 생성 시스템
개발 형태1인 풀스택 (기획·설계·구현·배포·평가 전 과정)<br>기간: 2026-08 착수 · 장기 과제 (병행 과제 고려)<br>예산: 개인 부담. GPU 인스턴스 상시 운영 제외, 보유 장비(GTX 1660Ti 6GB)로 분석까지.<br>생성 엔진은 VRAM 16GB 이상 장비에서 돈다 — 6GB에서 실측으로 떨어졌다 (D-0218)
개발자 및 역할오창준 — 전 영역 단독 수행

추진배경 및 필요성

○ [생성형 음악 서비스는 "누가 듣는가"를 모델링하지 않는다]

Suno, Udio 등 현행 서비스는 텍스트 프롬프트를 입력으로 받는다. 프롬프트는 사용자의 의도를 전달하지만 취향은 전달하지 못한다. "슬픈 발라드"라고 입력한 두
사람이 원하는 결과는 전혀 다르며, 그 차이는 각자가 그동안 들어온 음악에 축적되어 있다. 현행 서비스는 이 축적된 정보를 입력 경로 자체에서 버린다.

○ [사람은 자기 취향을 형용사로 표현하지 못한다]

"어떤 음악을 좋아하세요"라는 질문에 정확히 답할 수 있는 사용자는 드물다. 반면 "이 곡 같은 느낌"이라는 지시는 누구나 할 수 있다. 취향 입력의 단위는 형용사가 아니라
곡이어야 한다. 이는 UI 편의의 문제가 아니라 정보량의 문제다. 곡 하나에는 형용사 열 개보다 많은 정보가 들어 있다.

○ [취향 데이터는 개인 기기에 있고, 그것을 서버로 옮기는 순간 문제가 된다]

사용자의 취향을 가장 잘 나타내는 자료는 그가 실제로 소유하고 듣는 음원이다. 그런데 이 음원은 대부분 저작권 보호 대상이다. 서비스가 이를 업로드받아 서버에 저장하는 순간 서비스
제공자가 복제 주체가 된다. 취향 정보를 얻으면서 저작물은 취득하지 않는 구조가 필요하다.

○ [기존 시스템은 축이 분리되어 있지 않다]

현행 생성 모델은 프롬프트 하나로 곡 전체를 만든다. "멜로디는 A곡처럼, 가창은 B곡처럼"과 같은 축별 지정이 불가능하다. 그러나 실제 창작에서 작곡·편곡·작사·가창은 분리된
작업이며, 사용자의 취향도 축마다 다르다. 발라드 멜로디를 좋아하면서 힙합 편곡을 선호하는 것은 모순이 아니다.

○ [평가 기준이 "그럴듯함"에 머물러 있다]

생성 음악의 품질 평가는 대부분 주관적 청취에 의존하거나 FAD 같은 분포 거리 지표에 머문다. "이 사용자의 취향에 맞는가"를 정량적으로 평가하는 체계가 없다. 취향을 벡터로
정의하면 생성 결과와 취향 벡터의 거리를 직접 측정할 수 있다.

목적 및 핵심가치

○ [취향의 벡터화 — 프롬프트가 아니라 잠재 표현]

사용자 라이브러리를 음악·편곡·가사·가창 4축으로 분석하여 각 축의 잠재 공간을 구축하고, 사용자의 취향을 그 공간 위의 벡터로 정의한다. 생성 시 이 벡터를 조건으로 사용한다.
프롬프트는 보조 입력이지 주 입력이 아니다.

○ [엣지 우선 저작권 설계 — 서버는 음원을 보지 않는다]

원본 오디오가 서버에 도달하는 순간 서비스가 복제 주체가 된다. 스캔·분석·특징 추출을 사용자 기기에서 수행하고, 서버로는 벡터만 전송한다. 이는 성능 최적화가 아니라 **법적
구조의 설계**다.

○ [축별 독립 조건화 — "멜로디는 A, 가창은 B"]

4축 각각에 다른 시드곡을 지정할 수 있게 한다. 프롬프트 기반 시스템이 구조적으로 제공할 수 없는 조작이며, 축을 분리해 설계한 것의 직접적 산출이다.

○ [양성 사례만으로 성립하는 학습 설계]

사용자 라이브러리는 전부 "좋아해서 소유한" 곡이다. 음성 사례가 존재하지 않는다. 이 문제를 외부 데이터로 메우는 대신, 문제를 선호도 예측에서 조건부 생성으로 재정의하여 양성
사례만으로 성립시킨다. 상대 순위 정보가 필요한 부분은 쌍대비교로 내부에서 생성한다.

○ [실측이 설계를 결정한다 — 추측으로 채우지 않는다]

라이브러리 태그 실측에서 발매일·ISRC가 전량 부재함을 확인하고 지문 기반 정규화를 주
경로로 승격했다 (D-0006). 그 뒤 다시 재서 뒤집었다 — 정규 키는 **MusicBrainz
MBID**이고 지문 경로는 곡당 디코딩 비용으로 폐기했다 (D-0017). 아티스트 필드의 괄호가
피처링이 아니라 별칭 병기임을 확인하고 파서
설계를 뒤집었다. 미검증 항목은 (실측 필요)로 표시하고 추측으로 진행하지 않는다.

○ [생성 결과의 안전 게이트 — 실존 가수 음색 차단]

취향 학습이 특정 가수의 음색 복제로 귀결되면 인격권·퍼블리시티권 침해가 된다. 참조 오디오로 조건화한 출력의 보컬을 화자 임베딩으로
재서, 참조 가수와 유의하게 가까우면 참조 오디오 모드 자체를 제품에서 끈다 (G2 · D-0217).

HATHOR System

- 1.3 백그라운드 분석 작업 — 중단·재개, 곡 단위 진행률
- 1.4 취향 벡터 산출 및 서버 동기화 (벡터만 전송)
- 1.5 로컬 분석 결과 조회 — 라이브러리 4축 프로파일 시각화

2. 취향 프로파일링
- 2.1 라이브러리 기반 초기 취향 벡터 자동 산출
- 2.2 적응적 쌍대비교 온보딩 (이상형 월드컵형, 20~30회)
- 2.3 축별 취향 분해 표시 (음악·편곡·가사·가창)
- 2.4 취향 변화 이력 및 재학습

3. 곡 생성
- 3.1 시드곡 선택 (축별 독립 지정 가능, 1~5곡)
- 3.2 미세조정 슬라이더 (템포·밝기·밀도 등, 시드 위의 보정)
- 3.3 생성 파이프라인 실행 — 구조 → 화성 → 멜로디 → 편곡 → 가사 → 가창 → 믹스
- 3.4 단계별 중간 산출물 열람 및 부분 재생성
- 3.5 시드 고정 재현 생성 (동일 시드 = 동일 산출물)

4. 결과 관리
- 4.1 생성 곡 라이브러리 및 버전 이력
- 4.2 스템 분리 다운로드 (보컬·드럼·베이스·기타)
- 4.3 MIDI·악보 내보내기
- 4.4 생성 결과 피드백 → 취향 벡터 갱신

5. 품질 · 안전 게이트
- 5.1 화자 동일성 검사 — 실존 가수 식별 가능 시 차단
- 5.2 멜로디 유사도 검사 — 기존 곡 표절 구간 탐지
- 5.3 취향 적합도 점수 — 생성 결과와 취향 벡터 거리
- 5.4 차단 사유 및 재생성 가이드 제시

6. 관리 · 검증
- 6.1 파이프라인 재실행 및 산출 이력(manifest) 조회
- 6.2 평가 리포트 — 베이스라인 대비 지표
- 6.3 데모 모드 — 설치 없이 사전 분석된 프로파일로 체험

주요 기술

[Local Agent]
- Tauri (Rust + 웹뷰). Electron 대비 번들 크기·메모리가 작고 웹 UI를 서버와 공유한다.
- 인제스트 파이프라인은 Python 사이드카 프로세스로 분리. 이미 구현된 스캐너·추출기를 그대로 재사용한다.
- 델타 감지(mtime + size)로 재분석을 변경분에 한정한다. 곡당 GPU 수십 초가 드는 스템 분리에서 이 절감이 결정적이다.
- drvfs·NTFS 등 파일시스템 감시가 불가능한 환경이 존재하므로 실시간 감시가 아니라 명시적 재스캔 방식을 채택한다.

[Audio Analysis]
- Demucs v4 (htdemucs) 스템 분리 — 편곡축·가창축의 전제. 44.1kHz 입력.
- MERT — 음악 이해 자기지도 표현. 음악축 임베딩. 24kHz 입력.
가중치가 CC-BY-NC-4.0이라 제품 경로에 못 간다 — 대체를 같은 하네스로 잰다 (D-0217 · O-68).
- CLAP — 오디오·텍스트 정렬 임베딩. 축 간 공통 참조 공간. 48kHz 입력.
- 샘플레이트는 인제스트에서 통일하지 않고 원본을 유지한 뒤 모델 입력 직전에 리샘플한다. 모델별 요구 샘플레이트가 상이하므로 사전 통일은 손실만 발생시킨다.
- 곡 신원은 MusicBrainz MBID로 정규화한다 (D-0017). 태그 표기로는 곡을 못 찾아 아티스트를 먼저 확정하고
그 정규명으로 곡을 찾는 2단계이며, 곡 조회 상한은 78.5%다 (D-0019). 지문 경로는 곡당 디코딩 비용으로 기각했다.

[NLP · Lyrics]
- USLT 태그 가사를 우선 사용하고, 부재 시 Whisper STT로 폴백한다. 포트를 분리해 구현체를 교체 가능하게 둔다.
- 동기 가사(SYLT)가 전량 부재하므로 한국어 강제정렬(Montreal Forced Aligner 등)로 시간 정보를 생성한다. 가창축 학습의 전제다.
- 가사 언어는 태그의 언어 필드를 신뢰하지 않고 본문에서 판별한다. 실측상 한국어 가사가 eng로 기재되어 있다.
- 가사 임베딩의 정본은 해시 8192다 (M0 0.9174). 한·영 혼재 가사가 40%라 D-0045가
다국어 인코더 BGE-M3(MIT)를 골랐고, D-0048이 재 보니 M0 0.8445로 해시보다 나빴다.
의미 유사성 쪽(앨범 M1 4.2배)은 더 좋지만 **채택 기준 5배에 미달이라 정본을 안
바꿨다**. 축 탐색은 종료됐다 (D-0045 · D-0048 · D-0344).

[Generation]
- 단계 분리 파이프라인: 구조 → 화성 → 멜로디 → 편곡 → 가사 → 가창 → 믹스. 각 단계가 독립 엔진이며 중간 산출물이 검사 가능하다.
- 심볼릭 단계(구조·화성·멜로디)는 MIDI로 다루고, 오디오 렌더링은 이후 단계에서 수행한다. 전 구간 오디오 생성보다 제어 가능성이 높다.
- 가창은 오디오 엔진이 입힌다. 실존 가수 음색 복제는 구현하지 않는다 (D-0003) — 참조 오디오 모드의 음색 누설을
화자 임베딩 self/other로 재는 관문(G2)을 엔진 채택 조건으로 건다 (D-0217).
- 전 파이프라인은 시드 고정 시 결정적으로 동작한다.
- 오디오 렌더링은 공개 가중치 엔진에 맡긴다. 서류 관문으로 일곱을 걸러 ACE-Step 1.5(MIT)가
1순위다. hathor가 기획하고 — 구조·화성·가락 — 엔진이 소리를 입힌다. 엔진의 기획 언어
모델은 hathor가 대신한다 (D-0217 · D-0218).

[Backend & Infrastructure]
- FastAPI (취향 동기화 API · 생성 작업 API · 결과 서빙)
- PostgreSQL + pgvector (취향 벡터·특징 임베딩 검색), MongoDB (생성 이력·중간 산출물), Redis (작업 상태), RabbitMQ (생성 작업
큐), MinIO (산출물 오브젝트 스토리지)
- 계층 구조를 import-linter 계약으로 강제한다. 도메인 격리 / 애플리케이션 격리 / 엔진 간 직접 호출 금지 / 계층 순서 /
송신부는 오디오를 모른다 5종 (D-0134).
- 현재 산출물은 var/의 곡 묶음(npz)과 JSONL이다. DB·큐·오브젝트 저장소는 Compose로 기동만 해 두었고 P4에서 붙인다.
- CI 3잡: 품질(ruff·mypy strict·계약·커버리지) / 시크릿 스캔 / 재현성 검증.
- Docker Compose 기반 로컬 구성, 배포는 단일 인스턴스.

[Frontend]
- React(Vite) + TypeScript. 로컬 에이전트 웹뷰와 웹 대시보드가 동일 컴포넌트를 공유한다.
- 파형·스펙트로그램 표출은 WaveSurfer.js, 취향 공간 시각화는 D3 기반 2차원 투영(UMAP·t-SNE).

기대효과

[취향 입력 방식의 대안 제시]
- 텍스트 프롬프트가 아니라 시드곡과 잠재 벡터로 생성을 조건화하는 방식을 구현하고, 프롬프트 기반 베이스라인 대비 취향 적합도를 정량 비교한다.

[저작물을 취득하지 않는 개인화 구조]
- 원본 오디오가 서버에 도달하지 않으면서 개인 취향을 반영하는 구조를 실제 동작으로 제시한다. 음악뿐 아니라 개인 미디어 자료 전반에 적용 가능한 참조 설계가 된다.

[축별 조건 분리의 실증]
- "멜로디는 A곡, 가창은 B곡"과 같은 축별 지정이 실제로 결과에 반영되는지를 축별 절제 실험으로 검증한다.

[생성 안전 게이트의 구현 사례]
- 실존 가수 음색 누설을 화자 임베딩 self/other로 재는 관문(G2)을 엔진 채택 조건으로 건다. 귀무를 먼저 돌리고, 판정 규칙을 착수 전에 적는다.
정성적 정책 선언이 아니라 동작하는 관문으로 제시한다.

[1인 풀스택 역량의 통합 증명]
- 오디오 신호처리·심층학습·백엔드·데스크톱 앱·인프라·CI를 하나의 시스템에서 통합 운용한 이력을 남긴다. 개별 기술 나열이 아니라 상호 의존하는 시스템으로 증명한다.

활용방안 및 비즈니스 모델

□ 활용 방안

[창작자의 아이디어 스케치]

[로컬 우선 프리미엄 구독]

[분석 모듈 라이선스]
- 4축 특징 추출 파이프라인을 음악 서비스·DAW 플러그인에 공급하는 모듈형 라이선스.

[한계 인식]
- 착수 때는 취업 포트폴리오였고 2026-09에 남들이 쓰는 제품으로 목표를 바꿨다 (D-0215). 그 순간 전제가 바뀌었다 — **모델 가중치의 라이선스와
학습 데이터 출처가 제약이 됐고,** 이미 쓰던 MERT부터 걸렸다 (D-0217). 생성 음악의 저작권 귀속은 국내외에서 정리되지 않았고, 이는 출시 이전에
해소되어야 할 선결 조건이다.

2. 아이디어 도출 과정

본 프로젝트는 'AI 음악 생성'이라는 소재에서 출발했으나, 그것을 프롬프트가 아니라 취향 잠재 표현으로 다루기까지 네 단계의 발상 정리를 거쳤다.

□ 강제연결법 (Forced Connection)

축 A — 하고 싶은 것축 B — 보유 자산결합 결과
AI 음악 생성프롬프트 엔지니어링프롬프트 기반 생성 — Suno·Udio와 완전 중복. 차별성 없음
AI 음악 생성개인 음원 라이브러리 1004곡취향 학습 기반 추천 — 추천은 생성이 아니며 Spotify와 중복
음악 추천잠재 표현 학습임베딩 기반 추천 시스템 — 다수 존재. 신규성 없음
AI 음악 생성 × 개인 라이브러리잠재 표현 + 엣지 분석개인 취향 벡터로 조건화한 생성 — 상용 시스템 미확인. 채택 (연구 선행은 §선행연구가 든다)

앞의 세 조합은 기존 서비스와 겹치거나 기술 신규성이 없었다. 네 번째만 오디오 분석·표현
학습·생성 모델이 모두 필수적으로 요구되며, 조사 결과 개인 라이브러리를 잠재 표현으로
변환해 생성을 조건화하는 상용 시스템이 확인되지 않았다.

> 갱신 — D-0284. 이 절은 281판 동안 선행연구를 한 번도 안 봤다. 그러고 나서
> *"선행 사례 미확인"*이라 적었다. 재 보니 직계 원형이 있다 — van den Oord,
> *Deep content-based music recommendation* (NeurIPS 2013)이 **오디오 임베딩을 취향 축으로
> 쓰는 발상 자체다. 상용 시스템이 없다는 좁은 주장은 지금도 서고**, 발상이 새롭다는
> 넓은 주장은 안 선다. 갈래별 원형은 §선행연구가 든다 (D-0350이 이 배지를 달았다).

분석 요약

- 개인 취향을 누적 학습하는 생성 서비스는 확인되지 않는다. 모든 서비스가 세션 단위 프롬프트로 동작한다.
- MusicGen이 멜로디 조건화를 제공하나 단일 축이며 취향 개념이 없다.
- 공개 엔진은 경쟁자가 아니라 부품이다. ACE-Step 1.5는 참조 오디오를 받지만 누구의 취향인지 모른다 — hathor가 그 자리를 채운다 (D-0217).
- AIVA가 MIDI 편집으로 축 분리에 가장 근접하나, 사용자의 취향을 학습하지 않고 프리셋을 선택하게 한다.
- 데이터 경계를 설계 원칙으로 명시한 서비스가 없다. 모두 서버 처리 전제다.
- (실측 필요) 각 서비스의 최신 기능·정책은 조사 시점 기준이며, 구현 착수 전 재확인이 필요하다.

□ 선행연구

풀었나»가 없고, 인용한 것은 쓴 모델(MERT · CLAP · Demucs)뿐이다. 쓴 도구를 적는 것과

- 대표로 들던 수가 앨범 효과 위의 것이다. M1 20.4배는 «같은 앨범 찾기»이고 그 과제가

표준이고, 배수는 추천시스템 쪽 관용이다.
- 외부 비교가 성립하지 않는다. 1004곡 개인 라이브러리에 아티스트·앨범 프록시이므로

수가 아니다.

□ 요구사항 ID 체계 정의

REQ-{그룹}-{번호} 형식. 번호는 그룹 내 3자리 일련번호.

항목규칙
그룹위 체계도의 3문자 코드
번호001부터 순차. 폐기해도 재사용하지 않는다
우선순위M(Must, MVP 필수) / S(Should) / C(Could)
단계해당 요구사항이 구현되는 P단계
상태미착수 / 진행 / 부분 / 완료 / 강제 / 설계 / 보류 / 변경 / 폐기

MVP 경계: 우선순위 M은 P4까지의 범위에 한정한다. P5 이후 요구사항은 최대 S를
부여한다. 이는 미완 시 MVP 판정에 영향을 주지 않기 위한 장치다.

예외가 9이고 셋으로 갈린다 — 안전·법적(D-0003 · 가사 복제 금지) · 재현성(D-0009) ·
엔진 관문(D-0217), 그리고 제출 요건 하나다. 단계와 무관하게 M이다: 실존 가수 음색
차단을 「Should」로 내리면 제품이 아니라 위험이고, 재현성을 내리면 결과를 못 믿는다.
규칙이 블런트했던 것이고 행이 틀린 것이 아니다.

tools/check_requirements.py가 이 표 전체를 센다 (D-0350) — 상태 집합 · 그룹 ↔ 체계도
양방향 · 번호 결번·중복 · 선언 안 된 M/P5+ · 끝났는데 근거 없는 행. 예외마다
사유가 붙고 사유 없는 예외는 그냥 구멍이다. 이 표는 요구사항 97행이고, 그 수와
예외 수 둘 다 doc_fsck의 축이 든다 — 수는 숫자로 적는다. 「아홉」이라 적으면 세는
자가 못 읽고, 못 읽는 축은 조용히 통과한다 (D-0349).

□ 계층 구조 (GR-2)

정적 계약(import-linter)으로 강제되는 6계층. **계약 정의는 core/pyproject.toml이 진실이며
여기에는 근거만 둔다** — 설정을 문서에 다시 적으면 반드시 어긋난다 (D-0042 · D-0043).

계층책임의존 방향
domain엔티티·값객체·포트. 외부를 전혀 모른다없음
application유스케이스·오케스트레이션. 포트에만 의존→ domain
engines무거운 AI 연산 단위. 엔진 간 직접 호출 금지→ domain
infrastructure포트 구현체. DB·파일시스템·외부 API·모델→ domain, application
interfacesCLI·REST·워커 진입점. 비즈니스 로직 없음→ application
shared설정·텔레메트리없음

계약 7종 — 다른 자리에서 순번으로 부르지 않는다. 계약을 하나 끼우면 그 뒤가
전부 밀리고, 실제로 그렇게 깨졌다 (D-0350) — 일곱째를 넣으니 세 곳의 순번 참조가 한
칸씩 밀렸다. 이름으로 부른다. check_retired가 그 꼴을 막는다.

1. 도메인은 외부를 모른다 — domain이 다른 계층을 import하지 않는다
2. 공용은 위를 모른다 — shared가 어느 계층도 import하지 않는다. 위 표가 이 계층의
의존 방향을 「없음」이라 적어 두고 강제하는 계약이 없었다 (D-0350). 위반이 0인
채로 못을 박았다 — D-0190이 *"infrastructure가 계약에 없어 역방향이 안 잡혔다"*고
적은 그 자리다
3. 애플리케이션은 구현체를 모른다 — application이 infrastructure를 import하지 않는다
4. 엔진 간 직접 호출 금지 — 엔진끼리 서로 import하지 않는다. 조합은 application이 한다
5. 계층 순서 — 위 의존 방향을 역행하지 않는다
6. 송신부는 오디오를 모른다 — 망을 타는 모듈이 디코더·분리기·특징 추출기·파형
타입을 import하지 않는다. D-0015의 *"타입 수준의 불가능"*을 서버 없이 구현한
형태다 (D-0134)
7. 가창 엔진은 라이브러리 오디오를 모른다 — engines.vocal이 디코더·분리기·특징
추출기·특징 저장소를 import하지 않는다. 낱말을 안 쓰고도 성문을 뽑는 길을 막는
것이며, D-0003의 판단을 계층으로 옮긴 형태다 (D-0261)

엔진 vs 배관의 구분 기준: 엔진은 무거운 AI 연산이다. 인제스트는 파일을 읽고 표를 만드는 배관이므로 엔진이 아니며 application +
infrastructure에 배치한다.

5. 취향 모델 설계

보조 기능으로 격하됐다 (D-0029). 아래 설계는 보존하되 착수하지 않는다. 주기능은 시드곡 퓨전이고,
무엇이 «좋은가»의 채점관은 제품이 돈 뒤 자체 행동 데이터로 세운다 — 밖에서 대중성 라벨을 구하는
길은 세 번 다 라이선스·커버리지에 막혔다 (D-0215 · D-0216 · O-67).

□ 문제 재정의

라이브러리는 전량 양성 사례다. 선호도 이진 분류를 학습할 음성 사례가 존재하지 않는다.

접근필요 데이터판정
선호도 예측양성 + 음성성립 불가
조건부 생성양성만채택

"이 곡을 좋아할 것인가"는 음성 사례를 요구하지만 "이런 느낌으로 생성하라"는 양성만으로 성립한다. 균일 양성 데이터가 결함이 아니라 전제가 된다. <!--voice-ok-->

□ 취향 신호 3층

층신호성격갱신
1. 라이브러리보유 곡 전체전역 사전확률재스캔 시
2. 쌍대비교A vs B 선택상대 순위온보딩·재학습

층이 다르므로 충돌하지 않고 누적된다. 시드가 지정하지 않은 부분을 사전확률이 메운다.

□ 쌍대비교

목적: 절대 라벨 없이 상대 순위 신호를 만든다. A를 고르면 B는 그 맥락에서 상대 음성이 되며, 음성 사례 부재 문제를 외부 데이터 없이 완화한다.

쌍 선택: 임베딩 공간에서 거리가 먼 쌍을 우선하고, 이후 현재 모델의 예측 불확실성이 높은 쌍(확률 0.5 근방)을 선택한다. 무작위 추출은 유사곡 쌍에서 정보량이 0에
수렴한다.

> 갱신 — D-0028. 위 문단은 처음부터 적응적으로 고르는 안이고 그 안은 기각됐다.
> 같은 방식으로 평가 쌍까지 뽑으면 시험 분포가 모델에 의존한다 — 자기가 헷갈리는
> 문제만 골라 풀는 꼴이다. 무작위 쌍으로 고정 평가 집합 30건을 먼저 만든 뒤 적응적
> 선택으로 넘어간다. 그 30건은 보존돼 있다 (REQ-TST-003). 건너뛴 문항도 기록한다 —
> 어떤 쌍을 판단하지 못했는지가 정보다.
>
> 이 절은 *"보존하되 착수하지 않는다"*이지만 **보존된 설계가 뒤 결정과 어긋나면
> 재개하는 손이 기각된 것을 만든다** (D-0350이 이 배지를 달았다).

적합: Bradley-Terry 계열 쌍대비교 모델. 반드시 잠재 공간 위에서 적합한다. 곡 ID에 대한 선호만 학습하면 라이브러리 밖으로 일반화되지 않아 신규
생성곡에 대해 아무것도 말해주지 못한다.

시행 횟수: 최소 20회, 이후 건너뛰기 허용. 재학습 시 반복 부담을 방지한다.

호칭: 본 기법은 랜덤 포레스트가 아니다. 문서·발표에서 혼용하지 않는다.

□ 조건화 판정 — self/other와 그 한계

조건화가 출력에 닿는지는 자기 참조와 더 가까운가(self)를 남의 참조(other)와 곡 단위 짝으로

10초 청크는 곡 구조와 정렬될 이유가 없지만 가사 구간은 빈 줄 경계, 즉 곡 구조 그 자체라 홀짝이 절·후렴을 갈라놓을 수 있다. 기본값을 바꾸면
D-0031~D-0038의 M0 수치와 비교할 수 없으므로 odd-even을 유지하고 회귀 테스트로 고정한다.

M0는 top-1과 함께 순위 진단(MRR · R@5 · R@10 · 실패 순위 중앙값)과 해석적 베이스라인(무작위 top-1 = 1/n, 무작위 순위 중앙값 =
(n+1)/2)을 낸다 (D-0041). top-1만으로는 실패가 순위 2에 몰려 있는지 수백 등에 흩어져 있는지 구분할 수 없고, 그 둘은 처방이 정반대다.

M0 게이트를 어떻게 읽는가

M0 게이트의 전제는 축마다 다르다 (D-0044). 게이트는 "M0가 무너지면 아래 지표는
무의미하다"를 전제한다. 오디오축에서는 음색·믹스가 곡 특정성과 유사성을 겸해 성립한다.
가사축에서는 반증됐다 — 반복 감쇠 조건이 M0 0.3850(반토막)인데 M1 2.2배·M2 2.5배로
M0 0.90대 조건과 같았다. 가사에서 M0는 반복 문구를, M1/M2는 어휘·주제를 재며
둘이 다른 신호다. **가사축 게이트를 무엇으로 둘지는 안 정했다 — 고칠 축이 종료돼
정할 이유가 사라졌다 (O-15 닫힘 D-0344).**

미달의 성격은 순위로 가른다. R@10이 게이트를 넘으면 정답이 상위권에 있다는 뜻이고
표현이 무너진 것이 아니다(가사 8192: top-1 0.9174, R@10 0.9715, 실패 순위 중앙값 3.8).
넘지 못하면 표현이 곡을 특정하지 못하는 것이다(반복 감쇠: R@10 0.4688, 실패 순위 831.1).
두 상황은 처방이 정반대이며, D-0041 이전에는 같은 문구로 보고되고 있었다.

그 가름이 이제 관문 자체를 가른다 (D-0234). 판정은 둘이다.

판정기준못 넘으면
붕괴R@10 ≥ 게이트, 또는 실패 순위 중앙값이 k 안. 둘 다 무작위 중앙값이 k 밖인 코퍼스에서만 인정한다 — 곡이 열뿐이면 잡음도 R@10 1.0이다M1/M2를 계산하지 않는다
식별top-1 ≥ 게이트 (0.95)계산하되 «비교용» 표식을 달고 정본으로 인용하지 않는다

리포트 JSON이 collapsed · citable을 들고 다닌다 — 자격을 로그가 아니라 산출물이 든다.

하네스 운용과 실측 이력

- 베이스라인 2종 필수: 무작위(시드 고정), MFCC 평균. 측정값 단독 인용 금지.
- MAP은 min(R, k)로 정규화한다. k로 나누면 지표가 앨범 크기 분포를 재게 된다.
- CPU 수 초. GPU 없는 기기에서 도는 것이 요건이다.
- 저장소를 둘 이상 합칠 때는 블록별 단위 정규화(--block-l2)가 필수다. MERT 768차원과
MFCC 40차원을 그냥 이어붙이면 코사인이 노름 큰 쪽에 압도당해 작은 블록이 무시된다.
블록 정규화 후 concat하면 전체 코사인이 블록 코사인의 평균이 되어 기여가 균등해진다.
- 실측 결과는 D-0024. 9조건 비교에서 MFCC 40차원이 MERT 768차원을 이겼다(M2 기준 47% 우위).
원인 미확정이며 O-8(D-0024)로 등재. 스템은 MERT 임베딩에 기여하지 않음이 확인됐다.

표현 선택의 실측 이력 — 공간과 층

- 공간 뭉침은 D-0030. 전체 쌍 평균 코사인 0.9476으로 허브 곡이 존재한다.
시드 퓨전이 중점 대신 코퍼스 중심으로 빨려가는 것이 실측으로 확인됐다.
중심화 도입 후 전 지표가 개선됐다(D-0031): 평균 코사인 0.9476 → -0.0006,
M1 MAP +14.1%, M2 MAP +13.0%, M0 유지. 기본값으로 승격했으며 --raw로만 끈다.
시드 퓨전에서 허브 곡이 사라지고 유사도 범위가 0.98대 → 0.42~0.33으로 정상화됐다.
- 레이어 곡선 종결은 D-0027. 0~3이 단조 감소이고 6의 반등도 0을 넘지 못한다.
layer00이 최댓값이며 레이어 축은 소진했다 — 검색축에서다 (D-0181이 화성축에서 layer03을 찾았다).
재현성 검산 2회 통과(별도 배치·저장소에서 네 지표 완전 일치).
- 레이어 실측은 D-0026. MERT 마지막 레이어가 측정한 전 레이어 중 최악이었다.
layer00으로 바꾸자 M2 P@10이 0.0829 → 0.2327로 2.8배 올랐고 MFCC를 90% 앞선다.
D-0024의 "MFCC가 MERT를 이긴다"는 모델 문제가 아니라 레이어 선택 문제였다.
검색축 기본 뷰가 layer00이다 (D-0181 · D-0203).

표현 선택의 실측 이력 — 결합과 상업 가능 축

- 결합 실측은 D-0025. MERT+MFCC 결합이 M1에서 어느 단독보다 우월하다(MAP@10 0.1022,
MFCC 대비 +40%). 두 표현은 상보적이며, MERT를 버리는 판단은 틀린 것이었다.
M2는 무승부이므로 MERT의 기여는 앨범 수준에 한정된다.
- 코퍼스 구조 도출: 1004곡 중 595곡이 단일 곡 앨범이라 M1 쿼리는 409뿐이다.
아티스트당 평균 약 17곡으로 M2의 검정력이 M1보다 높다.
- 상업 가능 축 실측은 D-0235 (O-68 닫힘). 같은 1004곡·홀짝 분할에서 CLAP 단독 M1
MAP@10 0.0527(6.6배) · M2 0.0348(3.6배) — MERT layer00의 27% · 16%다. 상업 가능
최선은 CLAP+MFCC(--block-l2)로 0.0825(9.9배) · 0.0822(7.1배)이며 42% · 38%다.
MFCC를 붙이면 CLAP은 +57%, MERT는 -32%다 — CLAP에 없는 음향 정보가 MFCC에 있고 MERT
첫 층에는 이미 있다. 대체재는 없다.
- D-0299가 그 표를 다시 쟀다. 수는 전부 재현됐고 MFCC 단독이 빠져 있었다 — M2에서
그것이 CLAP+MFCC를 이긴다(0.0899 대 0.0822). 「최선은 조합」은 M1을 앞세운 판정이었다.

손으로 적지 않는다 (D-0070 · GR-0.7). 파일 목록도, 패치 머리 셋도 그렇다 —

결정 번호는 어느 판인지 가르지 못한다. 같은 번호로 패치를 두 번 보내면 선행 검사가
둘 다 통과하고, 어긋난 쪽은 git apply의 *"브랜치와 기준 커밋을 확인한다"* 한 줄로만
나타난다 — 어느 기준인지는 말하지 않는다. 그래서 트리 해시를 같이 적는다. 트리 해시는
파일 이름·모드·내용만으로 정해져 이력이 안 들어가므로 미러와 실물에서 같다 (실측:
커밋 350개인 미러와 커밋 1개인 새 저장소가 같은 트리 4201d34a를 냈고 커밋 해시만 달랐다).
make patch VERIFY=는 거꾸로도 쓴다 — 받은 패치가 어느 판 위에 서는지 이력을 훑어 댄다.
