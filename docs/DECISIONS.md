## D-0001. MongoDB를 core 프로파일에 유지한다

- **배경**: 8GB RAM 노드에서 P0~P2 동안 MongoDB 용처가 없어 제외를 제안했다.
- **후보**: (a) 제거 후 §3.7 착수 시 추가 / (b) core에 유지
- **선택**: **(b) 유지.** **사용자 판단으로 결정됨.**
- **근거**: 폴리글랏 저장소(§3.7)가 설계 확정 사항이며, 나중에 붙이는 비용보다 처음부터 켜두는 편이 낫다는 판단.
- **결과**: `mongo:8`을 core에 두되 `--wiredTigerCacheSizeGB 0.25`, `mem_limit 512m`으로 제한.
  core 프로파일 메모리 상한 합계 약 2.3GB → 약 2.8GB.

## D-0002. 본인 보컬 시드 녹음을 P7까지 연기한다

- **배경**: 부록 E 착수 순서 4는 보컬 녹음을 크리티컬 패스로 지정했다.
- **후보**: (a) P0에 즉시 착수 / (b) 연기하고 필요 시 수집
- **선택**: **(b) 연기.** **사용자 판단으로 결정됨.**
- **근거**: 가창 개인화는 후순위이며, 파이프라인이 임의 시점에 화자 데이터를 받아
  재학습하는 구조로 만들면 조기 수집의 이점이 사라진다.
- **결과**: `hathor.vocal`은 **화자 무의존 설계**로 간다. 화자 임베딩을 런타임 주입 파라미터로
  두고, 시드 화자는 교체 가능한 자원으로 취급한다. 부록 E 착수 순서 4를 삭제하고
  "화자 데이터 수집은 상시, 학습은 요청 시" 원칙으로 대체한다.

## D-0003. 실존 가수의 음색 복제·보간은 구현하지 않는다

- **배경**: 라이브러리 아티스트의 음색·발성을 학습해 보간하는 방안이 제기됨.
- **후보**: (a) 라이브러리 실존 가수 음색 학습 / (b) 공개 다화자 가창 DB 기반 화자 공간 학습
- **선택**: **(b).**
- **근거**: 국내법상 음성은 인격권·퍼블리시티권(부정경쟁방지법 제2조 파목) 보호 대상이며,
  식별 가능한 실존 가수의 음색 재현은 개인 연구라도 면책되지 않는다.
  부록 D 저작권 답변("실존 화자 복제 미구현")과도 정면 충돌하며,
  포트폴리오 심사에서 자산이 아니라 결격 사유로 작동한다.
- **결과**: 화자 임베딩 공간은 **라이선스가 명확한 공개 다화자 가창 DB**로만 학습한다(부록 B).
  보간은 익명 화자 공간 내부에서 수행한다. 사용자 본인 음성은 언제든 시드로 추가 가능.
  라이브러리 음원은 **편성·화성·리듬 등 음악적 통계 추출 전용**이며 성문 특징은 추출하지 않는다.

## D-0004. 저장소를 WSL ext4에 두고 F 드라이브는 데이터 전용으로 쓴다

- **배경**: `/mnt/f`(drvfs)에서 `uv sync`가 symlink 생성 실패(`Operation not permitted`)로 중단.
- **후보**: (a) drvfs에서 우회 옵션으로 강행 / (b) 저장소를 WSL ext4로 이전
- **선택**: **(b).**
- **근거**: drvfs는 POSIX symlink를 지원하지 않으며, 파일 I/O가 ext4 대비 10~20배 느리다.
  우회는 성능 문제를 해결하지 못한다.
- **결과**: 코드는 `~/projects/hathor`(ext4), 음원·체크포인트는 `/mnt/f`,
  DB는 Docker named volume(WSL 내부)에 둔다.
  노트북 2대(자취방 GTX 1660Ti / 광인사 13코어 무GPU) 동기화는
  GitHub + `pg_dump` 스냅샷(`/mnt/f/hathor-state`)으로 처리한다.

## D-0005. 가사는 태그 우선, STT 폴백 경로를 유지한다

- **배경**: step0 실측 결과 라이브러리 1004곡의 USLT(비동기 텍스트 가사) 보유율 100%.
  SYLT(시간 동기) 0%.
- **후보**: (a) STT 경로 삭제 / (b) 포트만 정의하고 구현 보류
- **선택**: **(b).** **사용자 판단으로 결정됨.**
- **근거**: 100%는 현 사용자 라이브러리의 속성이지 시스템이 보장하는 값이 아니다.
  향후 사용자는 태그 없는 음원을 투입한다. 눈앞의 통계에 설계를 맞추면 확장성을 잃는다.
- **결과**: `LyricsSource` 포트를 정의한다. `TagLyricsSource`는 P1에서 구현,
  `WhisperLyricsSource`는 인터페이스만 두고 P2 이후 구현한다.
  SYLT가 0%이므로 **한국어 강제 정렬(forced alignment)이 P2 필수 과제**로 승격된다
  (음절 정합률 97% 검증에 음절↔시각 매핑이 필요).

## D-0006. ISRC 부재로 Chromaprint 지문 정규화가 주 경로가 된다

- **배경**: step0 실측 — ISRC 0%, 발매일 0%, 제목·아티스트·앨범 각 100%.
- **결과**: AcoustID + MusicBrainz 조회를 P1 필수 경로로 승격한다(선택 아님).
  발매일은 동일 조회로 함께 복구한다. 발매일 부재 시 취향 벡터의 시대 축을 만들 수 없다.
  파일명이 `아티스트-제목.mp3` 규칙으로 100% 일관되므로 태그와 교차검증하여
  불일치 곡을 정규화 우선 검토 대상으로 선별한다.
  아티스트 필드에 피처링이 혼재하므로(`10CM, BIG Naughty (서동현)`)
  아티스트 엔티티 분리 파서가 P1에 필요하다.

## D-0007. 샘플레이트는 인제스트에서 통일하지 않는다

- **배경**: 44.1kHz 76.8% / 48kHz 23.2% 혼재. 포맷은 100% mp3.
- **후보**: (a) 인제스트에서 44.1kHz로 통일 / (b) 원본 유지 후 모델 입력 직전 리샘플
- **선택**: **(b).**
- **근거**: 모델별 요구 샘플레이트가 상이하다(MERT 24kHz, CLAP 48kHz, Demucs 44.1kHz).
  사전 통일은 정보 손실만 발생시키고 어느 모델에도 최적이 아니다.
- **결과**: 원본 유지, 모델 입력 직전 리샘플.
  **한계**: 전량 mp3(손실 압축)이므로 스템 분리 품질에 원리적 상한이 있다.
  FAD 등 지표 해석 시 이 한계를 명시한다.

## D-0008. MASTER.md는 단일 진실 공급원이되 코드가 충돌 시 우선한다
- **배경**: MASTER.md 4300줄은 사용자가 직접 작성하지 않았고 전량 검증되지 않았다.
  설계 논의 중 "MASTER에 무엇이 정의되어 있는가"를 확인할 수 없어 진행이 정체됐다.
- **후보**: (a) MASTER.md 폐기 후 코드+DECISIONS만 유지 / (b) 단일 진실 공급원 유지 + 개정 절차 명시
- **선택**: **(b).**
- **근거**: 문서 폐기는 전역 설계 시야를 잃는다. 문제는 문서의 존재가 아니라
  미검증 내용이 확정 사실처럼 취급되는 것이다.
- **결과**: MASTER.md는 단일 진실 공급원을 유지한다.
  코드와 MASTER.md가 충돌하면 **코드가 우선**하며, 충돌 발견 즉시 MASTER.md를 갱신한다.
  MASTER.md 변경은 합의 하에 상시 가능하다.
  미검증 항목은 추측으로 유지하지 않고 실측 후 확정한다(GR-0.5).

## D-0009. 노트북 2대 역할을 재정의하고 파이썬 3.12로 고정한다
- **배경**: 광인사 노트북 실측 — Intel Ultra 7 155U / RAM 16GB / 내장 그래픽 / 저장소 477GB.
  리전 노트북은 GTX 1660Ti 6GB / RAM 8GB(WSL 4.8GB 할당).
  기존 D-0004는 광인사를 "인프라 노드"로 규정했으나 실제 스펙은 반대다.
  추가로 `requires-python = ">=3.12"`만 지정되고 `.python-version`이 부재하여
  광인사에서 CPython 3.14.4, 리전에서 3.12가 선택되는 불일치가 발생했다.
- **후보**: (a) 기존 역할 유지 / (b) 역할 교체
- **선택**: **(b), 파이썬은 3.12 고정.**
- **근거**: P1~P3 인제스트·분석 배관은 GPU를 요구하지 않으며 RAM과 코어 수가 지배적이다.
  광인사가 RAM 2배, 코어 수 우위다. GPU는 P4 모델 학습 시점부터 필요하다.
  파이썬 3.14는 PyTorch 휠 지원이 확인되지 않았고, P4에서 재구성 비용이 발생한다.
- **결과**: **광인사 = 주 개발기, 리전 = GPU 워커.**
  `.python-version`에 3.12를 핀하여 2대 간 인터프리터를 일치시킨다(재현성 CI 잡 보호).
  **한계**: 리전 RAM 8GB에서 docker compose 5종 + PyTorch 동시 구동은 P4에서 재검토 필요.
  라이브러리 루트 경로가 머신마다 다르므로(리전 `/mnt/f`, 광인사 `/mnt/d`)
  `HATHOR_LIBRARY_ROOT` 환경변수로 외부화한다.

## D-0010. ID3 전수 조사 결과 유효 태그는 4종이며 태그 기반 메타데이터 경로를 폐기한다
- **배경**: step0가 `easy=True` 매핑을 사용했을 경우 ID3v2.3 `TYER` 등이 누락될 가능성을 제기하여
  1004곡 원시 프레임 전수 조사를 수행했다(`tools/probe_id3.py`).
- **실측 결과**: 읽기 실패 0. 파일명 NFD 0(전량 NFC).
  TIT2 / TPE1 / TALB / USLT / APIC / POPM 각 100%. TSSE 62.8%.
  TSOA 3.7% / TSOP 0.8% / TSOT 0.7%.
  **발매일 프레임(TDRC·TDRL·TDOR·TYER·TDAT·TORY) 전량 0%. TSRC 0%. SYLT 0%.**
  **TRCK·TPE2·TCON·TPOS 전량 부재.**
- **결과**: D-0006의 전제(ISRC·발매일 부재)가 **확증**되었다. 가설은 기각.
  D-0005의 전제(USLT 100%, SYLT 0%)도 확증.
  인제스트가 태그에서 읽는 필드를 **제목·아티스트·앨범·가사 4종으로 한정**한다.
  트랙번호·디스크번호·장르·앨범아티스트 필드는 도메인 모델에서 삭제한다(전량 부재).
  발매일·ISRC는 도메인에 필드로 유지하되 항상 None이며, 유닛 #3 외부 조회가 채운다.
  파일명 유니코드 정규화는 방어적으로 유지하되 실측상 불필요하다.
  POPM은 전곡 동일 최고값으로 분산이 0이므로 **선호도 신호로 사용하지 않는다**(존재 여부만 기록).
  앨범아트는 APIC 100%를 사용한다. `앨범 커버/` 폴더(743개, 앨범 단위, .jfif)는
  파일명↔TALB 매칭 로직이 추가로 필요하므로 P1에서 사용하지 않고 교차검증용으로 보존한다.
  P1 스캔 산출물에는 이미지 바이트를 포함하지 않고 `has_album_art` 불리언만 기록한다.
- **한계**: POPM 100% + 발매일 0% 조합은 일반적인 구매·리핑 경로에서 발생하지 않는다.
  태그 출처를 신뢰할 근거가 약하므로 지문 기반 정규화(D-0006)의 필요성이 강화된다.

## D-0011. 취향은 선호도 예측이 아니라 조건부 생성으로 다룬다
- **배경**: 라이브러리 1004곡은 전량 사용자가 선호하여 다운로드한 곡이고 POPM도 전곡 동일 최고값이다.
  선호도 이진 분류기를 학습할 음성 사례가 저장소 내에 존재하지 않는다.
- **후보**: (a) 외부 카탈로그에서 네거티브 샘플링하여 선호도 예측 모델 학습
  / (b) 라이브러리 전체를 균일 선호로 전제하고 스타일 조건부 생성으로 전환
- **선택**: **(b).**
- **근거**: (a)는 음성 사례의 대표성을 보장할 수 없고 편향이 결과에 직결된다.
  "이 곡을 좋아할 것인가"는 음성 사례를 요구하지만
  "이런 느낌으로 생성하라"는 양성 사례만으로 성립한다.
  균일 양성 데이터가 결함이 아니라 전제가 된다.
- **결과**: 라이브러리를 **음악·편곡·가사·가창 4축**으로 분석하여 잠재 표현을 구축한다.
  - 음악: 코드 진행, 멜로디, 조성, BPM
  - 편곡: 악기 구성, 음색, 섹션 구조, 믹스 (**스템 분리 의존**)
  - 가사: 주제, 어휘, 정서, 운율 (USLT 100% 확보)
  - 가창: 창법, 음역, 비브라토, 표현 (**보컬 스템 의존**)
  생성 시 사용자 입력은 **시드곡 선택** 방식을 채택한다(형용사 체크박스 아님).
  라이브러리에서 참조곡 1~5개를 선택하면 해당 잠재 표현을 조건으로 사용한다.
  **축별로 다른 시드 지정을 허용한다**(예: 멜로디는 A곡, 가창은 B곡).
  체크박스형 입력은 시드 위의 미세조정 수단으로만 부수 제공한다.
  앨범아트는 선호도 신호에서 제외하고, 음악↔이미지 대응 학습에만 사용하여
  P6~P7 생성 결과물의 커버 생성 후처리에 활용한다.
  **한계**: 편곡·가창축은 스템 분리(추가 약 35GB)에 의존하므로 P2 병목이다.
  가사축만 P1 산출물로 즉시 착수 가능하다.

## D-0012. 취향 웜스타트는 적응적 쌍대비교로 수행한다
- **배경**: 시드곡 조건(D-0011)은 매 생성 시점의 지역 조건이며, 전역 취향 사전확률이 별도로 필요하다.
  사용자가 "이상형 월드컵" 형태의 강제 온보딩을 제안했다.
- **후보**: (a) 전곡 단일 토너먼트(1003회 비교) / (b) 64강 무작위 추출(63회)
  / (c) 적응적 쌍대비교(20~30회)
- **선택**: **(c).**
- **근거**: 쌍대비교는 절대 라벨 없이 상대 순위 신호를 생성하므로
  D-0011의 음성 사례 부재 문제를 외부 데이터 없이 완화한다.
  무작위 추출은 유사곡 쌍에서 정보량이 0에 수렴한다.
  임베딩 공간상 거리가 먼 쌍을 우선하고 현재 모델의 예측 불확실성이 높은 쌍

- **결과**: Bradley-Terry 계열 쌍대비교 모델을 **잠재 표현 위에서** 적합한다.
  곡 ID에 대한 선호도만 학습하면 라이브러리 외부로 일반화되지 않으므로,
  반드시 임베딩 공간에서 학습한다. 적합된 가중치는 영속화하여 재사용한다.
  최소 20회 이후 건너뛰기를 허용한다(재학습 시 반복 비용 방지).
  **호칭 정정**: 본 기법은 랜덤 포레스트가 아니다. 문서·발표에서 혼용하지 않는다.
  **선행 조건**: 임베딩이 존재해야 성립하므로 **P3 이후 착수**한다.

## D-0013. 라이브러리 변경 추적은 명시적 재스캔 + 델타 감지로 한다
- **배경**: P1 완료 조건에 "이벤트 기반 업서트"가 포함되나 초기 설계는 일회성 전수 스캔만 다뤘다.
  음원은 사용자가 원본 위치(외장 SSD)에 직접 관리하며, iTunes처럼 전용 디렉터리로
  복제해 소유권을 갖는 방식은 8.6GB 중복을 발생시켜 채택하지 않는다(D-0004).
- **후보**: (a) inotify/watchdog 실시간 감시 / (b) 데몬 주기 폴링
  / (c) 명시적 재스캔 + 이전 스냅샷 대비 델타 감지
- **선택**: **(c).**
- **근거**: (a)는 drvfs 경유 NTFS 외장 볼륨에서 리눅스 inotify가 변경 알림을 수신하지 못해
  기술적으로 성립하지 않는다.
  **실측 완료(2026-08-10, /mnt/d)**: `inotify_add_watch`는 유효한 watch descriptor를 반환하지만
  해당 디렉터리에서 파일 생성·삭제를 수행해도 이벤트가 전달되지 않는다.
  등록이 성공하므로 watchdog 등 상위 라이브러리는 오류 없이 무동작 상태가 되며,
  감시가 조용히 실패한다. 이 실패 양상 때문에 (a)는 재고 대상이 아니다.
  (b)는 상시 데몬을 요구하는데 노트북 2대를 오가는 환경(D-0009)에서
  어느 쪽 상태가 최신인지 모호해지고 관리 비용이 이득을 넘는다.
  음원 라이브러리는 사용자가 곡을 내려받는 시점에만 변한다.
  변경 빈도가 월 단위이므로 실시간 감시는 과잉이다.
  명시적 실행은 "이 산출물은 이 시점 상태"를 명확히 하여 재현성과 정합한다.
- **결과**: 사용자가 `ingest scan`을 명시적으로 실행한다.
  이전 스냅샷이 존재하면 대조하여 도메인 이벤트 4종으로 분류한다:
  `TrackDiscovered`(신규) / `TrackModified`(변경) / `TrackRemoved`(소실) / `TrackUnchanged`(무변화).
  **여기서 이벤트는 파일시스템 이벤트가 아니라 도메인 이벤트다.**
  델타 판정 기준은 `modified_at`(mtime)과 `file_size_bytes`이며 둘 다 이미 ScannedTrack에 있다.
  **성능 실측(2026-08-10, 리전, /mnt/f drvfs)**: 1004곡 초회 스캔 10.8초, 재스캔 9.6초.
  현 구현은 태그를 모두 읽은 뒤 판정하므로 UNCHANGED 파일의 추출을 건너뛰지 않는다.
  절감 여지가 약 7초에 불과해 스캐너에 baseline을 주입하는 설계 복잡도를 정당화하지 못한다.
  인제스트 단계에서는 추출 생략을 구현하지 않는다.
  추출 생략이 실질적 이득을 내는 지점은 곡당 GPU 연산이 발생하는 P2 스템 분리이며,
  해당 단계에서 델타 기반 건너뛰기를 별도로 구현한다.
  스냅샷 비교 대상은 P1에서 직전 JSONL 산출물이고, 유닛 #4 이후 PostgreSQL로 승격한다.
  실제 업서트는 유닛 #4에서 구현한다.
- **한계**: mtime·size 동일하되 내용이 바뀐 파일은 감지하지 못한다.
  지문 재계산(유닛 #3)은 델타 대상에만 수행하므로 이 경우 갱신이 누락된다.
  전수 재검증이 필요하면 `--force` 옵션으로 델타 감지를 우회한다.

## D-0014. 아티스트 파서는 정규화하지 않고 후보를 제시한다
- **배경**: 1004곡 아티스트 필드 전수 조사(`tools/probe_artist.py`).

  / (c) 파서는 분해 후보만 제시하고 확정은 유닛 #3 외부 조회에 위임
- **선택**: **(c).**
- **근거**: (a)는 현 65개 다중 후보 문자열에 과적합되며 신규 곡에서 재차 붕괴한다.

  임베딩상 `Earth, Wind & Fire`와 `Earth`가 가까워 오히려 혼동을 유발한다.
  정규명 확정은 문자열만으로 불가능하다. `아이유(IU)`는 한글이 앞이고
  `BIGBANG (빅뱅)`은 영문이 앞이므로 주-부 순서 규칙을 세울 수 없다.
  유닛 #3이 MusicBrainz에서 정규명과 MBID를 확정하므로 유닛 #2가 정규화하면
  동일 작업을 두 번 수행하고 뒤집게 된다.
- **결과**: `ArtistNameParser`는 다음을 산출한다.
  `raw`(원문 보존) / `primary_name` / `aliases`(괄호 별칭 후보)
  / `collaborators`(구분자 분리 후보) / `confidence`(HIGH·MEDIUM·LOW)
  / `ambiguity_reasons`(판정 불가 사유).
  판정이 애매한 경우 임의 결정하지 않고 LOW와 사유를 남겨 유닛 #3으로 넘긴다.
  **정규화 키**는 파서가 산출한다: 괄호 제거 + 공백 제거 + 소문자화.
  `소유 (SOYOU)`와 `소유(SOYOU)`처럼 표기만 흔들리는 경우를 동일 키로 묶어
  중복을 제거하고, MusicBrainz 조회 실패 시 폴백 식별자로 사용한다.
  정규명 확정은 유닛 #3의 책임이다.
- **한계**: `GD&TOP` 유형은 외부 조회로도 확정되지 않을 수 있다.
  이 경우 LOW 신뢰도로 원문을 단일 엔티티로 취급하고 수동 검토 목록에 남긴다.
- **D-0006 정정**: "파일명과 태그 교차검증으로 정규화 대상을 선별한다"는 성립하지 않는다.

  **아티스트명에 하이픈이 포함된 경우**이며 태그 오류가 아니다.
  파일명이 태그로부터 생성되었으므로 두 소스는 독립이 아니고 교차검증의 정보량이 0이다.
  해당 검증 절차를 폐기한다.

## D-0017. 정규화 기준을 ISRC에서 MusicBrainz MBID로 옮기고 Track을 폐기한다
- **배경**: 유닛 #3 착수 전 `Track.is_normalized` 정의 점검.
- **문제 1 — 판정 기준이 순환한다**: `is_normalized`는 ISRC 존재만 본다.
  그런데 D-0010 실측대로 TSRC 프레임은 1004곡 전량 부재이고,
  `TrackTags.isrc`에는 **유닛 #3의 조회 결과가 채워진다**고 명시돼 있다.
  정규화가 끝나야 ISRC가 생기는데 그 ISRC로 정규화 여부를 판정하는 구조다.
  현 정의로는 모든 곡이 영구히 `False`다.
- **문제 2 — ISRC는 정규화 완료의 증명이 아니다**: 발급 식별자일 뿐이다.
  ISRC를 보유해도 아티스트 표기가 `GD X TAEYANG`이면 분해가 끝나지 않았다.
- **문제 3 — bool로는 상태가 표현되지 않는다**: 정규화는 파생 속성이 아니라
  조회 사건의 결과다. 미조회 · 확정 · 매칭 실패 · 후보 다수가 구분돼야 하는데
  참거짓 두 값으로는 "MB에 없는 곡"과 "아직 조회 안 한 곡"이 같아진다.
  전자는 재조회가 무의미하고 후자는 반드시 재조회해야 한다.
- **문제 4 — Track이 유닛 #2 산출물을 담지 못한다**: `artist: str` 단일 문자열이라
  `ParsedArtist`의 다중 후보와 신뢰도가 들어갈 자리가 없다(D-0016).
- **후보**: (a) `is_normalized` 조건만 MBID로 교체
  / (b) 상태 enum으로 바꾸고 `Track`은 유지
  / (c) 상태 enum 도입 + `Track` 폐기, 유닛 #3이 정규 엔티티를 새로 정의
- **선택**: **(c).**
- **근거**: `Track`은 프로덕션 코드에서 참조 0건이다. 실제 데이터는
  `ScannedTrack`(관측) 경로로만 흐르고 `Track`은 P0 시절 껍데기로 남았다.
  쓰이지 않는 클래스를 유닛 #3 예상 형태로 미리 고치는 것은
  실측 없이 규칙을 세우는 것과 같다. 오늘 유닛 #2에서 배제한 방식이다.
  더 중요한 것은 잘못된 정의를 남겨두면 근거로 재사용된다는 점이다.
  `is_normalized` = ISRC는 D-0010 실측으로 이미 무효인데도 코드에 남아
  미해결 목록에 오르기까지 했다. 스텁은 교체 전제로만 유지할 가치가 있다.
- **정규화 기준**: **MusicBrainz Recording MBID 확보.**
  ISRC는 판정 기준에서 내리고 조회 보조 키로만 쓴다. 있으면 정확도가 오르지만
  필수가 아니다. 실측 보유율 0%인 값을 필수 조건에 두면 파이프라인이 멈춘다.
- **상태 모델**: 참거짓 대신 4상태로 둔다.
  `PENDING` 미조회 / `RESOLVED` MBID 확정 / `UNRESOLVED` 조회했으나 미등재
  / `AMBIGUOUS` 후보 다수로 수동 검토 대기.
  `UNRESOLVED`를 별도로 두는 이유는 인디·미등재 곡이 MB에 영구히 없기 때문이다.
  `PENDING`으로 두면 재조회를 무한 반복하고 `RESOLVED`로 두면 거짓이다.
  이 경우 D-0014의 `normalized_key` 폴백 식별자를 정규 신원으로 쓴다.
  `AMBIGUOUS`는 D-0014가 한계로 남긴 `GD&TOP` 유형의 귀결점이다.
- **결과**: `Track`과 그에 묶인 저장소 계층을 함께 삭제한다.
  `domain/entities/track.py` · `domain/ports/track_repository.py` ·
  `infrastructure/persistence/in_memory_track_repository.py` 3종이며
  셋 다 프로덕션 참조 0건으로 서로만 참조한다.
  `InMemoryTrackRepository`는 `TrackRepository`를 상속조차 하지 않아
  구조적 타이핑이 실제로 연결된 적도 없다.
  저장소 인터페이스는 정규 신원 엔티티가 확정된 뒤 그에 맞춰 다시 정의한다.
  정규 신원 엔티티는 유닛 #3이 실제 MusicBrainz 응답 형태를 확인한 뒤 정의한다.
  파이프라인은 `ScannedTrack`(관측) → 유닛 #2 `ParsedArtist`(분해)
  → 유닛 #3(정규 신원 확정)으로 흐르며 그 사이에 중간 엔티티를 두지 않는다.
- **부수 결정 — D-0016 미해결 항목 해소**: `parse_confidence` · `ambiguity_reasons` ·
  원문 `raw`는 `artists`가 아니라 `track_artists`에 둔다.
  같은 아티스트가 원문에 따라 다른 신뢰도로 파싱된다.
  `아이유(IU)`는 HIGH, `울랄라세션, 아이유(IU)`는 MEDIUM인데
  `normalized_key`가 같아 `artists` 한 행으로 수렴하므로 나중 스캔이 앞을 덮는다.
  파싱 신뢰도는 아티스트의 속성이 아니라 **어떤 원문에서 그 아티스트를 뽑았는가**의
  속성이다. 정규화 상태 4종도 곡 단위 값이므로 트랙 쪽에 둔다.
- **한계**: MusicBrainz 조회 실패율을 아직 모른다. `UNRESOLVED` 비율이 높으면
  `normalized_key` 폴백이 주 경로가 되고 P2 취향 벡터의 입력 품질이 떨어진다.
  **유닛 #3 착수 직후 247개 아티스트 표본으로 실측이 필요하다.**
- **이행**: 본 결정의 코드 반영은 위 3종 삭제와 `test_domain.py` 정리까지다.
  상태 enum과 정규 신원 엔티티는 유닛 #3 첫 커밋에서 함께 도입한다.
  정의만 미리 만들면 다시 쓰이지 않는 껍데기가 되어 문제 4가 반복된다.

## D-0018. R-1 해소 — GPU 실동작 확인, MERT 청크 10초 확정
- **배경**: 미해결 R-1 "GTX 1660Ti 6GB에서 Demucs·MERT 실동작 미확인".
  P2 착수 전 필수 확인 항목이었다.
- **측정 환경(2026-08-11, 리전)**: GTX 1660Ti / PyTorch 2.13.0+cu130 /
  Demucs 4.1.0 (htdemucs) / MERT-v1-95M(94M 파라미터).
  측정 대상은 실측 라이브러리 최장곡 408초와 평균 근사곡 218초.
- **가용 자원 정정**: 명목 6144MiB 중 디스플레이 출력이 약 1350MiB를 상시 점유해
  **실제 가용 VRAM은 약 4.8GB**다. 노트북 내장 디스플레이가 이 GPU에 물려 있다.
  또한 물리 RAM 8GB 중 **WSL 할당은 4.8GB**다. 두 값 모두 설계 전제에서
  6GB·8GB로 잡으면 안 된다.
- **Demucs 실측**: peak VRAM **549MB**. 218초 곡 11.7초, 408초 곡 19초.
  세그먼트 단위로 처리하므로 **VRAM이 곡 길이와 무관하다**(두 경우 모두 549MB).
  약 19~21배속이며 총 재생시간 64.1시간 기준 **배치 약 3.4시간**.
  제약 없이 사용 가능하다.
- **MERT 문제 — 전곡 단위 추론은 불가능하다**: 트랜스포머라 시퀀스 전체를
  한 번에 처리하며 어텐션이 길이 제곱으로 붙는다.
  218초 곡은 peak VRAM 4480MB로 가용 4.8GB의 93%를 쓰고 25초에 끝나지만,
  408초 곡은 **8062MB로 물리 VRAM을 초과**한다.
  이때 WSL의 CUDA 통합 메모리가 시스템 RAM으로 넘겨받아 죽지는 않으나
  PCIe를 경유하므로 **449초가 걸린다**. 곡 길이 1.87배에 시간 18배다.
  실행이 되는 것과 쓸 수 있는 것은 다르다. 전곡 추론은 배제한다.
- **청크 크기 실측(408초 곡, 모델 로딩 제외 순수 추론)**:

  | 청크 | 시간 | peak VRAM | 벡터 수 |
  |---|---|---|---|
  | 5초 | 3.78s | 462MB | 82 |
  | **10초** | **3.39s** | **557MB** | **41** |
  | 30초 | 3.99s | 935MB | 14 |
  | 60초 | 4.95s | 1500MB | 7 |
  | 120초 | 6.84s | 2629MB | 4 |

- **선택**: **청크 10초.**
- **근거**: 세 기준이 모두 같은 값을 가리키며 상충하지 않는다.
  (1) 속도 — 5초는 청크 82개의 커널 호출 오버헤드가, 30초 이상은 어텐션
  제곱이 붙는다. 10초가 그 사이의 최저점이다.
  (2) 메모리 — 557MB로 Demucs 549MB와 동시 적재해도 1.1GB다.
  (3) 시간 해상도 — 대중가요 한 섹션이 통상 15~30초다. 30초 청크는 벌스와
  코러스를 한 벡터에 뭉갠다. 10초면 섹션 내부 변화까지 잡힌다.
  5초는 속도가 밀리면서 벡터 수만 두 배가 되어 저장 비용만 는다.
- **결과**: R-1을 해소하고 다음을 P2 설계 전제로 둔다.
  Demucs는 제약 없이 사용한다. MERT는 **10초 청크 분할이 요구사항**이며
  선택 사항이 아니다. 청크별 `last_hidden_state`를 시간축 평균해
  청크당 768차원 벡터 하나를 얻는다.
  두 모델 합계 VRAM 약 1.1GB로 동일 프로세스에서 순차 실행이 가능하다.
- **배치 소요 추정**: 총 재생시간 64.1시간 / 1004곡 기준
  Demucs 약 3.4시간 + MERT 약 1시간으로 **5시간 이내**다.
  D-0015의 백그라운드 중단·재개 설계로 수용 가능한 범위다.
- **한계**: MERT-v1-330M은 미측정이다. 파라미터가 3.5배이므로 청크 10초에서도
  VRAM이 2GB를 넘길 수 있다. 95M으로 P2를 시작하고 표현력이 부족하면
  그때 330M을 실측한다. **실측 전까지 330M 사용을 가정하지 않는다.**
  청크 경계에서 문맥이 끊기는 문제도 남는다. 중첩 청크로 완화할 수 있으나
  연산량이 비례해 늘어난다. P2에서 벡터 품질을 보고 판단한다.
- **부수 확인**: 1660Ti는 Turing이지만 GTX 16xx 계열이라 텐서코어가 없다.
  fp16 커널은 정상 동작하나 가속 이득이 없다. 두 모델 모두 fp32로 측정했으며
  현 성능으로 충분하므로 half precision 최적화는 도입하지 않는다.
- **오디오 디코딩 미결**: 측정에는 soundfile을 썼다. torchaudio 최신 버전이
  자체 디코더를 제거하고 torchcodec에 위임하는데 그것이 ffmpeg 5 이상을
  요구해 환경(4.4.2)과 맞지 않는다. 프로덕션 디코더는 유닛 #4에서 정한다.
  2대 환경에 ffmpeg 4.4.2가 이미 통일돼 있으므로 서브프로세스 호출이 유력하다.

## D-0019. MusicBrainz 조회는 2단계 구조로 하고 78.5%를 상한으로 받아들인다
- **배경**: O-1·O-2 해소. 유닛 #3 착수 전 MB 조회 성공률 실측.
- **측정(2026-08-12)**: `tools/probe_musicbrainz.py`. 실측 1004곡 / 고유 후보 249개.
  판정은 검색 1·2순위 **점수 격차**로 한다. MB는 부분 일치에도 100점을 주므로
  점수 단독으로는 오답을 거를 수 없다. 격차 10점 미만은 AMBIGUOUS로 둔다.
- **아티스트 조회 결과**: RESOLVED **84.3%**(210) / AMBIGUOUS **13.7%**(34)
  / UNRESOLVED **2.0%**(5).
  한국 아티스트 커버리지는 우려보다 좋다. 미등재는 `디핵` `명카드라이브`
  `전혜성` `조이` `하이포` 5건뿐이다.
- **곡 조회 결과**: RESOLVED **78.5%**(788) / UNRESOLVED **21.5%**(216).
- **개선 경로**: 같은 코퍼스에서 39.0% → 77.9% → 78.5%로 올랐다.
  첫 도약(+38.9%p)은 2단계 조회 도입, 둘째(+0.6%p)는 중첩 괄호 처리다.
  두 번째 폭이 작다는 사실이 중요하다. 남은 실패는 코드로 더 줄지 않는다.
- **문제 — 태그 표기로는 곡을 찾을 수 없다**: 아티스트 필드의 한글 표기와
  MB 정규명이 다르다. `아이유`로 조회하면 실패하고 `IU`로는 성공한다.
  `엠씨더맥스`와 `M.C the MAX`, `싸이`와 `PSY`, `씨스타`와 `SISTAR`도 같다.
  1단계 아티스트 조회에서 이미 정규명을 확보하고도 2단계에서 쓰지 않으면
  한글 표기 아티스트가 통째로 누락된다. 실제로 아이유 64곡이 전량 실패했다.
- **후보**: (a) 태그 원문으로 곡을 직접 조회
  / (b) 아티스트를 먼저 확정하고 그 정규명으로 곡을 조회
  / (c) AcoustID 지문으로 곡을 먼저 식별하고 아티스트를 역으로 얻음
- **선택**: **(b).**
- **근거**: (a)는 실측 39.0%로 성립하지 않는다.
  (c)는 지문 계산에 곡당 오디오 디코딩이 필요해 비용이 크고,
  P4 로컬 에이전트에서 사용자 라이브러리 전체에 적용하기 어렵다.
  MB 미등재 곡에는 어차피 듣지 않으므로 (b)의 실패분을 메우지도 못한다.
  (b)는 조회 횟수가 고유 아티스트 249회 + 곡 1004회로 끝나고,
  1단계 결과를 캐시하면 재스캔 시 2단계만 다시 돌면 된다.
- **결과**: 조회는 2단계로 한다.
  1단계에서 파서가 분해한 후보(D-0016)별로 아티스트를 조회해 정규명과 MBID를
  확보하고, 2단계에서 그 **정규명**으로 Recording을 조회한다.
  **AMBIGUOUS 후보는 정규명으로 치환하지 않는다.** 어느 후보가 맞는지
  확정되지 않은 상태에서 치환하면 오답이 곡 조회로 전파된다.
  제목의 부가 표기는 조회 전에 제거한다. 괄호 깊이를 세어야 한다 —
  `(Feat. 펀치(Punch))`처럼 중첩되므로 정규식으로는 닫는 괄호가 남는다.
  단 `아파 (Slow)` `무제(無題)` 같은 곡명 일부와 `(Korean Ver.)` 같은
  버전 표기는 보존한다. 버전은 레코딩을 구분하는 단서다.
- **남은 실패 216건의 유형**: 코드 결함이 아니라 데이터 자체의 한계다.
  (1) **MB 곡 단위 커버리지 부족** — 아티스트는 등재돼 있으나 개별 레코딩이
  없다. 폴킴 25곡 중 15건, Primary 6곡 중 5건, 태양 7곡 중 4건 실패.
  아티스트 단위 커버리지(98%)와 곡 단위 커버리지가 크게 다르다.
  (2) **정규명 치환의 역효과** — `효린 → Hyolyn`으로 치환하니 4곡 전량 실패했다.
  `대성 → 강대성`도 5곡 전량 실패다. MB 아티스트 정규명과 레코딩 크레딧
  표기가 어긋나는 경우이며, 1단계가 RESOLVED여도 발생한다.
  (3) **버전·수록 맥락 표기** — `(Ballad Ver.)` `(Media Ver.)`
  `(Into the Unknown End Credit Version)` 등. 보존 정책의 대가다.
  (4) **1단계 UNRESOLVED의 전파** — `전혜성` `키네틱 플로우` `하이포` 등.
- **한계**: 78.5%를 상한으로 본다. 세 번째 반복에서 개선 폭이 0.6%p로
  떨어졌고 남은 실패가 코드로 줄지 않는 유형에 몰려 있다.
  더 짜내려면 (2)에 대한 재시도 경로(정규명 실패 시 태그 표기로 재조회)를
  넣을 수 있으나 조회 횟수가 두 배가 되고 이득은 수십 건 수준이다.
  **P2 착수 전에는 하지 않는다.**
- **D-0017과의 관계**: 정규화 상태 4종이 실측으로 뒷받침됐다.
  RESOLVED 78.5%는 MBID 확보분이고, UNRESOLVED 21.5%는 `normalized_key`
  폴백 경로다. 우려했던 "폴백이 주 경로가 되는" 상황은 아니다.
  AMBIGUOUS는 이번 측정에서 곡 단위로 분리해 세지 않았다. 아티스트
  13.7%가 동명이인으로 격차 미달이며, 곡에서도 `좋은 날`처럼 리마스터·
  라이브가 다수인 경우 격차가 나지 않는다. **보유 중인 `duration_ms`로
  해소 가능한지는 미검증이다(O-5).**
