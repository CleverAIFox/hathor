## D-0001. MongoDB를 core 프로파일에 유지한다

- **배경**: 8GB RAM 노드에서 P0~P2 동안 MongoDB 용처가 없어 제외를 제안했다.
- **후보**: (a) 제거 후 §3.7 착수 시 추가 / (b) core에 유지
- **선택**: **(b) 유지.** **사용자 판단으로 결정됨.**
- **근거**: 폴리글랏 저장소(§3.7)가 설계 확정 사항이며, 나중에 붙이는 비용보다 처음부터 켜두는 편이 낫다는 판단.
- **결과**: `mongo:8`을 core에 두되 `--wiredTigerCacheSizeGB 0.25`, `mem_limit 512m`으로 제한.
  core 프로파일 메모리 상한 합계 약 2.3GB → 약 2.8GB.

## D-0002. 본인 보컬 시드 녹음을 P7까지 연기한다

- **배경**: 부록 E 착수 순서 4는 보컬 녹음을 크리티컬 패스로 지정했다.
- **후보**: (a) P0에 즉시 착수 / (b) 연기하고 필요 시 수집
- **선택**: **(b) 연기.** **사용자 판단으로 결정됨.**
- **근거**: 가창 개인화는 후순위이며, 파이프라인이 임의 시점에 화자 데이터를 받아
  재학습하는 구조로 만들면 조기 수집의 이점이 사라진다.
- **결과**: `hathor.vocal`은 **화자 무의존 설계**로 간다. 화자 임베딩을 런타임 주입 파라미터로
  두고, 시드 화자는 교체 가능한 자원으로 취급한다. 부록 E 착수 순서 4를 삭제하고
  "화자 데이터 수집은 상시, 학습은 요청 시" 원칙으로 대체한다.

## D-0003. 실존 가수의 음색 복제·보간은 구현하지 않는다

- **배경**: 라이브러리 아티스트의 음색·발성을 학습해 보간하는 방안이 제기됨.
- **후보**: (a) 라이브러리 실존 가수 음색 학습 / (b) 공개 다화자 가창 DB 기반 화자 공간 학습
- **선택**: **(b).**
- **근거**: 국내법상 음성은 인격권·퍼블리시티권(부정경쟁방지법 제2조 파목) 보호 대상이며,
  식별 가능한 실존 가수의 음색 재현은 개인 연구라도 면책되지 않는다.
  부록 D 저작권 답변("실존 화자 복제 미구현")과도 정면 충돌하며,
  포트폴리오 심사에서 자산이 아니라 결격 사유로 작동한다.
- **결과**: 화자 임베딩 공간은 **라이선스가 명확한 공개 다화자 가창 DB**로만 학습한다(부록 B).
  보간은 익명 화자 공간 내부에서 수행한다. 사용자 본인 음성은 언제든 시드로 추가 가능.
  라이브러리 음원은 **편성·화성·리듬 등 음악적 통계 추출 전용**이며 성문 특징은 추출하지 않는다.

## D-0004. 저장소를 WSL ext4에 두고 F 드라이브는 데이터 전용으로 쓴다

- **배경**: `/mnt/f`(drvfs)에서 `uv sync`가 symlink 생성 실패(`Operation not permitted`)로 중단.
- **후보**: (a) drvfs에서 우회 옵션으로 강행 / (b) 저장소를 WSL ext4로 이전
- **선택**: **(b).**
- **근거**: drvfs는 POSIX symlink를 지원하지 않으며, 파일 I/O가 ext4 대비 10~20배 느리다.
  우회는 성능 문제를 해결하지 못한다.
- **결과**: 코드는 `~/projects/hathor`(ext4), 음원·체크포인트는 `/mnt/f`,
  DB는 Docker named volume(WSL 내부)에 둔다.
  노트북 2대(자취방 GTX 1660Ti / 광인사 13코어 무GPU) 동기화는
  GitHub + `pg_dump` 스냅샷(`/mnt/f/hathor-state`)으로 처리한다.

## D-0005. 가사는 태그 우선, STT 폴백 경로를 유지한다

- **배경**: step0 실측 결과 라이브러리 1004곡의 USLT(비동기 텍스트 가사) 보유율 100%.
  SYLT(시간 동기) 0%.
- **후보**: (a) STT 경로 삭제 / (b) 포트만 정의하고 구현 보류
- **선택**: **(b).** **사용자 판단으로 결정됨.**
- **근거**: 100%는 현 사용자 라이브러리의 속성이지 시스템이 보장하는 값이 아니다.
  향후 사용자는 태그 없는 음원을 투입한다. 눈앞의 통계에 설계를 맞추면 확장성을 잃는다.
- **결과**: `LyricsSource` 포트를 정의한다. `TagLyricsSource`는 P1에서 구현,
  `WhisperLyricsSource`는 인터페이스만 두고 P2 이후 구현한다.
  SYLT가 0%이므로 **한국어 강제 정렬(forced alignment)이 P2 필수 과제**로 승격된다
  (음절 정합률 97% 검증에 음절↔시각 매핑이 필요).

## D-0006. ISRC 부재로 Chromaprint 지문 정규화가 주 경로가 된다

- **배경**: step0 실측 — ISRC 0%, 발매일 0%, 제목·아티스트·앨범 각 100%.
- **결과**: AcoustID + MusicBrainz 조회를 P1 필수 경로로 승격한다(선택 아님).
  발매일은 동일 조회로 함께 복구한다. 발매일 부재 시 취향 벡터의 시대 축을 만들 수 없다.
  파일명이 `아티스트-제목.mp3` 규칙으로 100% 일관되므로 태그와 교차검증하여
  불일치 곡을 정규화 우선 검토 대상으로 선별한다.
  아티스트 필드에 피처링이 혼재하므로(`10CM, BIG Naughty (서동현)`)
  아티스트 엔티티 분리 파서가 P1에 필요하다.

## D-0007. 샘플레이트는 인제스트에서 통일하지 않는다

- **배경**: 44.1kHz 76.8% / 48kHz 23.2% 혼재. 포맷은 100% mp3.
- **후보**: (a) 인제스트에서 44.1kHz로 통일 / (b) 원본 유지 후 모델 입력 직전 리샘플
- **선택**: **(b).**
- **근거**: 모델별 요구 샘플레이트가 상이하다(MERT 24kHz, CLAP 48kHz, Demucs 44.1kHz).
  사전 통일은 정보 손실만 발생시키고 어느 모델에도 최적이 아니다.
- **결과**: 원본 유지, 모델 입력 직전 리샘플.
  **한계**: 전량 mp3(손실 압축)이므로 스템 분리 품질에 원리적 상한이 있다.
  FAD 등 지표 해석 시 이 한계를 명시한다.

## D-0008. MASTER.md는 단일 진실 공급원이되 코드가 충돌 시 우선한다
- **배경**: MASTER.md 4300줄은 사용자가 직접 작성하지 않았고 전량 검증되지 않았다.
  설계 논의 중 "MASTER에 무엇이 정의되어 있는가"를 확인할 수 없어 진행이 정체됐다.
- **후보**: (a) MASTER.md 폐기 후 코드+DECISIONS만 유지 / (b) 단일 진실 공급원 유지 + 개정 절차 명시
- **선택**: **(b).**
- **근거**: 문서 폐기는 전역 설계 시야를 잃는다. 문제는 문서의 존재가 아니라
  미검증 내용이 확정 사실처럼 취급되는 것이다.
- **결과**: MASTER.md는 단일 진실 공급원을 유지한다.
  코드와 MASTER.md가 충돌하면 **코드가 우선**하며, 충돌 발견 즉시 MASTER.md를 갱신한다.

  미검증 항목은 추측으로 유지하지 않고 실측 후 확정한다(GR-0.5).

## D-0009. 노트북 2대 역할을 재정의하고 파이썬 3.12로 고정한다
- **배경**: 광인사 노트북 실측 — Intel Ultra 7 155U / RAM 16GB / 내장 그래픽 / 저장소 477GB.
  리전 노트북은 GTX 1660Ti 6GB / RAM 8GB(WSL 4.8GB 할당).
  기존 D-0004는 광인사를 "인프라 노드"로 규정했으나 실제 스펙은 반대다.
  추가로 `requires-python = ">=3.12"`만 지정되고 `.python-version`이 부재하여
  광인사에서 CPython 3.14.4, 리전에서 3.12가 선택되는 불일치가 발생했다.
- **후보**: (a) 기존 역할 유지 / (b) 역할 교체
- **선택**: **(b), 파이썬은 3.12 고정.**
- **근거**: P1~P3 인제스트·분석 배관은 GPU를 요구하지 않으며 RAM과 코어 수가 지배적이다.
  광인사가 RAM 2배, 코어 수 우위다. GPU는 P4 모델 학습 시점부터 필요하다.
  파이썬 3.14는 PyTorch 휠 지원이 확인되지 않았고, P4에서 재구성 비용이 발생한다.
- **결과**: **광인사 = 주 개발기, 리전 = GPU 워커.**
  `.python-version`에 3.12를 핀하여 2대 간 인터프리터를 일치시킨다(재현성 CI 잡 보호).
  **한계**: 리전 RAM 8GB에서 docker compose 5종 + PyTorch 동시 구동은 P4에서 재검토 필요.
  라이브러리 루트 경로가 머신마다 다르므로(리전 `/mnt/f`, 광인사 `/mnt/d`)
  `HATHOR_LIBRARY_ROOT` 환경변수로 외부화한다.

## D-0010. ID3 전수 조사 결과 유효 태그는 4종이며 태그 기반 메타데이터 경로를 폐기한다
- **배경**: step0가 `easy=True` 매핑을 사용했을 경우 ID3v2.3 `TYER` 등이 누락될 가능성을 제기하여
  1004곡 원시 프레임 전수 조사를 수행했다(`tools/probe_id3.py`).
- **실측 결과**: 읽기 실패 0. 파일명 NFD 0(전량 NFC).
  TIT2 / TPE1 / TALB / USLT / APIC / POPM 각 100%. TSSE 62.8%.
  TSOA 3.7% / TSOP 0.8% / TSOT 0.7%.
  **발매일 프레임(TDRC·TDRL·TDOR·TYER·TDAT·TORY) 전량 0%. TSRC 0%. SYLT 0%.**
  **TRCK·TPE2·TCON·TPOS 전량 부재.**
- **결과**: D-0006의 전제(ISRC·발매일 부재)가 **확증**되었다. 가설은 기각.
  D-0005의 전제(USLT 100%, SYLT 0%)도 확증.
  인제스트가 태그에서 읽는 필드를 **제목·아티스트·앨범·가사 4종으로 한정**한다.
  트랙번호·디스크번호·장르·앨범아티스트 필드는 도메인 모델에서 삭제한다(전량 부재).
  발매일·ISRC는 도메인에 필드로 유지하되 항상 None이며, 유닛 #3 외부 조회가 채운다.
  파일명 유니코드 정규화는 방어적으로 유지하되 실측상 불필요하다.
  POPM은 전곡 동일 최고값으로 분산이 0이므로 **선호도 신호로 사용하지 않는다**(존재 여부만 기록).
  앨범아트는 APIC 100%를 사용한다. `앨범 커버/` 폴더(743개, 앨범 단위, .jfif)는
  파일명↔TALB 매칭 로직이 추가로 필요하므로 P1에서 사용하지 않고 교차검증용으로 보존한다.
  P1 스캔 산출물에는 이미지 바이트를 포함하지 않고 `has_album_art` 불리언만 기록한다.
- **한계**: POPM 100% + 발매일 0% 조합은 일반적인 구매·리핑 경로에서 발생하지 않는다.
  태그 출처를 신뢰할 근거가 약하므로 지문 기반 정규화(D-0006)의 필요성이 강화된다.

## D-0011. 취향은 선호도 예측이 아니라 조건부 생성으로 다룬다
- **배경**: 라이브러리 1004곡은 전량 사용자가 선호하여 다운로드한 곡이고 POPM도 전곡 동일 최고값이다.
  선호도 이진 분류기를 학습할 음성 사례가 저장소 내에 존재하지 않는다.
- **후보**: (a) 외부 카탈로그에서 네거티브 샘플링하여 선호도 예측 모델 학습
  / (b) 라이브러리 전체를 균일 선호로 전제하고 스타일 조건부 생성으로 전환
- **선택**: **(b).**
- **근거**: (a)는 음성 사례의 대표성을 보장할 수 없고 편향이 결과에 직결된다.
  "이 곡을 좋아할 것인가"는 음성 사례를 요구하지만
  "이런 느낌으로 생성하라"는 양성 사례만으로 성립한다.
  균일 양성 데이터가 결함이 아니라 전제가 된다.
- **결과**: 라이브러리를 **음악·편곡·가사·가창 4축**으로 분석하여 잠재 표현을 구축한다.
  - 음악: 코드 진행, 멜로디, 조성, BPM
  - 편곡: 악기 구성, 음색, 섹션 구조, 믹스 (**스템 분리 의존**)
  - 가사: 주제, 어휘, 정서, 운율 (USLT 100% 확보)
  - 가창: 창법, 음역, 비브라토, 표현 (**보컬 스템 의존**)
  생성 시 사용자 입력은 **시드곡 선택** 방식을 채택한다(형용사 체크박스 아님).
  라이브러리에서 참조곡 1~5개를 선택하면 해당 잠재 표현을 조건으로 사용한다.
  **축별로 다른 시드 지정을 허용한다**(예: 멜로디는 A곡, 가창은 B곡).
  체크박스형 입력은 시드 위의 미세조정 수단으로만 부수 제공한다.
  앨범아트는 선호도 신호에서 제외하고, 음악↔이미지 대응 학습에만 사용하여
  P6~P7 생성 결과물의 커버 생성 후처리에 활용한다.
  **한계**: 편곡·가창축은 스템 분리(추가 약 35GB)에 의존하므로 P2 병목이다.
  가사축만 P1 산출물로 즉시 착수 가능하다.

## D-0012. 취향 웜스타트는 적응적 쌍대비교로 수행한다
- **배경**: 시드곡 조건(D-0011)은 매 생성 시점의 지역 조건이며, 전역 취향 사전확률이 별도로 필요하다.
  사용자가 "이상형 월드컵" 형태의 강제 온보딩을 제안했다.
- **후보**: (a) 전곡 단일 토너먼트(1003회 비교) / (b) 64강 무작위 추출(63회)
  / (c) 적응적 쌍대비교(20~30회)
- **선택**: **(c).**
- **근거**: 쌍대비교는 절대 라벨 없이 상대 순위 신호를 생성하므로
  D-0011의 음성 사례 부재 문제를 외부 데이터 없이 완화한다.
  무작위 추출은 유사곡 쌍에서 정보량이 0에 수렴한다.

  / (c) 명시적 재스캔 + 이전 스냅샷 대비 델타 감지
- **선택**: **(c).**
- **근거**: (a)는 drvfs 경유 NTFS 외장 볼륨에서 리눅스 inotify가 변경 알림을 수신하지 못해

  **실측 완료(2026-08-10, /mnt/d)**: `inotify_add_watch`는 유효한 watch descriptor를 반환하지만

  감시가 조용히 실패한다. 이 실패 양상 때문에 (a)는 재고 대상이 아니다.
  (b)는 상시 데몬을 요구하는데 노트북 2대를 오가는 환경(D-0009)에서
  어느 쪽 상태가 최신인지 모호해지고 관리 비용이 이득을 넘는다.
  음원 라이브러리는 사용자가 곡을 내려받는 시점에만 변한다.
  변경 빈도가 월 단위이므로 실시간 감시는 과잉이다.
  명시적 실행은 "이 산출물은 이 시점 상태"를 명확히 하여 재현성과 정합한다.
- **결과**: 사용자가 `ingest scan`을 명시적으로 실행한다.
  이전 스냅샷이 존재하면 대조하여 도메인 이벤트 4종으로 분류한다:
  `TrackDiscovered`(신규) / `TrackModified`(변경) / `TrackRemoved`(소실) / `TrackUnchanged`(무변화).
  **여기서 이벤트는 파일시스템 이벤트가 아니라 도메인 이벤트다.**
  델타 판정 기준은 `modified_at`(mtime)과 `file_size_bytes`이며 둘 다 이미 ScannedTrack에 있다.
  **성능 실측(2026-08-10, 리전, /mnt/f drvfs)**: 1004곡 초회 스캔 10.8초, 재스캔 9.6초.

  절감 여지가 약 7초에 불과해 스캐너에 baseline을 주입하는 설계 복잡도를 정당화하지 못한다.
  인제스트 단계에서는 추출 생략을 구현하지 않는다.
  추출 생략이 실질적 이득을 내는 지점은 곡당 GPU 연산이 발생하는 P2 스템 분리이며,
  해당 단계에서 델타 기반 건너뛰기를 별도로 구현한다.
  스냅샷 비교 대상은 P1에서 직전 JSONL 산출물이고, 유닛 #4 이후 PostgreSQL로 승격한다.

- **한계**: mtime·size 동일하되 내용이 바뀐 파일은 감지하지 못한다.

  **숫자는 비교에서 제외한다.** `DAY6` `10CM` `4FIRE`의 숫자는
  표기 체계 신호가 아니라 이름의 일부다. 제외하지 않으면
  `DAY6 (Even of Day)` `WSG워너비(4FIRE)`가 별칭으로 오분류된다. 둘 다 유닛이다.
  **실측 괄호 67건 기준 오분류 0건.**
- **결과**: `ArtistNameParser`의 산출을 다음으로 개정한다.
  `ParsedArtist`는 `raw` / `primary` / `collaborators` / `confidence` /
  `ambiguity_reasons`를 갖고, `primary`와 `collaborators`의 원소는
  `ArtistCandidate(name, aliases)`다. 괄호 별칭이 해당 이름에 묶인다.
  `normalized_key`는 `ParsedArtist`와 `ArtistCandidate` 양쪽에 둔다.
  전자는 원문 전체 기준으로 중복 제거·캐시에 쓰고,
  후자는 후보 단위로 유닛 #3 조회 키에 쓴다. 산출 규칙은 D-0014 그대로다.
- **처리 순서**: 쉼표 분리를 괄호 추출보다 **먼저** 수행한다.
  `나윤권, 아이유(IU)`에서 IU는 문자열 전체가 아니라 마지막 토큰의 별칭이다.
  순서가 반대면 쉼표 복합 24건 전부에서 별칭이 엉뚱한 이름에 붙는다.
  쉼표 분리는 괄호 깊이를 세어 최상위에서만 자른다.
  `이유 갓지(GOD G) 않은 이유(박명수, 아이유)`처럼 괄호 안에 쉼표가 있고,
  `미연((여자)아이들)`처럼 괄호가 중첩된다.
- **신뢰도**: 토큰별로 판정한 뒤 **최악값**을 취한다.
  하락 사유가 하나라도 있으면 LOW다. 쉼표로 분리된 경우 상한을 MEDIUM으로 둔다.
  D-0014의 "괄호만 있으면 HIGH"는 폐기한다. 소속 의심이 우선한다.
- **결합어**: `&` `＆` `+` `＋`와 단독 토큰 `x` `X` `×` `vs` `VS`를 동일 부류로 본다.
  분리하지 않고 신뢰도만 LOW로 내린다. 분리하면 `Earth, Wind & Fire`가 깨지고,
  방치하면 `GD X TAEYANG`이 단일 아티스트로 확정된다. 판정은 유닛 #3에 넘긴다.
  단어형은 공백으로 분리된 단독 토큰만 센다. `MAX` `X-teen` 오탐 방지다.
- **한계**: 하위 유닛·서브그룹은 표기 체계로 원리상 판별되지 않는다.
  숫자 제외 규칙으로 실측 2건은 해소됐으나 우연에 가깝다.
  MusicBrainz에 독립 아티스트로 등재되어 있으므로 유닛 #3이 처리한다.
- **D-0014 정정**: 결과 정의의 `primary_name` / `aliases` / `collaborators`
  평탄 구조를 위 중첩 구조로 대체한다. 나머지 조항은 유효하다.

## D-0017. 정규화 기준을 ISRC에서 MusicBrainz MBID로 옮기고 Track을 폐기한다
- **배경**: 유닛 #3 착수 전 `Track.is_normalized` 정의 점검.
- **문제 1 — 판정 기준이 순환한다**: `is_normalized`는 ISRC 존재만 본다.
  그런데 D-0010 실측대로 TSRC 프레임은 1004곡 전량 부재이고,
  `TrackTags.isrc`에는 **유닛 #3의 조회 결과가 채워진다**고 명시돼 있다.
  정규화가 끝나야 ISRC가 생기는데 그 ISRC로 정규화 여부를 판정하는 구조다.
  현 정의로는 모든 곡이 영구히 `False`다.
- **문제 2 — ISRC는 정규화 완료의 증명이 아니다**: 발급 식별자일 뿐이다.
  ISRC를 보유해도 아티스트 표기가 `GD X TAEYANG`이면 분해가 끝나지 않았다.
- **문제 3 — bool로는 상태가 표현되지 않는다**: 정규화는 파생 속성이 아니라
  조회 사건의 결과다. 미조회 · 확정 · 매칭 실패 · 후보 다수가 구분돼야 하는데
  참거짓 두 값으로는 "MB에 없는 곡"과 "아직 조회 안 한 곡"이 같아진다.
  전자는 재조회가 무의미하고 후자는 반드시 재조회해야 한다.
- **문제 4 — Track이 유닛 #2 산출물을 담지 못한다**: `artist: str` 단일 문자열이라
  `ParsedArtist`의 다중 후보와 신뢰도가 들어갈 자리가 없다(D-0016).
- **후보**: (a) `is_normalized` 조건만 MBID로 교체
  / (b) 상태 enum으로 바꾸고 `Track`은 유지
  / (c) 상태 enum 도입 + `Track` 폐기, 유닛 #3이 정규 엔티티를 새로 정의
- **선택**: **(c).**
- **근거**: `Track`은 프로덕션 코드에서 참조 0건이다. 실제 데이터는
  `ScannedTrack`(관측) 경로로만 흐르고 `Track`은 P0 시절 껍데기로 남았다.
  쓰이지 않는 클래스를 유닛 #3 예상 형태로 미리 고치는 것은
  실측 없이 규칙을 세우는 것과 같다. 오늘 유닛 #2에서 배제한 방식이다.
  더 중요한 것은 잘못된 정의를 남겨두면 근거로 재사용된다는 점이다.
  `is_normalized` = ISRC는 D-0010 실측으로 이미 무효인데도 코드에 남아
  미해결 목록에 오르기까지 했다. 스텁은 교체 전제로만 유지할 가치가 있다.
- **정규화 기준**: **MusicBrainz Recording MBID 확보.**
  ISRC는 판정 기준에서 내리고 조회 보조 키로만 쓴다. 있으면 정확도가 오르지만
  필수가 아니다. 실측 보유율 0%인 값을 필수 조건에 두면 파이프라인이 멈춘다.
- **상태 모델**: 참거짓 대신 4상태로 둔다.
  `PENDING` 미조회 / `RESOLVED` MBID 확정 / `UNRESOLVED` 조회했으나 미등재
  / `AMBIGUOUS` 후보 다수로 수동 검토 대기.
  `UNRESOLVED`를 별도로 두는 이유는 인디·미등재 곡이 MB에 영구히 없기 때문이다.
  `PENDING`으로 두면 재조회를 무한 반복하고 `RESOLVED`로 두면 거짓이다.
  이 경우 D-0014의 `normalized_key` 폴백 식별자를 정규 신원으로 쓴다.
  `AMBIGUOUS`는 D-0014가 한계로 남긴 `GD&TOP` 유형의 귀결점이다.
- **결과**: `Track`과 그에 묶인 저장소 계층을 함께 삭제한다.
  `domain/entities/track.py` · `domain/ports/track_repository.py` ·
  `infrastructure/persistence/in_memory_track_repository.py` 3종이며
  셋 다 프로덕션 참조 0건으로 서로만 참조한다.
  `InMemoryTrackRepository`는 `TrackRepository`를 상속조차 하지 않아
  구조적 타이핑이 실제로 연결된 적도 없다.
  저장소 인터페이스는 정규 신원 엔티티가 확정된 뒤 그에 맞춰 다시 정의한다.
  정규 신원 엔티티는 유닛 #3이 실제 MusicBrainz 응답 형태를 확인한 뒤 정의한다.
  파이프라인은 `ScannedTrack`(관측) → 유닛 #2 `ParsedArtist`(분해)
  → 유닛 #3(정규 신원 확정)으로 흐르며 그 사이에 중간 엔티티를 두지 않는다.
- **부수 결정 — D-0016 미해결 항목 해소**: `parse_confidence` · `ambiguity_reasons` ·
  원문 `raw`는 `artists`가 아니라 `track_artists`에 둔다.
  같은 아티스트가 원문에 따라 다른 신뢰도로 파싱된다.
  `아이유(IU)`는 HIGH, `울랄라세션, 아이유(IU)`는 MEDIUM인데
  `normalized_key`가 같아 `artists` 한 행으로 수렴하므로 나중 스캔이 앞을 덮는다.
  파싱 신뢰도는 아티스트의 속성이 아니라 **어떤 원문에서 그 아티스트를 뽑았는가**의
  속성이다. 정규화 상태 4종도 곡 단위 값이므로 트랙 쪽에 둔다.
- **한계**: MusicBrainz 조회 실패율을 아직 모른다. `UNRESOLVED` 비율이 높으면
  `normalized_key` 폴백이 주 경로가 되고 P2 취향 벡터의 입력 품질이 떨어진다.
  **유닛 #3 착수 직후 247개 아티스트 표본으로 실측이 필요하다.**
- **이행**: 본 결정의 코드 반영은 위 3종 삭제와 `test_domain.py` 정리까지다.
  상태 enum과 정규 신원 엔티티는 유닛 #3 첫 커밋에서 함께 도입한다.
  정의만 미리 만들면 다시 쓰이지 않는 껍데기가 되어 문제 4가 반복된다.

## D-0018. R-1 해소 — GPU 실동작 확인, MERT 청크 10초 확정
- **배경**: 미해결 R-1 "GTX 1660Ti 6GB에서 Demucs·MERT 실동작 미확인".
  P2 착수 전 필수 확인 항목이었다.
- **측정 환경(2026-08-11, 리전)**: GTX 1660Ti / PyTorch 2.13.0+cu130 /
  Demucs 4.1.0 (htdemucs) / MERT-v1-95M(94M 파라미터).
  측정 대상은 실측 라이브러리 최장곡 408초와 평균 근사곡 218초.
- **가용 자원 정정**: 명목 6144MiB 중 디스플레이 출력이 약 1350MiB를 상시 점유해
  **실제 가용 VRAM은 약 4.8GB**다. 노트북 내장 디스플레이가 이 GPU에 물려 있다.
  또한 물리 RAM 8GB 중 **WSL 할당은 4.8GB**다. 두 값 모두 설계 전제에서
  6GB·8GB로 잡으면 안 된다.
- **Demucs 실측**: peak VRAM **549MB**. 218초 곡 11.7초, 408초 곡 19초.
  세그먼트 단위로 처리하므로 **VRAM이 곡 길이와 무관하다**(두 경우 모두 549MB).
  약 19~21배속이며 총 재생시간 64.1시간 기준 **배치 약 3.4시간**.
  제약 없이 사용 가능하다.
- **MERT 문제 — 전곡 단위 추론은 불가능하다**: 트랜스포머라 시퀀스 전체를
  한 번에 처리하며 어텐션이 길이 제곱으로 붙는다.
  218초 곡은 peak VRAM 4480MB로 가용 4.8GB의 93%를 쓰고 25초에 끝나지만,
  408초 곡은 **8062MB로 물리 VRAM을 초과**한다.
  이때 WSL의 CUDA 통합 메모리가 시스템 RAM으로 넘겨받아 죽지는 않으나
  PCIe를 경유하므로 **449초가 걸린다**. 곡 길이 1.87배에 시간 18배다.
  실행이 되는 것과 쓸 수 있는 것은 다르다. 전곡 추론은 배제한다.
- **청크 크기 실측(408초 곡, 모델 로딩 제외 순수 추론)**:

  | 청크 | 시간 | peak VRAM | 벡터 수 |
  |---|---|---|---|
  | 5초 | 3.78s | 462MB | 82 |
  | **10초** | **3.39s** | **557MB** | **41** |
  | 30초 | 3.99s | 935MB | 14 |
  | 60초 | 4.95s | 1500MB | 7 |
  | 120초 | 6.84s | 2629MB | 4 |

- **선택**: **청크 10초.**
- **근거**: 세 기준이 모두 같은 값을 가리키며 상충하지 않는다.
  (1) 속도 — 5초는 청크 82개의 커널 호출 오버헤드가, 30초 이상은 어텐션
  제곱이 붙는다. 10초가 그 사이의 최저점이다.
  (2) 메모리 — 557MB로 Demucs 549MB와 동시 적재해도 1.1GB다.
  (3) 시간 해상도 — 대중가요 한 섹션이 통상 15~30초다. 30초 청크는 벌스와
  코러스를 한 벡터에 뭉갠다. 10초면 섹션 내부 변화까지 잡힌다.
  5초는 속도가 밀리면서 벡터 수만 두 배가 되어 저장 비용만 는다.
- **결과**: R-1을 해소하고 다음을 P2 설계 전제로 둔다.
  Demucs는 제약 없이 사용한다. MERT는 **10초 청크 분할이 요구사항**이며
  선택 사항이 아니다. 청크별 `last_hidden_state`를 시간축 평균해
  청크당 768차원 벡터 하나를 얻는다.
  두 모델 합계 VRAM 약 1.1GB로 동일 프로세스에서 순차 실행이 가능하다.
- **배치 소요 추정**: 총 재생시간 64.1시간 / 1004곡 기준
  Demucs 약 3.4시간 + MERT 약 1시간으로 **5시간 이내**다.

  **2026-08-16 실측 정정.** 1004곡 전량 배치 결과 곡당 20~26초로 **5.5~7시간**이었다. 위 추정이 낮았던 이유는 Demucs 분리와 MERT 순수 추론만 합산했기 때문이다. 실제로는 곡당 디코딩 1회, MERT 5회(혼합 1 + 스템 4), npz 저장이 더 붙는다. MERT 5회만 약 17초다. 냉각이 한계에 걸려 스로틀링이 발생하면 곡당 50초까지 떨어졌다(GPU 83도, 81W/80W). 노트북에서 장시간 GPU 배치를 돌릴 때는 발열이 실질 제약이다.
  D-0015의 백그라운드 중단·재개 설계로 수용 가능한 범위다.

  **산출물 실적(2026-08-16).** 1004곡 전량 추출 완료. 곡별 npz 1004개, 누락 0, 총 348MB로 추정 350MB와 일치했다. 청크 합계 23,444(곡당 평균 23.4), 임베딩은 (청크, 768) float32, 키 5개(mixture/drums/bass/other/vocals). 배치가 절전·발열·외장하드 마운트 해제로 네 번 중단됐으나 인덱스 기반 재개가 매번 정상 작동해 손실은 진행 중이던 곡뿐이었다.
- **한계**: MERT-v1-330M은 미측정이다. 파라미터가 3.5배이므로 청크 10초에서도
  VRAM이 2GB를 넘길 수 있다. 95M으로 P2를 시작하고 표현력이 부족하면
  그때 330M을 실측한다. **실측 전까지 330M 사용을 가정하지 않는다.**
  청크 경계에서 문맥이 끊기는 문제도 남는다. 중첩 청크로 완화할 수 있으나
  연산량이 비례해 늘어난다. P2에서 벡터 품질을 보고 판단한다.
- **부수 확인**: 1660Ti는 Turing이지만 GTX 16xx 계열이라 텐서코어가 없다.
  fp16 커널은 정상 동작하나 가속 이득이 없다. 두 모델 모두 fp32로 측정했으며
  현 성능으로 충분하므로 half precision 최적화는 도입하지 않는다.
- **오디오 디코딩 미결**: 측정에는 soundfile을 썼다. torchaudio 최신 버전이
  자체 디코더를 제거하고 torchcodec에 위임하는데 그것이 ffmpeg 5 이상을
  요구해 환경(4.4.2)과 맞지 않는다. 프로덕션 디코더는 유닛 #4에서 정한다.
  2대 환경에 ffmpeg 4.4.2가 이미 통일돼 있으므로 서브프로세스 호출이 유력하다.

## D-0019. MusicBrainz 조회는 2단계 구조로 하고 78.5%를 상한으로 받아들인다
- **배경**: O-1·O-2 해소. 유닛 #3 착수 전 MB 조회 성공률 실측.
- **측정(2026-08-12)**: `tools/probe_musicbrainz.py`. 실측 1004곡 / 고유 후보 249개.

  점수 단독으로는 오답을 거를 수 없다. 격차 10점 미만은 AMBIGUOUS로 둔다.
- **아티스트 조회 결과**: RESOLVED **84.3%**(210) / AMBIGUOUS **13.7%**(34)
  / UNRESOLVED **2.0%**(5).
  한국 아티스트 커버리지는 우려보다 좋다. 미등재는 `디핵` `명카드라이브`
  `전혜성` `조이` `하이포` 5건뿐이다.

- **후보**: (a) 태그 원문으로 곡을 직접 조회
  / (b) 아티스트를 먼저 확정하고 그 정규명으로 곡을 조회
  / (c) AcoustID 지문으로 곡을 먼저 식별하고 아티스트를 역으로 얻음
- **선택**: **(b).**
- **근거**: (a)는 실측 39.0%로 성립하지 않는다.
  (c)는 지문 계산에 곡당 오디오 디코딩이 필요해 비용이 크고,
  P4 로컬 에이전트에서 사용자 라이브러리 전체에 적용하기 어렵다.
  MB 미등재 곡에는 어차피 듣지 않으므로 (b)의 실패분을 메우지도 못한다.
  (b)는 조회 횟수가 고유 아티스트 249회 + 곡 1004회로 끝나고,
  1단계 결과를 캐시하면 재스캔 시 2단계만 다시 돌면 된다.

  확보하고, 2단계에서 그 **정규명**으로 Recording을 조회한다.

- **남은 실패 216건의 유형**: 코드 결함이 아니라 데이터 자체의 한계다.
  (1) **MB 곡 단위 커버리지 부족** — 아티스트는 등재돼 있으나 개별 레코딩이
  없다. 폴킴 25곡 중 15건, Primary 6곡 중 5건, 태양 7곡 중 4건 실패.

  표기가 어긋나는 경우이며, 1단계가 RESOLVED여도 발생한다.
  (3) **버전·수록 맥락 표기** — `(Ballad Ver.)` `(Media Ver.)`
  `(Into the Unknown End Credit Version)` 등. 보존 정책의 대가다.
  (4) **1단계 UNRESOLVED의 전파** — `전혜성` `키네틱 플로우` `하이포` 등.
- **한계**: 78.5%를 상한으로 본다. 세 번째 반복에서 개선 폭이 0.6%p로
  떨어졌고 남은 실패가 코드로 줄지 않는 유형에 몰려 있다.
  더 짜내려면 (2)에 대한 재시도 경로(정규명 실패 시 태그 표기로 재조회)를

  **P2 착수 전에는 하지 않는다.**
- **D-0017과의 관계**: 정규화 상태 4종이 실측으로 뒷받침됐다.
  RESOLVED 78.5%는 MBID 확보분이고, UNRESOLVED 21.5%는 `normalized_key`

  13.7%가 동명이인으로 격차 미달이며, 곡에서도 `좋은 날`처럼 리마스터·
  라이브가 다수인 경우 격차가 나지 않는다. **보유 중인 `duration_ms`로

## D-0020. 재생시간으로 레코딩 버전을 확정한다 — O-5 해소, D-0019 정정
- **배경**: 유닛 #3 구현 후 프로덕션 코드로 1004곡 전수 재측정.

  곡 조회에는 적용하지 않은 비대칭이 있었다.

  **RESOLVED 402 / AMBIGUOUS 386**으로 갈렸다.
  즉 78.5%는 "MB가 무언가 찾았다"는 비율이지 "확정했다"는 비율이 아니다.
  D-0019의 수치를 폐기하고 본 결정의 실측으로 대체한다.
- **문제 — AMBIGUOUS 38.4%**: 대부분 유명한 곡이다.
  MB에 스튜디오·라이브·리마스터·컴필레이션이 모두 등재돼 전부 100점을 받는다.

  / (b) 재생시간으로 후보를 좁혀 확정

  (c)는 TALB가 100% 존재하나 태그 앨범명과 MB 릴리스명이 표기 체계가 달라
  아티스트에서 겪은 문제가 반복된다. 조회 조건이 늘수록 매칭이 좁아져

  (b)는 이미 보유한 값을 쓴다. `duration_ms`는 유닛 #1이 헤더에서 읽어

## D-0021. 오디오 디코딩은 ffmpeg 서브프로세스, 정규화는 MERT 특징 추출기에 맡긴다
- **배경**: 유닛 #4 착수 전 D-0018이 미결로 남긴 프로덕션 디코더 선정.
- **문제**: torchaudio 최신 버전이 자체 디코더를 제거하고 torchcodec에
  위임하는데 그것이 ffmpeg 5 이상을 요구한다. 2대 환경은 ffmpeg 4.4.2로
  통일돼 있고 유닛 #1이 이미 그 위에서 검증됐다.
- **후보**: (a) torchcodec 도입 + ffmpeg 5 이상으로 상향
  / (b) soundfile (libsndfile)
  / (c) ffmpeg 서브프로세스 호출
- **파형 품질 실측**: (b)와 (c)로 같은 mp3를 24kHz 모노로 만들어 대조했다.
  진폭 비율이 **1.4135(√2)** 로 일정하며, 스케일 보정 후 평균 절대오차가
  **0.00095**다. 부동소수점 수준이며 **디코딩·리샘플링 품질은 동일하다.**
  √2는 ffmpeg가 `-ac 1` 다운믹스에서 에너지를 보존하고(합÷√2),
  `numpy.mean`은 산술 평균(합÷2)을 쓰기 때문이다.
- **선택**: **(c).**
- **근거**: 품질이 같으므로 판단 기준은 환경 재현성이다.
  (a)는 검증된 ffmpeg 4.4.2 환경을 새 라이브러리 하나 때문에 흔든다.
  (b)는 시스템 libsndfile이 아니라 pip wheel에 번들된 버전에 의존한다.
  Ubuntu 22.04 기본 libsndfile 1.0.31은 mp3를 못 읽고 1.1 이상이 필요하다.
  (c)는 2대에 이미 통일된 바이너리를 쓰고 버전이 문서화돼 있다.
  유닛 #1이 fpcalc로 외부 바이너리 호출 패턴을 이미 쓰고 있다.
  프로세스 생성 비용은 곡당 10~50ms로 Demucs 12초 대비 0.5% 미만이다.
- **정규화 — MERT 특징 추출기에 맡긴다**: `Wav2Vec2FeatureExtractor`이며
  `do_normalize=True`, `return_attention_mask=True`, `sampling_rate=24000`이다.
  청크마다 제로 평균·단위 분산으로 맞추므로 디코더가 정규화하지 않는다.
- **R-1 측정의 결함 기록**: D-0018의 MERT 실측은 파형을 모델에 직접 넣어
  **특징 추출기를 건너뛰었다.** 성능 수치(VRAM 557MB, 청크 10초 3.39초)는
  연산량과 무관하므로 유효하나, 그때 뽑은 벡터는 정식 전처리를 거치지 않았다.
- **차이 실측**: 같은 10초 구간을 전처리 유무로 임베딩해 대조한 결과
  **코사인 유사도 0.917**이다. 같은 방향이나 무시할 수 없는 차이다.
- **근거**: 세 가지가 전처리 적용을 가리킨다.
  (1) 모델 제작자가 정한 전처리이며 건너뛸 이유가 없다.
  (2) 비용이 사실상 0이고, 되돌리는 비용은 5시간 배치 재실행이다.
  (3) **취향 벡터는 곡 간 비교가 목적이다.** 정규화하지 않으면 마스터링
  볼륨이 벡터에 섞인다. 그것은 음악적 특성이 아니라 제작 차이이며
  우리가 원하는 신호가 아니다. 0.917의 차이 상당 부분이 여기서 온다고 본다.
- **디코더 출력 규격**: **44100Hz / 스테레오 / float32 / 정규화 없음.**
  초안에서 24kHz 모노로 단정했으나 실측에서 틀렸음이 드러났다.
  Demucs는 44.1kHz 스테레오를 기대하고 MERT는 24kHz 모노를 기대한다.
  디코더는 원본에 가까운 전자를 내고 MERT용은 여기서 파생시킨다.
  디코딩을 두 번 하지 않는다. 218초 곡이 77MB이며 순차 처리이므로
  한 곡씩만 메모리에 올리면 문제가 없다.
- **클리핑 실측 — 정규화 불필요**: 디코딩 최대 절대값 1.12,
  Demucs 스템 최대 1.28로 둘 다 ±1을 넘는다.
  그러나 **스템을 파일로 저장하지 않는다.** 특징만 뽑고 버리므로
  float32로 다루는 한 클리핑이 발생하지 않는다. 저장이 필요해지면
  그때 정규화를 도입한다.
  다운믹스 계수를 명시한다. ffmpeg 기본값(√2)에 암묵적으로 기대면 버전이
  바뀔 때 파형이 달라진다. MERT 경로는 특징 추출기가 분산을 맞추므로
  계수가 무의미하지만 **Demucs는 정규화하지 않으므로 스템 분리에 영향이 있다.**
- **한계**: mp3 손실 압축의 인터샘플 피크로 디코딩 결과가 ±1을 넘는다.
  실측 최대 절대값이 1.06(산술 평균) · 1.50(ffmpeg 기본)이었다.
  위 클리핑 실측으로 해소했다.
- **의존성 계약 정정**: P0에서 `도메인은 외부를 모른다` 계약이 numpy를
  명시적으로 금지했다. 이를 해제한다.
  계약의 목적은 도메인이 **교체 가능한 인프라 선택**에 묶이지 않게 하는 것이다.
  numpy는 그런 선택이 아니다. 파형은 본질적으로 수치 배열이고 이를 표현할
  파이썬 표준 타입이 달리 없다. `list[float]`은 222초 곡 533만 샘플에서
  메모리가 20배로 늘어 1004곡 배치에서 성립하지 않는다.
  즉 인프라가 새는 것이 아니라 **도메인 언어에 수치 배열이 필요한 것**이다.
  **torch·scipy는 계속 막는다.** 그것들은 교체 가능한 선택이며, 구현체만 알면 된다.
  numpy를 기본 의존성으로 올린다. 도메인 포트가 쓰므로 선택적일 수 없다.

## D-0022. 배치 중복 실행은 flock으로 막고 인덱스는 키 정렬로 유지한다
- **배경**: O-7. 유닛 #4 특징 배치가 여러 번 중단·재시작되는 과정에서 두 프로세스가
  겹쳐 돌아 1004곡 인덱스에 1574줄이 쌓였다.
- **원인 정정**: 인덱스 append가 아니다. O_APPEND에 200바이트 줄이면 리눅스에서
  이미 원자적이며 실제로 데이터도 깨지지 않았다. 원인은 배치 프로세스가 둘 돈 것이다.
  방어는 쓰기 수준이 아니라 실행 수준에 둔다.
- **후보**: (a) PID 파일 / (b) flock / (c) 방어하지 않고 정리 도구만 제공
- **선택**: **(b) flock. 정리 도구(`ingest compact`)를 함께 둔다.**
- **근거**: 이 배치는 절전·발열·외장 마운트 해제로 네 번 죽었고 그때마다 정리
  코드가 돌지 않았다. PID 파일이면 죽은 잠금이 남아 다음 실행을 막는다.
  flock은 커널이 fd 수명에 묶어 관리하므로 프로세스가 어떻게 죽든 자동으로 풀린다.
  중단·재개가 전제인 파이프라인(D-0015)에서는 이 성질이 결정적이다.
- **인덱스 정렬**: compact는 source_key 순으로 다시 쓴다. 기존 인덱스 순서는
  배치가 몇 번 중단됐고 어디서 재개됐는지에 따라 달라져 **D-0009가 요구하는
  기기 간 동일 산출물을 순서가 이미 깨고 있었다.** 정렬이 이 순서 의존을 없앤다.
- **중복 해소 규칙**: 같은 키는 마지막 기록을 남긴다. npz가 같은 이름으로
  덮어써졌으므로 파일과 짝이 맞는 것은 나중 기록이다.
- **고아 기록**: npz가 없는 인덱스 줄은 기본적으로 버린다. 남으면
  `completed_keys()`가 없는 파일을 완료로 보고해 재개가 그 곡을 영영 건너뛴다.
  `--keep-missing`으로 보존할 수 있으나, 마운트가 끊긴 상태로 compact를 돌리면
  전량이 고아로 판정되므로 실행 전 `vectors/` 접근을 확인한다.
- **실측(2026-08-16)**: 정리 대상 없음. npz 1004개 347MB, 인덱스 1004줄,
  중복 0 · 고아 0 · 정렬 이미 일치. **데이터 손상은 발생하지 않았다.**
  O-7은 손상 사건이 아니라 단일 실행 전제가 깨진 사건이며, 남은 과제는 재발 방지였다.
- **한계**: flock은 POSIX 전용이다. WSL·리눅스에서만 동작하며 네이티브 윈도우에는
  `fcntl`이 없다. P4 로컬 에이전트가 윈도우를 대상으로 하면 재검토가 필요하다.

## D-0023. 검색 평가 하네스를 태그 동치류로 구성한다 (M0/M1/M2)

- **배경**: P1 유닛 #1~#4로 음원에서 임베딩까지는 나왔으나 **그 벡터로 무엇이 되는지
  보여주는 산출물도, 판단할 지표도 없다.** 지표가 없으면 95M/330M, 혼합/스템,
  청크 크기, 풀링 방식, 이후 취향 벡터 구성까지 전부 반증 불가능한 선택이 된다.
  D-0018이 "실측 전까지 330M 사용 가정 금지"로 유보한 그 실측을 수행할 수단이다.
- **연산 규모**: 1004x768 행렬 5개, 전체 코사인 1004x1004. CPU에서 수 초.
  **GPU 불필요** — 광인사에서 돈다.

### 정답 라벨을 외부에서 가져오지 않는다

- **후보**: (a) MusicBrainz 정규 신원을 라벨로 / (b) 태그 문자열 동치류 / (c) 수동 라벨링
- **선택**: **(b) 태그 동치류.**
- **근거**: 검색 평가에 필요한 것은 정규 신원이 아니라 **동치류**다. 개인 라이브러리는
  리핑 출처가 단일해 태그 문자열이 내부적으로 일관되며, `아이유`가 `IU`로 정규화되는지는
  MB 조회의 문제지 "이 두 곡이 같은 아티스트인가" 판정과 무관하다.
  **따라서 O-4(RESOLVED 오답)는 이 평가를 오염시키지 않는다.**
  TPE1·TALB 각 100% 커버(D-0010 실측), 외부 조회 0회, 재현 가능.
- **정규화 범위**: NFC + 양끝 공백 제거 + 케이스 폴딩까지만. 그 이상 손대지 않는다.
  피처링 혼재 원문(`10CM, BIG Naughty (서동현)`)은 단독 표기와 다른 키가 되는데,
  이는 라벨을 **더 엄격하게** 만들 뿐이라 점수를 부풀리지 않는다. 느슨하게 묶는
  휴리스틱을 넣으면 그 휴리스틱 자체가 검증 대상이 되어 평가의 신뢰를 깎는다.

### 지표 3개

| | 정의 | 라벨 | 성격 |
|---|---|---|---|
| M0 자기일관성 | 곡의 청크를 홀/짝으로 나눠 각각 풀링. 자기 짝을 top-1으로 찾는 비율 | 불필요 | **게이트 0.95** |
| M1 앨범 검색 | top-k 중 같은 TALB 비율, MAP@k | TALB | 주 지표 |
| M2 아티스트 검색 | top-k 중 같은 TPE1 비율, MAP@k | TPE1 | 보조 |

- **M0 미달이면 M1/M2를 계산하지 않는다.** 임베딩이 곡 정체성조차 담지 못한 것이고
  그 아래에서 나온 수치는 노이즈다. `--force`로 조사할 수 있으나 그 수치는 인용 금지.
- **홀/짝 분할을 쓴다. 앞/뒤로 자르지 않는다.** 곡의 앞부분과 뒷부분은 구성이 다르므로
  (인트로 대 아웃트로) 그 대조는 임베딩 품질이 아니라 곡 구조를 잰다. 홀짝은 양쪽이
  곡 전체에 고르게 퍼져 "같은 곡"이라는 사실 외의 차이를 최소화한다.
- **M2는 같은 앨범 곡을 후보에서 통째로 제외한다.** 관련도에서만 빼는 것이 아니라
  후보 집합에서 뺀다. 안 빼면 동일 마스터링·믹스가 만드는 앨범 효과를 아티스트
  유사도로 착각한다. MIR의 오래된 함정이다.
- **정답이 없는 쿼리는 평균에서 제외한다.** 단일 곡 앨범·단일 곡 아티스트가 여기 걸린다.
  남기면 AP가 정의상 0이 되어 **임베딩이 아니라 코퍼스 구성을 재게 된다.**

### MAP@k 정규화 — min(R, k)

- **후보**: (a) k로 나눔 / (b) min(R, k)로 나눔 (R = 유효 후보 중 정답 수)
- **선택**: **(b).**
- **근거**: (a)는 R < k일 때 완벽한 순위도 1.0에 못 미친다. 2곡짜리 앨범은 최대 0.2점이
  되어 **지표가 앨범 크기 분포를 재게 된다.** 앨범당 곡 수가 제각각인 코퍼스에서
  이 편향은 임베딩 차이보다 클 수 있다.
- **한계**: 정의를 바꾸면 수치가 통째로 달라진다. 외부 논문 수치와 비교할 때
  같은 정규화인지 반드시 확인해야 한다.

### 베이스라인 2종

- **무작위**: 시드 고정 난수를 유사도로 써서 **동일한 순위 코드 경로**를 탄다.
  별도 계산식을 쓰지 않으므로 마스크 구성 오류가 베이스라인에도 똑같이 반영된다.
  해석적 기대값(쿼리별 정답 비율의 평균)을 함께 산출해 서로 검산한다.
- **MFCC**: 별도 특징 추출기를 두되 **산출물 규격을 MERT와 동일하게** 한다.
  `eval retrieval --features`만 바꿔 같은 하네스를 돌린다. 베이스라인 전용 코드 경로를
  만들지 않는다.
- **근거**: `MAP 0.41`은 의미가 없고 `무작위 0.02 대비 20배`가 의미다. 무작위 대비
  20배여도 1990년대 MFCC와 같다면 GPU 6시간의 근거가 없다. 리포트 구조가 측정값만
  단독으로 남기지 못하게 강제한다.

### MFCC 구현 선택

- **후보**: (a) librosa / (b) torchaudio / (c) numpy 직접 구현
- **선택**: **(c) numpy.**
- **근거**: 베이스라인 하나 때문에 라이브러리를 들이면 그 버전이 재현성 논의에 끼어들고,
  광인사(GPU 엑스트라 미설치)에서 추가 설치가 필요해진다. librosa와 계수가 소수점
  아래에서 다를 수 있으나 **비교 대상은 librosa가 아니라 MERT다.**
- **44.1kHz 그대로 쓴다.** MERT의 24kHz 리샘플은 모델 요구사항이며 MFCC에는 불필요하다.
  scipy를 끌어들이지 않게 되는 부수 효과가 있다.
- **c0(0차 계수)를 버린다.** c0는 프레임 전체 에너지, 즉 마스터링 볼륨이다.
  D-0021이 정규화를 도입한 이유와 같은 이유로 취향 비교에 섞이면 안 된다.
  실측: 게인 10배 차이에서 c1~c20 상대 오차 1% 미만(로그 바닥값 때문에 완전 불변은 아님).
- **청크 단위로 접는다.** 프레임을 남기면 218초 곡이 1.4MB, 코퍼스 전체 1.4GB로
  MERT npz 347MB보다 커진다. MERT와 같은 10초 격자를 쓰므로 청크 수가 일치하고
  M0 비교에서 청크 분할 차이가 임베딩 차이로 보이지 않는다.

### 구조

- 지표는 도메인(`domain/services/retrieval_metrics.py`), 뷰 구성도 도메인

| 7 | MERT 혼합 · mean-std | 1536 | 0.9970 | 0.0252 (7.4배) | 0.0823 (4.7배) |
| 8 | MERT 혼합 · chunk-L2 | 768 | 0.9980 | 0.0249 (7.3배) | 0.0832 (4.8배) |
| 9 | **MFCC 베이스라인** | **40** | 0.9572 | **0.0303 (8.9배)** | **0.1224 (7.0배)** |

- **코퍼스 구조 도출**: M1 쿼리 409, M2 쿼리 841. 즉 **1004곡 중 595곡이 단일 곡 앨범**이며,
  무작위 M2 0.0175에서 아티스트당 평균 약 17곡이 나온다. M1은 코퍼스의 40%만 덮으므로
  인수인계가 "주 지표"로 지정한 것과 달리 **M2가 검정력이 높다.**

### 결론 4건

1. **스템을 MERT에 넣는 것은 검색에 기여하지 않는다.** 개별로도 전부 혼합보다 열등하고
   (조건 4·5·6), concat도 혼합 단독보다 나빴다(조건 2, 차원 5배에 리프트 하락).
   곡당 GPU 20초의 Demucs는 **이 목적에는** 값을 하지 못했다.
2. **스템 M0 순서가 분리 품질 상한을 드러낸다.** vocals 0.876 < bass 0.957 < drums 0.987
   < other 0.990. 무음·저에너지 구간이 많은 스템일수록 홀짝 청크가 서로를 못 알아본다.
   C-5(손실 압축 코퍼스)의 원리적 상한과 방향이 일치한다.
3. **풀링·정규화에 남은 여지가 없다.** mean-std는 차원 2배에 동일, chunk-L2는 노이즈 범위
   변동(M2 +0.1배, M1 −0.1배). 둘 다 M0를 미세하게 떨어뜨렸다. **기본값을 유지한다.**
4. **MFCC 40차원이 MERT 768차원을 이겼다.** M2에서 P@10 0.0829 → 0.1224로 **47% 우위**,
   M1도 앞선다. MERT가 이긴 것은 M0(게이트) 하나뿐이며 그것은 검색 성능이 아니다.
   **추출 비용은 GPU 6~7시간 대 CPU 33분이다.**

### 선택

- **취향 벡터 기본 뷰는 MERT 혼합 · mean · L2 없음으로 유지한다.** 조건 1이 MERT 계열
  최고이며, 3·7·8을 실측으로 배제하고 고른 값이다.
- **스템 재추출을 위한 배치를 돌리지 않는다.** 검색 목적의 근거가 소멸했다.
- **D-0018의 330M 유보를 해제하지 않고 오히려 강화한다.** 95M이 MFCC에 지는 상황에서
  파라미터를 4배로 키우는 것은 방향이 맞는지부터 미확정이다. **O-8 해소 전까지 착수 금지.**

### 미해결 — O-8로 등재

MFCC 우위의 원인이 셋 중 어느 것인지 현재 데이터로 구분되지 않는다.

| 가설 | 내용 | 반증 실험 |
|---|---|---|
| (a) 모델 부적합 | 음악 이해 사전학습이 아티스트 동일성으로 전이되지 않는다 | 다른 음악 임베딩 모델과 대조 |
| (b) 풀링 손실 | MERT는 시간축 표현이고 23청크 평균이 정보를 뭉갠다 | 청크 크기 변경, 어텐션/최대 풀링, 중간 레이어 사용 |
| (c) 지표 오염 | MFCC가 음색·EQ·마스터링에 직접 반응하며, 같은 아티스트 = 같은 엔지니어·스튜디오다. 즉 **음악적 유사성이 아니라 제작 조건을 재서 이긴다** | MERT+MFCC 결합이 각각보다 나은지, 앨범 내 제외 조건을 더 강화했을 때 우위가 유지되는지 |

**(c)가 참이면 MFCC의 승리는 취향 모델링에 쓸 수 없다.** 제작 조건은 취향의 대상이 아니다.
결합 실험(MERT+MFCC concat)은 추가 추출 없이 수 초에 가능하므로 O-8 착수는 이것부터 한다.

### 한계

- 이 지표들은 **취향의 대리 지표가 아니다** (D-0023 한계 재확인). 임베딩이 곡 정체성과
  제작 맥락을 담는지까지만 말한다. 취향 축 검증에는 라벨이 필요하며 현재 0건이다
  (C-7: 코퍼스 전량 양성 사례).
- 결론 1은 **"스템을 MERT에 넣는 것"을 부정하며 "스템을 파일로 남기는 것"은 부정하지 않는다.**
  편곡축(스펙트럴 롤오프·스테레오 폭)과 가창축(음역대·비브라토)은 MERT 임베딩에서
  나오지 않으며 스템 오디오를 요구한다. 스템 영속화 판단은 이 결과와 독립이다.
- MFCC 구현은 numpy 직접 구현이며 librosa와 계수가 소수점 아래에서 다를 수 있다(D-0023).
  우열 판정이 47% 차이이므로 구현 차이로 뒤집히는 규모가 아니다.

## D-0025. MERT와 MFCC는 상보적이다 — O-8 가설 (c) 약화, (a)·(b)로 좁힌다

- **배경**: D-0024에서 MFCC 40차원이 MERT-95M 768차원을 이겼고, 원인이 셋으로 갈렸다(O-8).
  가장 값싼 반증 실험인 결합 뷰를 먼저 수행했다. 추가 추출 없이 기존 npz 두 벌만 읽는다.

### 블록별 단위 정규화는 옵션이 아니다

- **배경**: 서로 다른 추출기의 벡터를 이어붙이면 노름 규모가 다르다.
- **후보**: (a) 그냥 concat / (b) 블록별 단위 정규화 후 concat / (c) 전체 표준화(z-score)
- **선택**: **(b).**
- **근거**: 코사인 유사도는 내적이므로 (a)는 노름이 큰 블록이 결과를 지배한다.
  MERT 768과 MFCC 40을 그냥 붙이면 작은 블록이 사실상 무시되고, 그 결과는 "결합이
  효과 없다"로 **잘못 관측된다.** (b)는 전체 코사인이 **블록 코사인의 산술 평균**이
  되어 기여가 정확히 균등해진다. (c)는 코퍼스 전체 통계에 의존해 곡이 추가될 때마다
  값이 변한다.
- **결과**: `build_view(block_l2=True)`, CLI `--block-l2`. 저장소를 둘 이상 지정할 때는
  키를 `이름:mixture`로 네임스페이스한다. **한쪽에만 있는 곡은 제외한다.** 남기면
  저장소마다 다른 곡 집합을 비교하게 된다.

### 실측 (2026-08-16, 1004곡, 제외 0)

| 뷰 | 차원 | M0 | M1 P@10 | M1 MAP@10 | M2 P@10 | M2 MAP@10 |
|---|---|---|---|---|---|---|
| MERT 혼합 | 768 | 0.9990 | 0.0252 | 0.0846 | 0.0829 | 0.0560 |
| MFCC | 40 | 0.9572 | 0.0303 | 0.0728 | **0.1224** | 0.0768 |
| **결합 (block-L2)** | 808 | 0.9990 | **0.0355** | **0.1022** | 0.1180 | **0.0821** |

- **M1은 어느 단독보다 우월하다.** P@10 +17%, MAP@10 +40%(MFCC 대비).
- **M2는 무승부.** P@10 −3.6%, MAP@10 +7%. 정답을 조금 덜 찾지만 찾은 것은 더 위에 놓는다.
  노이즈 범위로 본다.

### 결론 — 두 표현은 상보적이다

**MERT에는 MFCC가 담지 못하는 정보가 있다.** M1 MAP 40% 향상은 균등 가중 결합에서
나온 것이며, MERT 블록이 무의미했다면 결합은 MFCC 단독과 같아야 했다.
D-0024만 보고 "MERT를 버린다"로 갔다면 틀린 판단이었다.

다만 그 정보는 **앨범 수준에서만 작동한다.** 아티스트 수준에서는 보탬이 없다.

### 가설 (c)가 약해졌다

MFCC의 우위 폭을 과제별로 보면 방향이 (c)와 반대다.

| 과제 | MFCC 리프트 | MERT 리프트 | 비 |
|---|---|---|---|
| M1 (앨범, 제작 조건 공유) | 8.9배 | 7.4배 | **1.20** |
| M2 (아티스트, 같은 앨범 제외) | 7.0배 | 4.7배 | **1.49** |

(c)는 "MFCC가 마스터링·엔지니어 같은 제작 조건을 재서 이긴다"였다. 참이라면 제작 조건이
가장 강하게 공유되는 M1에서 격차가 가장 커야 한다. **실측은 반대로 M1에서 가장 좁다.**

또한 M1/M2 리프트 비는 MERT가 1.57, MFCC가 1.27이다. **앨범 효과에 더 기대는 쪽은
오히려 MERT다.**

- **선택**: **(c)를 주된 설명에서 제외한다.** 완전 배제는 아니며, 앨범 내 마스터링 동일성
  자체를 직접 잰 것은 아니다.
- **O-8을 (a) 모델 부적합과 (b) 표현 추출 방식으로 좁힌다.**

### 다음 반증 — (b)의 최우선 후보는 레이어 선택

현재 구현은 `last_hidden_state`를 쓴다. MERT를 포함한 자기지도 음성·음악 모델은
**마지막 레이어가 다운스트림 과제에서 가장 나쁜 경우가 흔하다.** 사전학습 목표
(마스킹 예측)에 특화되어 있기 때문이며, 중간 레이어가 태깅·유사도에서 더 나은 것은
알려진 패턴이다. (b)를 칠 수 있는 가장 값싼 수단이다.

- **비용**: D-0024로 스템이 기여하지 않음이 확정됐으므로 **혼합만 뽑는다. Demucs를
  돌리지 않으므로 6~7시간이 아니라 1시간 안팎이다.**
- **레이어별로 따로 추출하지 않는다.** 한 번의 forward에서 전 레이어를 받아 선택한
  것만 같은 npz에 담는다. 13회 반복하면 13시간이다.

### 한계

- 결합은 **균등 가중**이다. 가중치를 조정하면 M2도 개선될 수 있으나, 가중치를 실측으로
  고르려면 홀드아웃이 필요하고 현재 하네스에 분할이 없다. 가중 탐색은 그 전까지 하지 않는다.
- M1 향상이 크고 M2가 제자리인 것을 "MERT가 앨범 단위 제작 맥락을 담는다"로 해석할
  수도 있다. 그 해석은 (c)를 MERT 쪽에 적용한 것이며 현재 데이터로 구분되지 않는다.

## D-0026. MERT 마지막 레이어가 최악이었다 — layer00으로 교체, M2 2.8배 개선

- **배경**: D-0024에서 MFCC가 MERT-95M을 이겼고, D-0025에서 원인을 (a) 모델 부적합과
  (b) 표현 추출 방식으로 좁혔다. (b)의 최우선 후보는 레이어 선택이었다.
  기존 구현은 `last_hidden_state`만 썼다.
- **실행**: 혼합만 재추출(스템 분리 없음, GPU 곡당 4.0초, 1004곡 67분, 실패 0).
  한 번의 추론에서 은닉 상태 0·3·6·9와 마지막 레이어를 함께 저장했다.

### 실측 (2026-08-16, 1004곡, 제외 0)

무작위: M1 P@10 0.0034, M2 P@10 0.0175.

| 뷰 | M0 | M1 P@10 | M1 MAP@10 | M2 P@10 | M2 MAP@10 | M2 리프트 |
|---|---|---|---|---|---|---|
| **layer00** | 1.0000 | **0.0638** | 0.1715 | **0.2327** | **0.1899** | **13.3배** |
| layer06 | 1.0000 | 0.0528 | 0.1476 | 0.1902 | 0.1516 | 10.9배 |
| layer03 | 1.0000 | 0.0389 | 0.1144 | 0.1571 | 0.1155 | 9.0배 |
| layer09 | 1.0000 | 0.0399 | 0.1184 | 0.1488 | 0.1129 | 8.5배 |
| mixture (마지막) | 0.9990 | 0.0252 | 0.0846 | 0.0829 | 0.0560 | 4.7배 |
| *(참고) MFCC* | 0.9572 | 0.0303 | 0.0728 | 0.1224 | 0.0768 | 7.0배 |
| layer00+layer06 (block-L2) | 1.0000 | 0.0628 | **0.1750** | 0.2279 | 0.1888 | 13.0배 |
| layer00+MFCC (block-L2) | 0.9970 | 0.0435 | 0.1209 | 0.1830 | 0.1370 | 10.5배 |

### 결론

1. **마지막 레이어가 측정한 모든 레이어 중 최악이다.** layer00 대비 M2 P@10이 2.8배 차이다.
   D-0024의 "MFCC가 MERT를 이긴다"는 관측은 **모델의 문제가 아니라 레이어 선택의 문제였다.**
   D-0025가 (b)로 좁힌 판단이 옳았고, **O-8은 (b)로 해소한다.**
2. **layer00이 MFCC를 90% 앞선다** (M2 P@10 0.2327 대 0.1224). 학습도, 더 큰 모델도,
   데이터 증강도 없이 **레이어 인덱스 하나**로 얻었다.
3. **결합은 더 이상 이득이 없다.** layer00+MFCC는 21% 손해다. D-0025에서 MFCC가 보완했던
   것은 그때 MERT 쪽이 마지막 레이어라 약했기 때문이며, 상대가 강해지자 보완 관계가
   사라졌다. layer00+layer06은 차원 2배에 사실상 동률이다.
4. **재현성 검산 통과.** 별도 배치·별도 저장소·다른 코드 경로로 뽑은 `mixture`가
   기존 산출물과 소수점 넷째 자리까지 일치했다(0.0252 / 0.0846 / 0.0829 / 0.0560).
   D-0009 계층 2(수치 동등)가 실제로 성립한다는 증거다.

### 선택

- **기본 뷰를 `mert-layers` 저장소의 `layer00`으로 바꾼다.** 이후 취향 벡터·검색 CLI는
  이 뷰를 전제로 한다.
- **`last_hidden_state` 단독 추출은 더 이상 쓰지 않는다.** 기존 `ingest features` 경로는
  남기되(스템 산출이 필요할 때가 온다) 검색·취향 용도로는 `eval layers` 산출물을 쓴다.
- **MERT 330M 확대는 우선순위를 더 내린다.** 95M조차 제대로 쓰지 않고 있었다.
  D-0018의 유보를 유지한다.

### 해석 — 저수준 표현이 이긴다

layer00은 **트랜스포머 블록 이전**, 즉 합성곱 프런트엔드 출력이다. 성격상 학습된
필터뱅크이며 MFCC와 같은 계열의 저수준 음향 표현이다.

즉 이 과제에서 이기는 것은 저수준 음색 표현이고, **트랜스포머 12블록이 쌓아올린 음악적
추상화는 오히려 방해가 된다.** 이것이 (a)를 완전히 지우지는 못한다 — "MERT의 사전학습
목표가 이 과제에 맞지 않는다"는 여전히 부분적으로 참일 수 있다. 확인된 것은
**MERT의 합성곱 프런트엔드가 MFCC보다 확실히 낫다**는 것까지다.

### 한계 — O-9로 등재

- **레이어 1·2를 보지 않았다.** 곡선이 비단조다(0 → 3 하락 → 6 반등 → 9 하락 → 12 붕괴).
  layer00이 국소 최적일 뿐 전역 최적이 아닐 수 있다. 낮은 레이어만 추가 추출하면
  70분이므로 비용은 낮다.
- **앨범·아티스트 검색은 취향의 대리 지표가 아니다** (D-0023 한계). "저수준 음향 표현이
  이긴다"가 취향 모델링에도 적용될지는 별개 문제이며, 취향은 오히려 추상화를 요구할
  수 있다. 취향 라벨이 0건인 현재로서는 판별 수단이 없다(C-7).

## D-0027. 레이어 곡선은 layer00에서 최대다 — O-9 해소, 임베딩 축 종료

- **배경**: D-0026에서 layer00이 최선이었으나 곡선이 비단조여서(0 → 3 하락 → 6 반등 →
  9 하락 → 12 붕괴) layer00이 전역 최적이라는 근거가 없었다(O-9).
  0 근처를 촘촘히 보면 닫힌다.
- **실행**: 레이어 0·1·2를 별도 저장소 `mert-layers-low`에 추출(1004곡 67분, 실패 0).
  **기존 `mert-layers`를 건드리지 않았다.** 같은 layer00을 양쪽에서 뽑아 검산에 쓰기 위함이다.

### 실측 — 레이어 곡선 7점

| 레이어 | M1 P@10 | M1 MAP@10 | M2 P@10 | M2 MAP@10 | M2 리프트 |
|---|---|---|---|---|---|
| **00** | **0.0638** | **0.1715** | **0.2327** | **0.1899** | **13.3배** |
| 01 | 0.0575 | 0.1618 | 0.2145 | 0.1737 | 12.3배 |
| 02 | 0.0447 | 0.1325 | 0.1776 | 0.1316 | 10.2배 |
| 03 | 0.0389 | 0.1144 | 0.1571 | 0.1155 | 9.0배 |
| 06 | 0.0528 | 0.1476 | 0.1902 | 0.1516 | 10.9배 |
| 09 | 0.0399 | 0.1184 | 0.1488 | 0.1129 | 8.5배 |
| 12 (마지막) | 0.0252 | 0.0846 | 0.0829 | 0.0560 | 4.7배 |

- **0에서 3까지 단조 감소한다.** 비단조 구간은 6의 반등 하나뿐이며 그 반등도 layer00에
  미치지 못한다. **0은 경계이자 최댓값이므로 더 볼 곳이 없다. O-9를 해소한다.**
- **재현성 검산 2회차 통과.** 별도 배치·별도 저장소·다른 세션에서 뽑은 layer00이
  네 지표 전부 완전히 일치했다(0.0638 / 0.1715 / 0.2327 / 0.1899).
  D-0026의 1회차(`mixture`)에 이어 D-0009 계층 2가 재확인됐다.

### 결론 — 트랜스포머 블록을 통과할수록 나빠진다

7개 점이 같은 방향을 가리킨다. 이 과제에 유용한 것은 **합성곱 프런트엔드의 저수준
음향 표현**이고, 트랜스포머가 쌓아올린 음악적 추상화는 기여하지 않는다.

### 선택

- **정본 저장소는 `var/ingest/mert-layers`, 정본 뷰는 `layer00`이다.**
  `mert-layers-low`는 O-9 검증용이며 정본이 아니다. 지우지 않고 남긴다 —
  재현성 검산 2회차의 증거이고, 낮은 레이어 재실험 시 재추출을 아낀다.
- **임베딩 축 탐색을 여기서 종료한다.** 레이어 축은 소진했다.

### 최적화를 지금 하지 않는 이유

남은 개선 수단은 MERT 330M(D-0018 유보) 또는 다른 모델이다. **지금 착수하지 않는다.**

- **판정 기준이 목표와 다르다.** M1·M2는 아티스트·앨범 검색이며 취향의 대리 지표가
  아니다(D-0023 한계). M2를 0.2327에서 0.28로 올려도 취향 모델은 나아지지 않는다.
- **최적 방향이 뒤집힐 수 있다.** 아티스트 동일성은 음색이 결정하므로 저수준 표현이
  유리하다. 취향은 오히려 추상화를 요구할 수 있으며, 그렇다면 **layer00은 취향 축에서
  최적이 아니다.** 지금의 최적화는 틀린 축을 올리는 작업이 된다.
- **같은 일을 두 번 하게 된다.** 취향 지표(가칭 M3)가 생긴 뒤 레이어·모델을 다시 재야 한다.

**따라서 다음 병목은 임베딩 품질이 아니라 취향 라벨이다.** 코퍼스는 전량 양성 사례이며
(C-7) 음성 사례가 0건이다. 표현 학습은 비지도로 끝났지만 **취향 판정은 원리적으로
사용자 응답을 요구한다.** 같은 벡터 공간에서 어느 방향이 선호인지는 음원 안에 없다.
D-0012의 쌍대비교가 그 라벨을 합성하는 장치이며, 다음 작업은 그 설계다.

### 한계

- 라이브러리 소장 자체를 약한 양성 신호로 쓸 수 있으나, 1004곡 평균은 "들어본 것의
  중심"이지 "좋아하는 것"이 아니다. 장르 분포가 치우치면 소수 애착 곡이 묻힌다.
  **안 들어본 영역이 비선호인지 미탐색인지도 판별되지 않는다.**
- 레이어 4·5·7·8·10·11은 여전히 미측정이다. 0~3 구간이 단조 감소이고 6이 0을 못 넘었으므로
  중간 구간에 layer00을 넘는 지점이 있을 가능성은 낮다고 판단했다. **실측은 아니다.**

## D-0028. 취향 라벨 수집은 무작위 평가 집합을 먼저 확보한다

- **배경**: O-10. 코퍼스가 전량 양성 사례이고(C-7) 취향 라벨이 0건이다. D-0012가
  적응적 쌍대비교를 웜스타트 수단으로 정했고 **선행 조건인 임베딩이 D-0027로 확보**됐다.
- **범위**: 이번 결정은 **라벨 수집 방식**만 다룬다. 선호 모델 적합과 지표(M3)는
  라벨이 존재해야 설계할 수 있으므로 다음 결정으로 미룬다.

### 무작위 쌍을 먼저 모은다

- **후보**: (a) 처음부터 적응적 선택 / (b) 무작위 쌍으로 고정 평가 집합을 만든 뒤 적응적 전환
- **선택**: **(b).**
- **근거**: D-0012의 적응적 선택은 모델의 예측 불확실성이 높은 쌍을 고른다. 같은 방식으로
  평가 쌍까지 뽑으면 **시험 분포가 모델에 의존한다.** 자기가 헷갈리는 문제만 골라 풀고
  채점하는 것과 같아서, 모델이 좋아졌는지 문제가 쉬워졌는지 구분되지 않는다.
  평가 집합은 모델이 없을 때 만들어야 하며, 그 시점은 지금뿐이다.
- **한계**: 무작위 쌍은 대부분 서로 매우 다른 곡이라 문항당 정보량이 적다.
  그것이 결함이 아니라 **평가 집합이 가져야 할 자연 분포**다. 학습 효율은 적응적 단계에서 얻는다.

### 저장 규약

- **정규 순서(`left <= right`)로 저장하고 제시 순서는 섞는다.** 사람은 먼저 제시된 쪽을
  고르는 경향이 있다. 좌우를 고정하면 그 위치 편향이 라벨에 그대로 실린다.
  저장을 정규화해야 `(A,B)`와 `(B,A)`가 같은 문항으로 취급되어 재출제도 막힌다.
- **응답마다 즉시 쓰고 flush한다.** 세션 끝에 일괄 기록하면 중간에 끊길 때 사람이 들인
  시간이 통째로 날아간다. **응답은 산출물 중 유일하게 재생성 불가능한 자산이다.**
  임베딩은 GPU를 다시 돌리면 되지만 응답은 되돌릴 방법이 없다.
- **건너뛴 문항도 기록한다.** 어떤 쌍을 판단하지 못했는지가 정보이고, 지우면 그 쌍이
  다시 출제된다.
- **임베딩이 있는 곡만 출제한다.** 응답을 받아도 모델에 쓸 수 없는 곡을 물으면
  사람의 시간을 버린다.
- `mode` 필드로 `random`과 `adaptive`를 구분한다. **섞이면 평가 집합이 오염된다.**

### 결과

- `hathor taste compare --count N` (문항 출제·기록), `hathor taste status` (현황).
- 저장: `var/ingest/taste/comparisons.jsonl` (추가 전용).
- 곡 표시는 `아티스트 — 제목`이다. 본인 라이브러리이므로 재생 없이 답할 수 있고,
  재생을 강제하면 수집 속도가 수십 배 느려진다.

### 미결 — 다음 결정으로

- **필요한 응답 수를 모른다.** 평가 집합이 작으면 표준오차가 커서 모델 개선을 검출하지
  못한다. 50건이면 오차가 ±7%p 수준이라 유의미한 비교가 어렵다. **(실측 필요)** —
  실제 응답의 일관성을 본 뒤 정한다.
- **모델 용량과 차원 축소.** 768차원 위에서 수십 건으로 적합하면 과적합이 확실하다.
  주성분 축소나 강한 정칙화가 필요하며, **여기서의 PCA는 성능 향상 수단이 아니라
  라벨 수에 모수를 맞추는 수단이다.** 어느 쪽이든 M3로 판정한다.
- **layer00이 취향 축에서도 최적인지 미확정.** D-0027이 남긴 한계다. 아티스트 동일성은
  음색이 결정하므로 저수준 표현이 유리했지만, 취향은 추상화를 요구할 수 있다.
  M3가 서면 레이어를 다시 잰다.
