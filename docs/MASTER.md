## 취향 잠재 표현 기반 종단간 AI 음악 창작 시스템

사용자의 음악 취향을 기기 안에서 벡터로 만들고,
그 벡터를 조건으로 작사·작곡·편곡·가창까지 한 곡을 완성한다

2026. 08. 10. 초판 · 2026. 09. 22. 개정 (D-0221)

1인 풀스택 · **남들이 쓰는 제품을 목표로 한다** (D-0215) | 저장소: github.com/CleverAIFox/hathor

---

**※ 데이터 경계 전제**: 사용자의 음원 파일과 원본 오디오는 **사용자 기기를 떠나지 않는다.** 분석은 로컬 에이전트가 수행하고 서버로는 취향 벡터와 특징 임베딩만
전송한다. 서버는 저작물을 애초에 보유하지 않는 구조로 설계한다. 이 원칙은 본 문서 전체를 관통하며, 어떤 기능도 이 경계를 넘지 않는다.

**※ 코퍼스 전제**: 개발용 코퍼스는 개발자 개인 보유 음원 1004곡(64.06시간, 9.29GB)이며 **배포 대상이 아니다.** 상용 음원이므로 서비스 코퍼스로 사용하지
않는다. 배포 시 참조가 필요한 경우 공개 라이선스 데이터셋(MTG-Jamendo, FMA)으로 교체하되, 로컬 에이전트 방식이므로 서비스 코퍼스 자체가 필수는 아니다.

**※ 수치 표기 원칙**: 본 문서의 수치는 인제스트·분석 산출물에서 코드로 재산출한 값이며 결정 기록마다 `재현` 명령이 붙는다 (D-0135). 미검증 항목은 **(실측
필요)**로 명시하며 추측으로 채우지 않는다(GR-0.5).

**※ 문서 체계**: 넷이다 (D-0186 ~ D-0189). 본 문서는 **현재 · 단일 진실 공급원**으로 "무엇이 참인가"를 쓴다. `docs/PLAN.md`가 미래,
`docs/DECISIONS.md`가 과거(추가 전용), `README.md`가 진입이다. **밖에 내는 기획서는 `docs/proposal.docx`** — 시제 밖이며
본 문서 Part I ~ III에서 `make proposal`로 빌드한다. 정본 지문을 `tools/docx_check.py`가 대조한다 (D-0221).

**※ 명칭**: HATHOR는 이집트 신화에서 음악·춤·사랑을 관장한 여신 하토르에서 따왔다. 도구가 아니라 창작의 동반자를 지향한다는 의미를 담는다.

**※ 병행 과제 고지**: 개발자는 2026-12-11까지 광주 인공지능사관학교 7기 파이널 프로젝트(Fire-Lane, 5인 1조)를 병행한다. 해당 기간 HATHOR는
후순위이며, 일정 계획에 이 제약을 반영한다.

# Part I. 프로젝트 제안서

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| **프로젝트 주제** | **엣지 분석 기반 개인 취향 잠재 표현으로 조건화한 종단간 AI 음악 생성 시스템** |
| **개발 형태** | 1인 풀스택 (기획·설계·구현·배포·평가 전 과정)<br>기간: 2026-08 착수 · 장기 과제 (병행 과제 고려)<br>예산: 개인 부담. GPU 인스턴스 상시 운영 제외, 보유 장비(GTX 1660Ti 6GB)로 분석까지.<br>**생성 엔진은 VRAM 16GB 이상 장비에서 돈다** — 6GB에서 실측으로 떨어졌다 (D-0218) |
| **개발자 및 역할** | 오창준 — 전 영역 단독 수행 |

### 추진배경 및 필요성

**○ [생성형 음악 서비스는 "누가 듣는가"를 모델링하지 않는다]**

Suno, Udio 등 현행 서비스는 텍스트 프롬프트를 입력으로 받는다. 프롬프트는 사용자의 **의도**를 전달하지만 **취향**은 전달하지 못한다. "슬픈 발라드"라고 입력한 두
사람이 원하는 결과는 전혀 다르며, 그 차이는 각자가 그동안 들어온 음악에 축적되어 있다. 현행 서비스는 이 축적된 정보를 입력 경로 자체에서 버린다.

**○ [사람은 자기 취향을 형용사로 표현하지 못한다]**

"어떤 음악을 좋아하세요"라는 질문에 정확히 답할 수 있는 사용자는 드물다. 반면 "이 곡 같은 느낌"이라는 지시는 누구나 할 수 있다. 취향 입력의 단위는 형용사가 아니라
**곡**이어야 한다. 이는 UI 편의의 문제가 아니라 정보량의 문제다. 곡 하나에는 형용사 열 개보다 많은 정보가 들어 있다.

**○ [취향 데이터는 개인 기기에 있고, 그것을 서버로 옮기는 순간 문제가 된다]**

사용자의 취향을 가장 잘 나타내는 자료는 그가 실제로 소유하고 듣는 음원이다. 그런데 이 음원은 대부분 저작권 보호 대상이다. 서비스가 이를 업로드받아 서버에 저장하는 순간 서비스
제공자가 복제 주체가 된다. 취향 정보를 얻으면서 저작물은 취득하지 않는 구조가 필요하다.

**○ [기존 시스템은 축이 분리되어 있지 않다]**

현행 생성 모델은 프롬프트 하나로 곡 전체를 만든다. "멜로디는 A곡처럼, 가창은 B곡처럼"과 같은 축별 지정이 불가능하다. 그러나 실제 창작에서 작곡·편곡·작사·가창은 분리된
작업이며, 사용자의 취향도 축마다 다르다. 발라드 멜로디를 좋아하면서 힙합 편곡을 선호하는 것은 모순이 아니다.

**○ [평가 기준이 "그럴듯함"에 머물러 있다]**

생성 음악의 품질 평가는 대부분 주관적 청취에 의존하거나 FAD 같은 분포 거리 지표에 머문다. "이 사용자의 취향에 맞는가"를 정량적으로 평가하는 체계가 없다. 취향을 벡터로
정의하면 생성 결과와 취향 벡터의 거리를 직접 측정할 수 있다.

### 목적 및 핵심가치

**○ [취향의 벡터화 — 프롬프트가 아니라 잠재 표현]**

사용자 라이브러리를 음악·편곡·가사·가창 4축으로 분석하여 각 축의 잠재 공간을 구축하고, 사용자의 취향을 그 공간 위의 벡터로 정의한다. 생성 시 이 벡터를 조건으로 사용한다.
프롬프트는 보조 입력이지 주 입력이 아니다.

**○ [엣지 우선 저작권 설계 — 서버는 음원을 보지 않는다]**

원본 오디오가 서버에 도달하는 순간 서비스가 복제 주체가 된다. 스캔·분석·특징 추출을 사용자 기기에서 수행하고, 서버로는 벡터만 전송한다. 이는 성능 최적화가 아니라 **법적
구조의 설계**다.

**○ [축별 독립 조건화 — "멜로디는 A, 가창은 B"]**

4축 각각에 다른 시드곡을 지정할 수 있게 한다. 프롬프트 기반 시스템이 구조적으로 제공할 수 없는 조작이며, 축을 분리해 설계한 것의 직접적 산출이다.

**○ [양성 사례만으로 성립하는 학습 설계]**

사용자 라이브러리는 전부 "좋아해서 소유한" 곡이다. 음성 사례가 존재하지 않는다. 이 문제를 외부 데이터로 메우는 대신, 문제를 선호도 예측에서 조건부 생성으로 재정의하여 양성
사례만으로 성립시킨다. 상대 순위 정보가 필요한 부분은 쌍대비교로 내부에서 생성한다.

**○ [실측이 설계를 결정한다 — 추측으로 채우지 않는다]**

라이브러리 태그 실측에서 발매일·ISRC가 전량 부재함을 확인하고 지문 기반 정규화를 주 경로로 승격했다. 아티스트 필드의 괄호가 피처링이 아니라 별칭 병기임을 확인하고 파서
설계를 뒤집었다. 미검증 항목은 (실측 필요)로 표시하고 추측으로 진행하지 않는다.

**○ [생성 결과의 안전 게이트 — 실존 가수 음색 차단]**

취향 학습이 특정 가수의 음색 복제로 귀결되면 인격권·퍼블리시티권 침해가 된다. 참조 오디오로 조건화한 출력의 보컬을 화자 임베딩으로
재서, 참조 가수와 유의하게 가까우면 **참조 오디오 모드 자체를 제품에서 끈다** (G2 · D-0217).

### 주요 서비스

**□ 서비스 메뉴 구조도**

**HATHOR System**

**1. 로컬 에이전트 (데스크톱 앱)**
- 1.1 라이브러리 스캔 및 태그 추출 (음원은 기기 외부로 전송하지 않음)
- 1.2 4축 특징 추출 파이프라인 (GPU 가속 / CPU 폴백)
- 1.3 백그라운드 분석 작업 — 중단·재개, 곡 단위 진행률
- 1.4 취향 벡터 산출 및 서버 동기화 (벡터만 전송)
- 1.5 로컬 분석 결과 조회 — 라이브러리 4축 프로파일 시각화

**2. 취향 프로파일링**
- 2.1 라이브러리 기반 초기 취향 벡터 자동 산출
- 2.2 적응적 쌍대비교 온보딩 (이상형 월드컵형, 20~30회)
- 2.3 축별 취향 분해 표시 (음악·편곡·가사·가창)
- 2.4 취향 변화 이력 및 재학습

**3. 곡 생성**
- 3.1 시드곡 선택 (축별 독립 지정 가능, 1~5곡)
- 3.2 미세조정 슬라이더 (템포·밝기·밀도 등, 시드 위의 보정)
- 3.3 생성 파이프라인 실행 — 구조 → 화성 → 멜로디 → 편곡 → 가사 → 가창 → 믹스
- 3.4 단계별 중간 산출물 열람 및 부분 재생성
- 3.5 시드 고정 재현 생성 (동일 시드 = 동일 산출물)

**4. 결과 관리**
- 4.1 생성 곡 라이브러리 및 버전 이력
- 4.2 스템 분리 다운로드 (보컬·드럼·베이스·기타)
- 4.3 MIDI·악보 내보내기
- 4.4 생성 결과 피드백 → 취향 벡터 갱신

**5. 품질 · 안전 게이트**
- 5.1 화자 동일성 검사 — 실존 가수 식별 가능 시 차단
- 5.2 멜로디 유사도 검사 — 기존 곡 표절 구간 탐지
- 5.3 취향 적합도 점수 — 생성 결과와 취향 벡터 거리
- 5.4 차단 사유 및 재생성 가이드 제시

**6. 관리 · 검증**
- 6.1 파이프라인 재실행 및 산출 이력(manifest) 조회
- 6.2 평가 리포트 — 베이스라인 대비 지표
- 6.3 데모 모드 — 설치 없이 사전 분석된 프로파일로 체험

### 주요 기술

**[Local Agent]**
- Tauri (Rust + 웹뷰). Electron 대비 번들 크기·메모리가 작고 웹 UI를 서버와 공유한다.
- 인제스트 파이프라인은 Python 사이드카 프로세스로 분리. 이미 구현된 스캐너·추출기를 그대로 재사용한다.
- 델타 감지(mtime + size)로 재분석을 변경분에 한정한다. 곡당 GPU 수십 초가 드는 스템 분리에서 이 절감이 결정적이다.
- drvfs·NTFS 등 파일시스템 감시가 불가능한 환경이 존재하므로 실시간 감시가 아니라 명시적 재스캔 방식을 채택한다.

**[Audio Analysis]**
- Demucs v4 (htdemucs) 스템 분리 — 편곡축·가창축의 전제. 44.1kHz 입력.
- MERT — 음악 이해 자기지도 표현. 음악축 임베딩. 24kHz 입력.
  **가중치가 CC-BY-NC-4.0이라 제품 경로에 못 간다** — 대체를 같은 하네스로 잰다 (D-0217 · O-68).
- CLAP — 오디오·텍스트 정렬 임베딩. 축 간 공통 참조 공간. 48kHz 입력.
- 샘플레이트는 인제스트에서 통일하지 않고 원본을 유지한 뒤 모델 입력 직전에 리샘플한다. 모델별 요구 샘플레이트가 상이하므로 사전 통일은 손실만 발생시킨다.
- 곡 신원은 **MusicBrainz MBID**로 정규화한다 (D-0017). 태그 표기로는 곡을 못 찾아 아티스트를 먼저 확정하고
  그 정규명으로 곡을 찾는 2단계이며, 곡 조회 상한은 **78.5%**다 (D-0019). 지문 경로는 곡당 디코딩 비용으로 기각했다.

**[NLP · Lyrics]**
- USLT 태그 가사를 우선 사용하고, 부재 시 Whisper STT로 폴백한다. 포트를 분리해 구현체를 교체 가능하게 둔다.
- 동기 가사(SYLT)가 전량 부재하므로 한국어 강제정렬(Montreal Forced Aligner 등)로 시간 정보를 생성한다. 가창축 학습의 전제다.
- 가사 언어는 태그의 언어 필드를 신뢰하지 않고 본문에서 판별한다. 실측상 한국어 가사가 `eng`로 기재되어 있다.
- 가사 임베딩은 **BGE-M3**(MIT)로 산출한다. 한·영 혼재 가사가 40%라 다국어 인코더가 결정 근거였다 (D-0045 · D-0048).

**[Generation]**
- 단계 분리 파이프라인: 구조 → 화성 → 멜로디 → 편곡 → 가사 → 가창 → 믹스. 각 단계가 독립 엔진이며 중간 산출물이 검사 가능하다.
- 심볼릭 단계(구조·화성·멜로디)는 MIDI로 다루고, 오디오 렌더링은 이후 단계에서 수행한다. 전 구간 오디오 생성보다 제어 가능성이 높다.
- 가창은 오디오 엔진이 입힌다. **실존 가수 음색 복제는 구현하지 않는다** (D-0003) — 참조 오디오 모드의 음색 누설을
  화자 임베딩 self/other로 재는 관문(G2)을 엔진 채택 조건으로 건다 (D-0217).
- 전 파이프라인은 시드 고정 시 결정적으로 동작한다.
- **오디오 렌더링은 공개 가중치 엔진에 맡긴다.** 서류 관문으로 일곱을 걸러 ACE-Step 1.5(MIT)가
  1순위다. **hathor가 기획하고 — 구조·화성·가락 — 엔진이 소리를 입힌다.** 엔진의 기획 언어
  모델은 hathor가 대신한다 (D-0217 · D-0218).

**[Backend & Infrastructure]**
- FastAPI (취향 동기화 API · 생성 작업 API · 결과 서빙)
- PostgreSQL + pgvector (취향 벡터·특징 임베딩 검색), MongoDB (생성 이력·중간 산출물), Redis (작업 상태), RabbitMQ (생성 작업
  큐), MinIO (산출물 오브젝트 스토리지)
- 계층 구조를 import-linter 계약으로 강제한다. 도메인 격리 / 애플리케이션 격리 / 엔진 간 직접 호출 금지 / 계층 순서 /
  **송신부는 오디오를 모른다** 5종 (D-0134).
- **현재 산출물은 `var/`의 곡 묶음(npz)과 JSONL이다.** DB·큐·오브젝트 저장소는 Compose로 기동만 해 두었고 P4에서 붙인다.
- CI 3잡: 품질(ruff·mypy strict·계약·커버리지) / 시크릿 스캔 / 재현성 검증.
- Docker Compose 기반 로컬 구성, 배포는 단일 인스턴스.

**[Frontend]**
- React(Vite) + TypeScript. 로컬 에이전트 웹뷰와 웹 대시보드가 동일 컴포넌트를 공유한다.
- 파형·스펙트로그램 표출은 WaveSurfer.js, 취향 공간 시각화는 D3 기반 2차원 투영(UMAP·t-SNE).

### 기대효과

**[취향 입력 방식의 대안 제시]**
- 텍스트 프롬프트가 아니라 시드곡과 잠재 벡터로 생성을 조건화하는 방식을 구현하고, 프롬프트 기반 베이스라인 대비 취향 적합도를 정량 비교한다.

**[저작물을 취득하지 않는 개인화 구조]**
- 원본 오디오가 서버에 도달하지 않으면서 개인 취향을 반영하는 구조를 실제 동작으로 제시한다. 음악뿐 아니라 개인 미디어 자료 전반에 적용 가능한 참조 설계가 된다.

**[축별 조건 분리의 실증]**
- "멜로디는 A곡, 가창은 B곡"과 같은 축별 지정이 실제로 결과에 반영되는지를 축별 절제 실험으로 검증한다.

**[생성 안전 게이트의 구현 사례]**
- 실존 가수 음색 누설을 화자 임베딩 self/other로 재는 관문(G2)을 엔진 채택 조건으로 건다. 귀무를 먼저 돌리고, 판정 규칙을 착수 전에 적는다.
  정성적 정책 선언이 아니라 동작하는 관문으로 제시한다.

**[1인 풀스택 역량의 통합 증명]**
- 오디오 신호처리·심층학습·백엔드·데스크톱 앱·인프라·CI를 하나의 시스템에서 통합 운용한 이력을 남긴다. 개별 기술 나열이 아니라 상호 의존하는 시스템으로 증명한다.

### 활용방안 및 비즈니스 모델

**□ 활용 방안**

**[개인 창작 보조 도구]**
- 작곡 경험이 없는 사용자가 자신의 취향에 맞는 곡을 얻는다. 완성곡뿐 아니라 MIDI·스템을 제공하여 이후 편집의 출발점으로 쓸 수 있다.

**[창작자의 아이디어 스케치]**
- 작곡가가 자신의 기존 작업물을 시드로 넣어 유사 계열의 변주를 대량 생성하고 그중 발전시킬 소재를 고른다.

**[취향 분석 자체의 가치]**
- 생성을 사용하지 않더라도 자기 라이브러리의 4축 프로파일을 시각화하는 것만으로 사용자에게 정보 가치가 있다.

**□ 비즈니스 모델**

**[로컬 우선 프리미엄 구독]**
- 분석은 로컬에서 무료, 생성은 서버 GPU를 사용하므로 종량 또는 구독. 로컬 분석이 무료여도 서버 비용이 발생하지 않는 구조가 이 설계의 이점이다.

**[분석 모듈 라이선스]**
- 4축 특징 추출 파이프라인을 음악 서비스·DAW 플러그인에 공급하는 모듈형 라이선스.

**[한계 인식]**
- 착수 때는 취업 포트폴리오였고 **2026-09에 남들이 쓰는 제품으로 목표를 바꿨다** (D-0215). 그 순간 전제가 바뀌었다 — **모델 가중치의 라이선스와
  학습 데이터 출처가 제약이 됐고,** 이미 쓰던 MERT부터 걸렸다 (D-0217). 생성 음악의 저작권 귀속은 국내외에서 정리되지 않았고, 이는 출시 이전에
  해소되어야 할 선결 조건이다.

## 2. 아이디어 도출 과정

본 프로젝트는 'AI 음악 생성'이라는 소재에서 출발했으나, 그것을 프롬프트가 아니라 취향 잠재 표현으로 다루기까지 네 단계의 발상 정리를 거쳤다.

### □ 강제연결법 (Forced Connection)

| 축 A — 하고 싶은 것 | 축 B — 보유 자산 | 결합 결과 |
|---|---|---|
| AI 음악 생성 | 프롬프트 엔지니어링 | 프롬프트 기반 생성 — Suno·Udio와 완전 중복. 차별성 없음 |
| AI 음악 생성 | 개인 음원 라이브러리 1004곡 | 취향 학습 기반 추천 — 추천은 생성이 아니며 Spotify와 중복 |
| 음악 추천 | 잠재 표현 학습 | 임베딩 기반 추천 시스템 — 다수 존재. 신규성 없음 |
| **AI 음악 생성 × 개인 라이브러리** | **잠재 표현 + 엣지 분석** | **개인 취향 벡터로 조건화한 생성 — 선행 사례 미확인. 채택** |

앞의 세 조합은 기존 서비스와 겹치거나 기술 신규성이 없었다. 네 번째만 오디오 분석·표현 학습·생성 모델이 모두 필수적으로 요구되며, 조사 결과 개인 라이브러리를 잠재 표현으로
변환해 생성을 조건화하는 상용 시스템이 확인되지 않았다.

### □ SCAMPER 적용

기준 대상은 '텍스트 프롬프트 기반 음악 생성 서비스'다.

| 기법 | 적용 | 결과 |
|---|---|---|
| **S**ubstitute | 프롬프트를 무엇으로 대체할 것인가 | 텍스트 → **시드곡 + 취향 벡터**. 사용자가 형용사를 고르지 않고 아는 곡을 고른다 |
| **C**ombine | 무엇과 결합할 것인가 | 생성 + **개인 라이브러리 분석**. 추천 시스템의 취향 모델링을 생성의 조건 입력으로 연결 |
| **A**dapt | 다른 분야에서 무엇을 가져올 것인가 | 연합학습·엣지 추론의 **데이터 비이동 원칙**을 저작권 문제에 적용 |
| **M**odify | 무엇을 확대·축소할 것인가 | 생성 단위를 곡 전체에서 **4축으로 분해**. 축별 독립 조건 지정 가능 |
| **P**ut to other use | 다른 용도 | 생성을 쓰지 않아도 **라이브러리 4축 프로파일 시각화** 자체가 산출물 |
| **E**liminate | 무엇을 제거할 것인가 | **음원 업로드를 제거**. 서버가 저작물을 보유하지 않음 |
| **R**everse | 무엇을 뒤집을 것인가 | "무엇을 좋아하는가"를 묻지 않고 **"둘 중 어느 쪽인가"를 반복**해 취향을 역산 (쌍대비교) |

### □ 모순 분석

설계 과정에서 정면으로 충돌한 요구를 정리한다.

| 모순 | 갈등 구조 | 해소 방식 |
|---|---|---|
| **개인화 vs 저작권** | 취향을 알려면 음원이 필요한데, 음원을 받으면 복제 주체가 된다 | 음원이 아니라 **음원에서 뽑은 벡터**만 이동시킨다. 분석을 엣지로 옮겨 문제를 발생 지점에서 제거 |
| **취향 학습 vs 음성 사례 부재** | 라이브러리는 전부 양성 사례이며 싫어하는 곡이 없다 | 문제를 **선호도 예측에서 조건부 생성으로 재정의**. 순위 정보가 필요한 부분은 쌍대비교로 내부 생성 |
| **취향 반영 vs 음색 도용** | 취향을 정확히 반영할수록 특정 가수 음색에 수렴한다 | **G2 음색 누설 관문** — 누설이 보이면 참조 오디오 모드를 끈다. 식별 가능한 산출만 막는다 (D-0217) |
| **로컬 분석 vs 연산 자원** | 개인 기기에 GPU가 없을 수 있다 | CPU 폴백을 정식 구현하고 **백그라운드 중단·재개**로 흡수. 부분 결과로도 취향 벡터 산출 가능 |
| **결정적 재현 vs 생성 다양성** | 재현성 검증을 하려면 결정적이어야 하는데 창작은 다양해야 한다 | **시드를 명시적 입력으로 노출**. 동일 시드는 동일 산출, 시드 변경으로 다양성 확보 |

### □ 아이디어 평가

| 평가 항목 | 프롬프트 기반 생성 | 임베딩 기반 추천 | **취향 조건 생성 (채택)** |
|---|---|---|---|
| 기술 신규성 | 낮음 | 낮음 | **높음** |
| 1인 구현 가능성 | 높음 | 높음 | **중간** |
| 포트폴리오 서사 | 약함 | 중간 | **강함** |
| 법적 리스크 | 중간 | 낮음 | **중간 (설계로 완화)** |
| 데이터 확보 | 불필요 | 필요 | **보유 (1004곡)** |
| 평가 가능성 | 어려움 | 쉬움 | **가능 (벡터 거리)** |

채택안은 구현 난도가 가장 높으나, 나머지 항목에서 우위가 명확하고 데이터를 이미 보유하고 있다. 난도는 단계 분할(P0~P8)과 각 단계의 독립 검증으로 관리한다.

## 3. 시장현황 및 유사 서비스 분석

### □ 유사 서비스 분석 및 비교

| 서비스 | 입력 방식 | 개인화 | 축 분리 | 데이터 경계 | 산출물 |
|---|---|---|---|---|---|
| **Suno** | 텍스트 프롬프트 + 가사 | 없음 | 없음 | 서버 처리 | 완성 오디오 |
| **Udio** | 텍스트 프롬프트 | 없음 | 부분 (리믹스) | 서버 처리 | 완성 오디오 |
| **SoundRaw** | 장르·무드 선택 | 없음 | 부분 (파트 교체) | 서버 처리 | 완성 오디오 |
| **AIVA** | 스타일 프리셋 | 없음 | 있음 (MIDI 편집) | 서버 처리 | MIDI + 오디오 |
| **Mubert** | 텍스트·태그 | 없음 | 없음 | 서버 처리 | 스트림 |
| **MusicGen (Meta)** | 텍스트 + 멜로디 조건 | 없음 | 부분 (멜로디 조건) | 로컬 실행 가능 · **가중치 비상업** | 오디오 |
| **ACE-Step 1.5** | 텍스트·가사 + 참조 오디오 | 없음 | 부분 (커버·리페인트) | 로컬 실행 가능 · MIT | 오디오 |
| **HATHOR** | **시드곡 + 취향 벡터** | **라이브러리 기반** | **4축 독립** | **엣지 분석, 음원 비이동** | **오디오 + 스템 + MIDI** |

**분석 요약**

- 개인 취향을 **누적 학습**하는 생성 서비스는 확인되지 않는다. 모든 서비스가 세션 단위 프롬프트로 동작한다.
- MusicGen이 멜로디 조건화를 제공하나 단일 축이며 취향 개념이 없다.
- **공개 엔진은 경쟁자가 아니라 부품이다.** ACE-Step 1.5는 참조 오디오를 받지만 누구의 취향인지 모른다 — hathor가 그 자리를 채운다 (D-0217).
- AIVA가 MIDI 편집으로 축 분리에 가장 근접하나, 사용자의 취향을 학습하지 않고 프리셋을 선택하게 한다.
- **데이터 경계를 설계 원칙으로 명시한 서비스가 없다.** 모두 서버 처리 전제다.
- (실측 필요) 각 서비스의 최신 기능·정책은 조사 시점 기준이며, 구현 착수 전 재확인이 필요하다.

### □ SWOT 분석

### □ SWOT 교차 분석 기반 실행 전략

**[SO — 강점으로 기회를 잡는다]**
- 보유 코퍼스로 4축 분석 파이프라인을 먼저 완성하고, 취향 프로파일 시각화를 **생성 이전에 독립 산출물로 확보**한다. 생성이 미완이어도 포트폴리오가 성립한다.
- 사전학습 모델을 학습이 아니라 **특징 추출기로 사용**하여 VRAM 제약을 우회한다.

**[ST — 강점으로 위협에 대응한다]**
- 결정 기록 체계로 **"왜 이 설계인가"를 문서로 남긴다.** 기능이 아니라 판단 과정이 포트폴리오의 실질이며, 이는 대형 서비스가 유사 기능을 내도 무효화되지 않는다.
- 음색 게이트를 선제 구현하여 규제 강화 시에도 설계 변경이 불필요하게 한다.

**[WO — 약점을 보완해 기회를 취한다]**
- 6GB VRAM에서 **파인튜닝은 LoRA·어댑터로 한정**하고 전체 학습은 시도하지 않는다. 필요 시 클라우드 GPU를 단발성으로 임차한다.
- 병행 과제 기간에는 문서·설계·분석 단계를 진행하고, GPU 집약 단계는 12월 이후로 배치한다.

**[WT — 약점과 위협을 동시에 회피한다]**
- 생성 단계 미완 가능성을 인정하고 **P3(취향 프로파일)까지를 최소 완성 목표**로 고정한다. P4 이후는 확장 목표로 분리한다.
- 기기가 1대로 줄었다 (D-0122). 산출물은 외장 백업으로 복원하며 실측 복원 17,192개 · 4분 12초다.
- **장비가 필요한 일만 멈춘다** (D-0218). 생성 엔진 실측이 GPU를 기다리는 동안 분석·검사·문서는 계속한다.

**[Targeting]**

**1차 타깃: B (창작 지망 비전공자).** 취향은 뚜렷하나 그것을 음악으로 옮길 수단이 없는 집단이다. 시드곡 선택이라는 입력 방식이 이 집단의 장벽을 정확히 제거한다.

**2차 타깃: C (아마추어 창작자).** MIDI·스템 산출물이 이들에게 실질 가치를 갖는다.

D는 제외한다. 현행 생성 모델 품질로 전문가 요구를 충족할 수 없으며, 억지로 겨냥하면 모든 지표에서 미달한다.

**[Positioning]**

> "프롬프트를 쓰지 않는 음악 생성. 당신이 들어온 음악이 입력이다."

## □ 요구사항 ID 체계 정의

`REQ-{그룹}-{번호}` 형식. 번호는 그룹 내 3자리 일련번호.

| 항목 | 규칙 |
|---|---|
| 그룹 | 위 체계도의 3문자 코드 |
| 번호 | 001부터 순차. 폐기해도 재사용하지 않는다 |
| 우선순위 | **M**(Must, MVP 필수) / **S**(Should) / **C**(Could) |
| 단계 | 해당 요구사항이 구현되는 P단계 |
| 상태 | 미착수 / 진행 / 부분 / 완료 / 강제 / 설계 / 보류 / 변경 / 폐기 |

**MVP 경계**: 우선순위 M은 P4까지의 범위에 한정한다. P5 이후 요구사항은 최대 S를 부여한다. 이는 미완 시 MVP 판정에 영향을 주지 않기 위한 장치다.

### □ 계층 구조 (GR-2)

정적 계약(import-linter)으로 강제되는 6계층. **계약 정의는 `core/pyproject.toml`이 진실이며
여기에는 근거만 둔다** — 설정을 문서에 다시 적으면 반드시 어긋난다 (D-0042 · D-0043).

| 계층 | 책임 | 의존 방향 |
|---|---|---|
| `domain` | 엔티티·값객체·포트. 외부를 전혀 모른다 | 없음 |
| `application` | 유스케이스·오케스트레이션. 포트에만 의존 | → domain |
| `engines` | 무거운 AI 연산 단위. 엔진 간 직접 호출 금지 | → domain |
| `infrastructure` | 포트 구현체. DB·파일시스템·외부 API·모델 | → domain, application |
| `interfaces` | CLI·REST·워커 진입점. 비즈니스 로직 없음 | → application |
| `shared` | 설정·텔레메트리 | 없음 |

**계약 5종**
1. 도메인은 외부를 모른다 — `domain`이 다른 계층을 import하지 않는다
2. 애플리케이션은 구현체를 모른다 — `application`이 `infrastructure`를 import하지 않는다
3. 엔진 간 직접 호출 금지 — 엔진끼리 서로 import하지 않는다. 조합은 `application`이 한다
4. 계층 순서 — 위 의존 방향을 역행하지 않는다
5. **송신부는 오디오를 모른다** — 망을 타는 모듈이 디코더·분리기·특징 추출기·파형
   타입을 import하지 않는다. D-0015의 *"타입 수준의 불가능"*을 서버 없이 구현한
   형태다 (D-0134)

**엔진 vs 배관의 구분 기준**: 엔진은 무거운 AI 연산이다. 인제스트는 파일을 읽고 표를 만드는 배관이므로 엔진이 아니며 `application` +
`infrastructure`에 배치한다.

### □ 트리거 타이밍 — 명시적 실행, 상시 감시 없음

파일시스템 실시간 감시는 채택하지 않는다. drvfs 경유 외장 볼륨에서 inotify watch 등록은 성공하나 이벤트가 전달되지 않음을 실측으로 확인했다. 등록이 성공하므로
상위 라이브러리는 오류 없이 무동작 상태가 되며, 감시가 조용히 실패한다.

| 시점 | 동작 |
|---|---|
| 사용자 명시적 실행 | 라이브러리 재스캔 → 델타 판정 |
| 델타 발생 곡 | 스템 분리 및 4축 분석 수행 |
| 무변화 곡 | 분석 건너뜀. 기존 결과 재사용 |
| 취향 벡터 | 분석 완료분으로 즉시 재산출 |
| 생성 요청 | 사용자 트리거. 큐에 등록 |

**델타 감지의 값이 나오는 지점**: 인제스트 자체는 1004곡 10.8초라 절감 여지가 없다. 실질 이득은 곡당 GPU 연산이 발생하는 스템 분리에서 나온다. 따라서 델타 기반
건너뛰기는 P2에서 구현한다.

## 2. 데이터 설계

### □ 데이터 규칙 (GR-3)

**저장소 역할 분담** — 어느 저장소가 진실인지 흐려지면 같은 사실이 두 곳에서 갈린다.

| 저장소 | 역할 | 금지 |
|---|---|---|
| **PostgreSQL** | 관계 데이터의 **단일 진실 공급원**. 벡터(pgvector) 포함 | — |
| MongoDB | 원본 태그·트레이스·로그 등 비정형 | **진실 공급원으로 사용 금지** |
| Redis | 캐시·락·진행률 | **영속 데이터 저장 금지.** 유실을 전제로 설계 (미도입, O-11) |
| 오브젝트 스토리지 | 오디오·모델·산출물 | 메타데이터 저장 금지 |

**공통 컬럼** — 모든 PostgreSQL 테이블에 포함한다.

| 컬럼 | 타입 | 규칙 |
|---|---|---|
| `{entity}_id` | UUID | PK. `gen_random_uuid()`. **순차 정수 금지** (열거 공격 방지) |
| `created_at` | TIMESTAMPTZ | 생성 시 기록. **변경 금지** |
| `updated_at` | TIMESTAMPTZ | 트리거로 자동 갱신 |
| `deleted_at` | TIMESTAMPTZ | 사용자 데이터는 소프트 삭제 |

**시각은 전부 TIMESTAMPTZ(UTC)로 저장한다.** 표시 시점에만 로컬 변환한다.

**모델링**

1. 기본 설계는 **3NF**에서 시작한다.
2. 반정규화는 **측정된 성능 문제가 있을 때만** 하고, 사유와 일관성 보장 방법을 남긴다.
3. 모델 구조는 API 응답이 아니라 **저장 기준**으로 설계한다.
4. **ORM 엔티티를 API 응답으로 직접 반환하지 않는다.** 반드시 DTO를 거친다.
5. JSONB는 (1) 스키마가 유동적이고 (2) 검색 조건이 아닌 것에만 쓴다. 검색 조건이 되면 컬럼으로 승격한다.

**ML 데이터**

| 규칙 | 내용 |
|---|---|
| 피처 버전 | 추출기 변경 시 버전 증가. **기존 버전 보존** |
| 임베딩 버전 | 모델 버전 필수 기록. 모델이 다르면 다른 레코드 |
| 취향 프로파일 | 갱신 시 새 버전 INSERT. **기존 버전 불변** |
| 외부 참조 | 라이선스 NOT NULL. 오디오 미보관 제약 (C-8) |
| 대용량 | Git에 바이너리 금지. `var/` 하위는 gitignore |

## 3. 인제스트 상세 설계

### □ 처리 순서

```text
파일 발견 (sorted 강제)
  → 헤더·태그 읽기 (디코딩 없음)
  → 실패 격리 (분류 후 계속)
  → 델타 판정 (mtime + size)
  → 아티스트 파싱 (후보 제시)
  → 외부 조회 (MusicBrainz 2단계: 아티스트 → 정규명으로 곡)       D-0019
  → 레코딩 버전 확정 (재생시간)                                    D-0020
  → 곡 묶음 추출 (디코딩 1회 · 분리 1회 → MERT · 크로마 · 온셋 · 음고)  D-0203
  → JSONL · npz 저장 (DB 업서트는 P4)
```

| `UNREADABLE_FILE` | OS 수준 읽기 실패 |
| `CORRUPT_HEADER` | 태그·헤더 파싱 실패 |
| `MISSING_AUDIO_STREAM` | 스트림 정보 부재 또는 길이 0 이하 |
| `TAG_DECODE_ERROR` | 태그 디코딩 실패 |
| `PERMISSION_DENIED` | 권한 없음 |
| `UNEXPECTED_ERROR` | 그 외 |

**격리 원칙**: 어떤 단일 파일도 전체 순회를 중단시키지 않는다. 프로세스 종료 코드는 실패율이 임계를 넘을 때만 비정상이 된다.

### □ 델타 이벤트

| 이벤트 | 조건 | 후속 처리 |
|---|---|---|
| `DISCOVERED` | 이전 스냅샷에 없음 | 전체 분석 |
| `MODIFIED` | mtime 또는 size 변경 | 전체 재분석 |
| `UNCHANGED` | 둘 다 동일 | 분석 건너뜀 |
| `REMOVED` | 이전에 있었으나 발견되지 않음 | 소실 처리 |

**소실 오판 방지**: 외장 볼륨 미연결 시 전량이 `REMOVED`로 판정된다. 소실 비율이 임계(50%)를 넘으면 경고하고 자동 삭제를 수행하지 않는다.

**`REMOVED`는 실패가 아니다.** 실패 통계와 분리하여 기록한다.

### □ 아티스트 파서

**출력**

| 필드 | 내용 |
|---|---|
| `raw` | 원문 보존 |
| `primary` | 주 후보 `ArtistCandidate(name, aliases)` |
| `collaborators` | 쉼표 분리 후보. 각 원소가 `ArtistCandidate` |
| `normalized_key` | 괄호·공백 제거 + 소문자. 후보 단위로도 산출 |
| `confidence` | HIGH / MEDIUM / LOW |
| `ambiguity_reasons` | 판정 불가 사유 |

**신뢰도 규칙**

| 등급 | 조건 |
|---|---|
| HIGH | 구분자 없음, 또는 괄호만 존재 |
| MEDIUM | 쉼표 분리이며 각 토큰이 2자 이상 |
| LOW | 짧은 토큰, `&`만 존재, 괄호 내용이 다수 곡에 반복 출현(소속 의심) |

### □ MusicBrainz 조회 개선 이력 (D-0019)

| 단계 | 곡 조회 성공률 | 무엇이 올렸나 |
|---|---|---|
| 태그 원문 직접 조회 | 39.0% | — |
| 2단계 조회 | 77.9% | 아티스트를 먼저 확정하고 그 정규명으로 곡을 찾는다 (+38.9%p) |
| 중첩 괄호 처리 | 78.5% | 제목 부가 표기 (+0.6%p) — **남은 실패는 코드로 더 안 준다** |

**설계 원칙**: 파서는 정규화하지 않는다. 정규명 확정은 외부 조회의 책임이다. `아이유(IU)`는 한글이 앞이고 `BIGBANG (빅뱅)`은 영문이 앞이므로 주-부 순서
규칙을 문자열만으로 세울 수 없다.

## 5. 취향 모델 설계

**보조 기능으로 격하됐다** (D-0029). 아래 설계는 보존하되 착수하지 않는다. 주기능은 시드곡 퓨전이고,
무엇이 «좋은가»의 채점관은 제품이 돈 뒤 **자체 행동 데이터**로 세운다 — 밖에서 대중성 라벨을 구하는
길은 세 번 다 라이선스·커버리지에 막혔다 (D-0215 · D-0216 · O-67).

### □ 문제 재정의

라이브러리는 전량 양성 사례다. 선호도 이진 분류를 학습할 음성 사례가 존재하지 않는다.

| 접근 | 필요 데이터 | 판정 |
|---|---|---|
| 선호도 예측 | 양성 + 음성 | 성립 불가 |
| **조건부 생성** | **양성만** | **채택** |

"이 곡을 좋아할 것인가"는 음성 사례를 요구하지만 "이런 느낌으로 생성하라"는 양성만으로 성립한다. 균일 양성 데이터가 결함이 아니라 전제가 된다. <!--voice-ok-->

### □ 취향 신호 3층

| 층 | 신호 | 성격 | 갱신 |
|---|---|---|---|
| 1. 라이브러리 | 보유 곡 전체 | 전역 사전확률 | 재스캔 시 |
| 2. 쌍대비교 | A vs B 선택 | 상대 순위 | 온보딩·재학습 |
| 3. 시드곡 | 생성 시 참조곡 | 지역 조건 | 생성마다 |

**층이 다르므로 충돌하지 않고 누적된다.** 시드가 지정하지 않은 부분을 사전확률이 메운다.

### □ 쌍대비교

**목적**: 절대 라벨 없이 상대 순위 신호를 만든다. A를 고르면 B는 그 맥락에서 상대 음성이 되며, 음성 사례 부재 문제를 외부 데이터 없이 완화한다.

**쌍 선택**: 임베딩 공간에서 거리가 먼 쌍을 우선하고, 이후 현재 모델의 예측 불확실성이 높은 쌍(확률 0.5 근방)을 선택한다. 무작위 추출은 유사곡 쌍에서 정보량이 0에
수렴한다.

**적합**: Bradley-Terry 계열 쌍대비교 모델. **반드시 잠재 공간 위에서 적합한다.** 곡 ID에 대한 선호만 학습하면 라이브러리 밖으로 일반화되지 않아 신규
생성곡에 대해 아무것도 말해주지 못한다.

**시행 횟수**: 최소 20회, 이후 건너뛰기 허용. 재학습 시 반복 부담을 방지한다.

**호칭**: 본 기법은 랜덤 포레스트가 아니다. 문서·발표에서 혼용하지 않는다.

### □ 축별 분해

취향 벡터는 4축 각각에 대해 독립적으로 산출한다. 사용자가 발라드 멜로디를 선호하면서 힙합 편곡을 선호하는 것은 모순이 아니며, 축을 합치면 이 정보가 소실된다.

## 6. 생성 파이프라인 설계

### □ 기획과 렌더를 나눈다

**hathor가 기획하고 엔진이 소리를 입힌다** (D-0217 · D-0218). 초판은 구조부터 믹스까지
일곱 단계를 전부 자체 엔진으로 적었다. 기호 단계를 구현하고 들어 본 뒤 두 가지가 나왔다 —
**취향은 가창·음색·프로덕션에 살고** 기호 생성의 상한은 «편곡 스케치»다 (D-0214).

```text
[참조곡 1~5 + 라이브러리 사전]
       ↓
── 기획 (hathor · 결정적 · 구현됨) ──────────────────────────
1. 구조     참조곡 가사의 반복에서 섹션 배열을 뽑는다         D-0049
2. 화성     참조곡 조성 추정 → 화성 도수 사전                 D-0054 · D-0063
3. 배열     으뜸음 기준으로 회전한 전이 사전                   D-0110 · D-0213
4. 가락     박마다 화음 구성음을 짚는다                        D-0141
5. 베이스   근음을 받치고 성부 진행으로 잇는다                 D-0137 · D-0139
6. 반주     층별 세기 · 박으로 쪼갠 위 성부                    D-0174 ~ D-0177 · D-0207
       ↓  SMF (라이브러리 없이 직접 인코딩 · D-0052)
── 렌더 (오디오 엔진 · 장비 대기) ──────────────────────────
7. 가사 · 가창 · 편곡 · 믹스     ACE-Step 1.5 (MIT)             D-0217
       ↓
[관문] G2 음색 누설 · G3 조건 도달 → 통과 시 산출
```

**엔진의 기획 언어 모델을 hathor가 대신한다.** ACE-Step 1.5는 한 줄 설명에서 BPM·조성·구조·
가사를 짜는 기획 모델과 소리를 만드는 확산 모델로 나뉘고, 저사양 층에서는 기획 모델이
꺼진다. 엔진 문서도 참조 오디오 모드에서 *"사용자가 기획자"*라 적는다 (D-0218).

### □ 결정성

기획 단계는 시드 고정 시 **바이트까지 결정적**이다. MIDI 라이브러리를 쓰지 않고 SMF를 직접
인코딩한다 — 외부 라이브러리는 버전마다 바이트가 달라진다 (D-0052). CI가 같은 시드로 두 번
돌려 대조한다. **렌더 단계는 결정적이지 않다** — 확산 샘플링은 바이트 결정론이 아니며,
결정론은 기획(조건)까지만 보장한다 (O-65).

### □ 엔진 선정 — 서류 관문 (D-0217)

설치에 한나절이 드는 모델을 **라이선스 한 줄로 떨굴 수 있다.** 넷을 순서대로 걸었다 — 가중치
라이선스 · 보컬 · 조건 자리(참조 오디오) · 공개 VRAM.

| 모델 | 가중치 라이선스 | 보컬 | 조건 자리 | 공개 VRAM | 판정 |
|---|---|---|---|---|---|
| **ACE-Step 1.5** | **MIT** | 가사 · 50여 언어 | **참조 오디오** · 커버 · 리페인트 | 4 ~ 6GB 층: LM 없음 · INT8 · CPU 오프로드 | **1순위** |

| YuE | Apache-2.0 | 한국어 명시 | 참조 오디오(ICL) | 24GB 이하는 세션 둘 · 전곡 80GB | VRAM 탈락 |

### □ 실측 관문 — 착수 전에 적었다 (D-0217)

**앞에서 걸리면 뒤를 안 돈다** (O-25 — 판정 규칙을 먼저 쓴다).

| 관문 | 무엇을 재나 | 탈락 |
|---|---|---|
| **G0 설치 · 메모리** | 3분 곡 하나 · 최대 할당량 | 가용치를 넘거나 죽는다 |

## 7. 가창 및 안전 게이트 설계

### □ 가창은 엔진이 입힌다

초판은 공개 다화자 데이터베이스 위에 취향 화자 가중치를 델타로 얹는 자체 합성을 적었다.
**가창을 오디오 엔진에 맡기면서 그 설계는 쓰지 않는다** (D-0217). 남는 원칙은 하나다 —
**실존 가수의 음색 복제·보간은 구현하지 않는다** (D-0003).

### □ 음색 누설 관문 (G2)

참조 오디오로 조건화하면 **그 가수의 음색이 새어 나올 수 있다.** 곡마다 임계로 막는 대신
**모드 단위로 판정한다.**

```text
가수가 서로 다른 참조곡 20곡
   ↓ 곡마다 참조 오디오로 생성
출력에서 보컬 스템 분리
   ↓
화자 임베딩 — 자기 참조 가수와의 유사도 − 다른 19명과의 유사도 (곡 단위 짝 비교)
   ↓
유의하게 크다? ── 예 → 참조 오디오 모드를 제품에서 금지 (모델 탈락이 아니다)
   │
   아니오 → 모드 허용
```

**귀무를 먼저 돌린다.** 참조 없이 생성한 출력으로 같은 self/other를 내면 차이가 0 근처여야
한다 — 거기서 0이 안 나오면 화자 임베딩이 가수가 아니라 다른 것을 잰다 (O-25 (4)).
**화자 임베딩 모델의 라이선스는 착수 전에 본다** (D-0217).

**허용 범위**: 음색 자체를 금지하는 것이 아니라 **식별 가능한 산출**을 금지한다.

### □ 조건화 판정 — self/other와 그 한계

조건화가 출력에 닿는지는 **자기 참조와 더 가까운가**(self)를 **남의 참조**(other)와 곡 단위 짝으로
견준다 (D-0112). 쌍 거리는 배열 조건화를 판정하지 못했다.

**이 하네스는 «닿는가»를 재고 «맞게 닿는가»는 못 잰다.** 배열 사전이 절대음으로 읽혀 으뜸화음이
0%였던 결함을 통과시켰다 — 틀린 좌표계로도 자기 참조와는 일관되게 가깝기 때문이다 (D-0213).
그래서 하네스가 통과해도 **귀가 판정한다.**

### □ 검색 평가 하네스 (D-0023)

취향 모델 이전에 **임베딩 자체가 쓸 만한지**부터 판정한다. 라벨은 외부 조회 없이
태그 동치류(TALB·TPE1, 각 100% 커버)로 만든다. 정규 신원이 아니라 동치류만
필요하므로 O-4(RESOLVED 오답)의 영향을 받지 않는다.

| 지표 | 정의 | 라벨 |
|---|---|---|
| M0 | 곡의 청크를 두 조각으로 나눠 한쪽으로 나머지를 top-1으로 찾는 비율 | 불필요 |
| M1 | top-k 중 같은 앨범 비율, MAP@k | TALB |
| M2 | top-k 중 같은 아티스트 비율, MAP@k (같은 앨범은 후보에서 제외) | TPE1 |

**M0의 분할 규칙은 설정이다** (D-0040). `odd-even`(기본, 오디오축 정본)과 `random`(무작위 균등 분할, 반복 평균±표준편차) 중 고른다. 오디오의
10초 청크는 곡 구조와 정렬될 이유가 없지만 **가사 구간은 빈 줄 경계, 즉 곡 구조 그 자체**라 홀짝이 절·후렴을 갈라놓을 수 있다. 기본값을 바꾸면
D-0031~D-0038의 M0 수치와 비교할 수 없으므로 `odd-even`을 유지하고 회귀 테스트로 고정한다.

M0는 top-1과 함께 **순위 진단**(MRR · R@5 · R@10 · 실패 순위 중앙값)과 **해석적 베이스라인**(무작위 top-1 = 1/n, 무작위 순위 중앙값 =
(n+1)/2)을 낸다 (D-0041). top-1만으로는 실패가 순위 2에 몰려 있는지 수백 등에 흩어져 있는지 구분할 수 없고, **그 둘은 처방이 정반대다.**

#### M0 게이트를 어떻게 읽는가

**M0 게이트의 전제는 축마다 다르다 (D-0044).** 게이트는 "M0가 무너지면 아래 지표는
무의미하다"를 전제한다. 오디오축에서는 음색·믹스가 **곡 특정성과 유사성을 겸해** 성립한다.
**가사축에서는 반증됐다** — 반복 감쇠 조건이 M0 0.3850(반토막)인데 M1 2.2배·M2 2.5배로
M0 0.90대 조건과 같았다. 가사에서 M0는 **반복 문구**를, M1/M2는 **어휘·주제**를 재며
둘이 다른 신호다. **가사축 게이트를 무엇으로 둘지는 미해결이다 (O-15).**

**미달의 성격은 순위로 가른다.** R@10이 게이트를 넘으면 정답이 상위권에 있다는 뜻이고
표현이 무너진 것이 아니다(가사 8192: top-1 0.9174, R@10 0.9715, 실패 순위 중앙값 3.8).
넘지 못하면 표현이 곡을 특정하지 못하는 것이다(반복 감쇠: R@10 0.4688, 실패 순위 831.1).
**두 상황은 처방이 정반대이며, D-0041 이전에는 같은 문구로 보고되고 있었다.**

#### 하네스 운용과 실측 이력

- **베이스라인 2종 필수**: 무작위(시드 고정), MFCC 평균. 측정값 단독 인용 금지.
- MAP은 `min(R, k)`로 정규화한다. k로 나누면 지표가 앨범 크기 분포를 재게 된다.
- CPU 수 초. GPU 없는 기기에서 도는 것이 요건이다.
- **저장소를 둘 이상 합칠 때는 블록별 단위 정규화(`--block-l2`)가 필수다.** MERT 768차원과
  MFCC 40차원을 그냥 이어붙이면 코사인이 노름 큰 쪽에 압도당해 작은 블록이 무시된다.
  블록 정규화 후 concat하면 전체 코사인이 블록 코사인의 평균이 되어 기여가 균등해진다.
- **실측 결과는 D-0024.** 9조건 비교에서 **MFCC 40차원이 MERT 768차원을 이겼다**(M2 기준 47% 우위).
  원인 미확정이며 O-8(D-0024)로 등재. 스템은 MERT 임베딩에 기여하지 않음이 확인됐다.

#### 표현 선택의 실측 이력

- **공간 뭉침은 D-0030.** 전체 쌍 평균 코사인 **0.9476**으로 허브 곡이 존재한다.
  시드 퓨전이 중점 대신 코퍼스 중심으로 빨려가는 것이 실측으로 확인됐다.
  중심화 도입 후 **전 지표가 개선됐다**(D-0031): 평균 코사인 0.9476 → -0.0006,
  M1 MAP +14.1%, M2 MAP +13.0%, M0 유지. **기본값으로 승격**했으며 `--raw`로만 끈다.
  시드 퓨전에서 허브 곡이 사라지고 유사도 범위가 0.98대 → 0.42~0.33으로 정상화됐다.
- **레이어 곡선 종결은 D-0027.** 0~3이 단조 감소이고 6의 반등도 0을 넘지 못한다.
  **layer00이 최댓값이며 레이어 축은 소진했다** — **검색축에서다** (D-0181이 화성축에서 `layer03`을 찾았다).
  재현성 검산 2회 통과(별도 배치·저장소에서 네 지표 완전 일치).
- **레이어 실측은 D-0026.** **MERT 마지막 레이어가 측정한 전 레이어 중 최악이었다.**
  `layer00`으로 바꾸자 M2 P@10이 0.0829 → 0.2327로 **2.8배** 올랐고 MFCC를 90% 앞선다.
  D-0024의 "MFCC가 MERT를 이긴다"는 모델 문제가 아니라 레이어 선택 문제였다.
  **검색축 기본 뷰가 `layer00`이다** (D-0181 · D-0203).
- **결합 실측은 D-0025.** MERT+MFCC 결합이 **M1에서 어느 단독보다 우월**하다(MAP@10 0.1022,
  MFCC 대비 +40%). 두 표현은 상보적이며, MERT를 버리는 판단은 틀린 것이었다.
  M2는 무승부이므로 MERT의 기여는 앨범 수준에 한정된다.
- **코퍼스 구조 도출**: 1004곡 중 595곡이 단일 곡 앨범이라 M1 쿼리는 409뿐이다.
  아티스트당 평균 약 17곡으로 **M2의 검정력이 M1보다 높다.**
- 실행: `uv run python -m hathor.cli eval retrieval --out var/ingest`

**한계**: 앨범·아티스트 검색은 취향의 대리 지표가 아니다. 임베딩이 곡 정체성과
제작 맥락을 담는지까지만 말해준다.

## 작업 원칙 (GROUND RULES)

**`CONTRIBUTING.md`에서 흡수했다** (D-0186). `fire-lane` · `thoth`가 규약을 마스터
안에 두고, 규약과 현재 상태를 따로 두면 **한 항목이 두 문서에 산다.**

**`GR-` 번호는 그대로다.** 저장소 안에서 220곳이 그 ID를 부른다 — 번호를 다시
매기는 것은 값이 없고 참조만 깬다.

### GR-0. 협업 규칙

### GR-0.1 문서 우선

설계 변경은 **문서를 먼저 고치고 코드를 고친다.** 반대 순서는 금지한다.
대화에서 나온 결정도 문서에 반영되지 않으면 **존재하지 않는 것으로 간주한다.**

### GR-0.2 결정 기록

되돌리기 어려운 선택은 `docs/DECISIONS.md`에 남긴다. 형식: **배경 / 후보 / 선택 / 근거 / 결과**.

**기록 기준**: 선택지가 있었고 어느 쪽을 왜 골랐는지 남아야 하면 기록한다.
단순 사실이면 어디에도 적지 않는다.

- **추가 전용이다.** 판단이 바뀌면 고쳐 쓰지 않고 새 번호로 정정한다.
- **문서 체계·개발 규약·도구 체인 변경은 부수 결정으로 처리하지 않는다** (D-0039).
- **판단 착오도 기록한다.** 반증된 가설은 형식 목록에 없지만 판단력을 증명한다.

**번호를 조용히 비우지 않는다** (D-0080). 잡아 둔 번호에 기록을 안 썼으면
`## D-XXXX. (결번) …` 표제를 남긴다. 실제로 D-0076이 그렇게 사라졌고 **78건이
쌓이는 동안 아무 검사도 그것을 보지 않았다.**

**앞 기록을 갱신하면 양쪽에 표시한다.** 갱신하는 쪽에 `- **갱신**: D-XXXX`,
갱신되는 쪽 표제 아래에 `> **갱신됨 — D-XXXX.**`. **낡은 수치는 기록 맨 뒤가 아니라
맨 앞에서 알려야 한다** — D-0063의 표를 그대로 인용해 세 곳이 동시에 틀린 적이
있다 (O-28). 앞을 고치는 것이 아니라 표시하는 것이므로 추가 전용은 깨지지 않는다.

**옛 기록을 형식에 맞추려고 소급 수정하지 않는다.** 형식 검사는
`check_decisions.py`의 `FORMAT_ENFORCED_FROM` 이후에만 걸린다. 추가 전용이
이 기록의 유일한 방어선이고, 78건을 손대는 순간 그것이 사라진다.

**굵은 글씨는 강조가 필요한 곳에만 쓴다.** 78건 시점에 본문 2.7줄당 하나였고
그쯤 되면 강조가 강조 기능을 잃는다. **다만 기계로 검사하지 않는다** — 밀도에
숫자를 걸면 문체를 그 숫자에 맞추게 되고, 그것이 D-0058~D-0061에서 네 세션을
태운 형태다. 규약을 새로 정하면 검사할 수 있는지 함께 보되(GR-0.8), **검사하지
않기로 한 것은 그 이유를 남긴다.**

**표기는 소급해 맞추고 내용은 안 맞춘다** (D-0081). 구분선·표 열 수·펜스 태그·
줄 길이(100자)·낡은 수치는 고쳐도 **그때의 판단이 바뀌지 않으므로** 전 기록에
강제한다. 배경·후보·선택·결과는 다르다 — 없는 것을 지금 채우면 **그때 하지 않은
판단을 사후에 지어내는 것**이고 추가 전용이 막으려는 것이 그것이다.

`make check`가 다음을 본다: 색인 일치 · 번호 중복·결번 · **참조 무결성** ·
필수 절과 후보-선택 짝 · 갱신 배지 짝 · 미해결표 중복·정렬·닫힘 잔류 ·
표제 앞뒤 표기 · 줄 길이 · 펜스 태그 · 표 열 수 (D-0080 · D-0081).

### GR-0.2.1 강제자와 재현

결정마다 **`강제자`와 `재현`**을 요구한다 (D-0131 · D-0135). 둘 다 **전수**이며
`강제자 없음 — 사유: …` · `재현 불명 — …`도 기술이다 — **없다는 사실 자체가
기록이어야 한다** (D-0132 · D-0136).

### GR-0.3 자율성 경계

| 묻지 않고 결정 | 반드시 확인 |
|---|---|
| 라이브러리·프레임워크 선택 | 프로젝트 범위 변경 |
| 알고리즘·자료구조 선택 | 비용이 발생하는 결정 |
| 코드 구조·네이밍·패턴 적용 | 되돌리기 어려운 아키텍처 결정 |
| 문서 서술 방식·다이어그램 종류 | 사용자 취향·경험이 판단 근거인 것 |
| 지표·임계값 초안 | 법적·윤리적 판단이 필요한 것 |

### GR-0.4 반대 의무

판단이 틀렸다고 보면 동의하는 척하지 않고 **근거를 들어 반대한다.**
그럼에도 사용자가 결정하면 따르되, 문서에 **"사용자 판단으로 결정됨"**을 남긴다.

### GR-0.5 불확실성 표시

확실하지 않은 사실을 **추측으로 채우지 않는다.** 검증하거나 **(실측 필요)**로 표시한다.
**미해결표에 올리는 것도 정당한 처리다** — 지금 안 하기로 결정했다는 기록이 남는다.

### GR-0.6 진행률 정직성

"거의 다 됐다" 같은 표현을 쓰지 않는다. **완료 조건(GR-6.6) 충족 여부로만 판단한다.**

### GR-0.7 전달 방식

코드·문서 수정은 **검증·되돌리기·멱등성을 갖춘 패치로 전달한다.** 손으로 옮기게 하지 않는다.

**셋 다 git이 진다** (D-0066). `git apply --check`가 검증, `git reset --hard HEAD~1`이
되돌리기, `git apply --reverse --check`가 멱등 판정이다.

**`make apply` 한 번으로 붙이고 커밋까지 한다** (D-0070). 작업 트리가 깨끗한지 보고,
이미 적용됐으면 아무것도 하지 않고, 붙인 뒤 색인을 검사하고, **`git add -A`로 커밋한다.**

**커밋할 파일 목록을 손으로 적지 않는다.** 목록을 적다가 실제로 `CONTRIBUTING.md`와
`tools/apply_patch.sh`를 빠뜨려 작업 트리가 더러운 채 다음 작업으로 넘어갔다.
GR-4.1의 커밋 분리보다 **빠뜨리지 않는 것이 먼저다** — 한 패치는 한 작업 단위이므로
한 커밋이 맞다.

**`git add -A`도 쓰지 않는다** (D-0072). 그것은 트리에 있는 것이 전부 이 작업
것이라고 믿는 것이며, 다른 프로젝트의 명령을 이 저장소에서 돌린 적이 실제로 있다.
**패치가 건드린다고 선언한 파일과 실제로 바뀐 파일을 대조하고, 일치할 때만 그
목록으로 담는다.** 사람도 트리도 믿지 않는다.

**별도 백업 디렉터리를 만들지 않는다.** `.backup/`을 쓰다가 `.gitignore`가 뒤늦게
추가돼 무효인 것을 놓쳤고, 청소하다 추적 파일 25개를 지웠다. git이 이미 하는 일을
두 번 하면서 사고만 늘렸다.

### GR-0.8 작업 위생

**패치는 저장소 안에서만 푼다.** 저장소 밖에 세션별 디렉터리를 만들지 않는다.
`~/hathor-D0040` ~ `D0060` 열여섯 개 6.8GB가 그렇게 쌓였고, 전부 git 이력에 있는
내용의 사본이었다.

**기기를 옮기면 `make doctor`부터 돌린다.** 결정 기록이 여든 건을 넘었고 아무도
매번 다시 읽지 않는다. D-0004가 저장소 위치를 정해 두었는데 **그 사실을 모른 채
두 기기 모두 다른 곳에 클론했고 한 번은 윈도우 드라이브였다.** 규칙이 없어서가
아니라 확인하는 것이 없어서였다.

**규약을 새로 정하면 `doctor`가 검사할 수 있는지 함께 본다.** 검사할 수 없는 규약은
문서에만 남고 잊힌다.

### GR-0.9 결함은 부류로 고친다

**결함을 고칠 때 같은 부류를 막는 검사를 함께 넣는다.** 개별 수정은 다음 사례를
못 막는다 — D-0064에서 "인자가 조용히 무시된다"를 고치고 검사를 안 넣었더니
**네 시간 뒤 같은 부류가 다시 나왔다**(D-0069).

**검사를 넣었으면 일부러 결함을 되살려 빨갛게 뜨는지 본다.** 아무것도 못 잡는 검사는
늘 통과하는 하네스와 같다.

`import-linter`의 아키텍처 계약 넷은 한 번도 깨지지 않았다. **규율이 좋아서가 아니라
기계가 매번 보기 때문이다.** 문서에만 있는 규칙은 잊힌다 — D-0004가 이 년 가까이
그랬다.

**원인을 모를 때 파일을 옮기거나 지우지 않는다.** 진단이 먼저다. 원인을 찾기 전에
스캔 산출물을 옮겼다가 유일한 사본을 잃었다.

### GR-1. 명명 규칙

**현재 저장소는 Python 단일 언어다** (D-0015 로컬 에이전트 전환). 다언어 규칙은
해당 스택을 실제로 도입할 때 되살린다 — 지금 적으면 검증할 대상이 없다 (GR-0.5).

### GR-1.1 케이스

| 대상 | 케이스 | 예시 |
|---|---|---|
| 변수 · 함수 | `snake_case` (PEP 8) | `get_taste_vector` |
| 클래스 · 타입 | `PascalCase` | `HarmonyStrategy`, `GenerationSpec` |
| 상수 | `UPPER_SNAKE_CASE` | `MAX_REPAIR_ATTEMPTS`, `DEFAULT_GATE` |
| 파일 · 모듈 | `snake_case` | `harmony_strategy.py` |
| DB 테이블 · 컬럼 | `snake_case` | `taste_cluster`, `created_at` |
| 환경 변수 | `UPPER_SNAKE_CASE` | `SYLLABLE_MATCH_THRESHOLD` |
| 이벤트 라우팅 키 | `dot.case` | `ingest.raw.discovered` |
| 브랜치 | `kebab-case` | `feat/ingest-fingerprint` |
| 문서 파일 | `UPPER` 또는 `kebab-case` | `DESIGN.md`, `docker-compose.yml` |

**언어·생태계 관례와 싸우지 않는다.** 일괄 규칙보다 관례가 우선한다.

**문서·설정 파일명에 한글을 쓰지 않는다** (D-0043). macOS는 NFD, Linux·Windows는 NFC로
정규화해 git이 같은 파일을 다른 파일로 인식한다. 이 프로젝트는 WSL + Windows 조합이라
정확히 그 사고가 나는 환경이다. **파일명은 도구가 읽고 문서 제목은 사람이 읽는다** —
제목은 한글로 둔다.

### GR-1.2 명명 원칙

1. 이름만으로 역할과 의미가 드러나야 한다.
2. 함수명은 **동사**로 시작한다 (`resolve_entity`, `compute_deficiency`).
3. 불리언은 `is` / `has` / `can` / `should`로 시작한다 (`is_deficient`, `has_lyric_tag`).
4. 컬렉션은 **복수형**을 쓴다 (`clusters`, `stems`, `candidates`).
5. 타입명을 변수명에 넣지 않는다 (`track_list` ✗ → `tracks` ✓).
6. **단위·시각을 이름에 포함한다** (`timeout_ms`, `f0_rmse_cent`, `created_at`).
7. 서브시스템명을 접두사로 쓴다 (`IngestNormalizer`, `HarmonyGenerator`).

### GR-1.3 금지어

| 금지어 | 이유 | 재명명 예시 |
|---|---|---|
| `data`, `info`, `value`, `thing` | 의미 없음 | `data` → `feature_set` |
| `temp`, `tmp` | 수명 불명 | `temp` → `decoded_buffer` |
| `list`, `arr`, `obj` | 타입명 노출 | `list` → `tracks` |
| `flag` | 의미 없음 | `flag` → `is_deficient` |
| **`manager`, `util`, `helper`, `common`, `handler`** | **우연적 응집의 신호** | `AudioUtil` → `LoudnessNormalizer` |
| `process()`, `handle()`, `do_work()` | 동작 불명 | `handle()` → `handle_file_discovered()` |

**`manager` · `util` · `helper`가 이름에 들어가면 응집도 위반을 의심하고 분해를 검토한다.**

### GR-4. 커밋 · 브랜치 · PR

### GR-4.1 커밋

형식: `type(scope): subject`

| type | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `perf` | 성능 개선 (**수치 필수**) |
| `docs` | 문서 |
| `test` | 테스트 |
| `chore` | 설정·의존성 |
| `data` | 데이터셋 버전 |
| `exp` | 실험 (리포트 라벨 명시) |

scope는 서브시스템 코드명을 쓴다.

```text
feat(ingest): 지문 기반 정규화 폴백 체인 구현
perf(eval): 전체 코사인을 행렬곱으로 4.2배 단축
exp(lyrics): M0 분할 규칙 대조 12조건 (label: o12-random-8192)
```

**하나의 커밋은 하나의 변경만 포함한다.**

### GR-4.2 브랜치

| 브랜치 | 규칙 |
|---|---|
| `main` | 항상 배포 가능. **직접 push 금지.** CI 전부 통과해야 병합 |
| `feat/{subsystem}-{topic}` | 기능 개발 |
| `fix/{topic}` | 버그 수정 |
| `spike/{topic}` | 실험. **병합하지 않고 폐기 가능.** 결과만 문서에 기록 |
| `hotfix/{topic}` | 긴급. main 분기 → fast-forward |

**`develop` 브랜치를 쓰지 않는다.** GitFlow의 develop은 릴리즈 묶음 관리가 있을 때
의미가 있는데, 1인 + 지속배포 환경에서는 병합 단계만 늘린다. GitHub Flow로 간다.

### GR-4.3 이슈 · PR

1. 작업 시작 전 Issue를 만든다. 제목은 **완료 조건이 드러나게** 쓴다.
2. `feat/*` 브랜치에서 개발하고 PR로 병합한다.
3. **1인이라도 PR을 거친다.** CI 게이트를 통과시키기 위해서다.
4. PR 본문에 **변경 내용 / 변경 이유 / 확인 방법** 3항목을 쓴다.
5. 병합 후 브랜치를 삭제한다.

### GR-5. 기술 원칙

| # | 원칙 | 내용 |
|---|---|---|
| 1 | **Async First** | I/O는 비동기 우선. **CPU/GPU 연산은 강제하지 않는다** — 워커나 executor로 이벤트 루프를 보호한다 |
| 2 | **Fail Fast** | 입력 검증을 진입점에서. 예외를 삼키지 않는다. 재시도 가능한 오류만 명시적 재시도 |
| 3 | **Idempotency** | 동일 요청 반복 시 상태 동일. 모든 워커에 멱등 키 필수 |
| 4 | **Deterministic** | 동일 입력 → 동일 출력. **시드 명시 고정.** 재현성 계층은 `docs/MASTER.md`에 있고 CI가 검사한다 |
| 5 | **Secrets 분리** | 코드에 비밀정보 금지. `.env` + 환경 변수. `make docs`와 CI가 `check_secrets.py`를 돌리고, 기기 훅은 `doctor`가 본다 (D-0128) |
| 6 | **DRY** | 동일 로직 **3회 반복 시** 공통화. 2회까지는 중복 허용 (성급한 추상화 방지) |
| 7 | **Single Responsibility** | 함수·클래스·모듈은 하나의 책임. 계층 간 전달은 DTO로 |
| 8 | **No Hard Coding** | 반복 값은 상수·enum·설정으로. 임계값은 주입 |
| 9 | **Environment Independence** | 환경 의존 코드 금지. 설정 분리 |
| 10 | **Structured Logging** | 구조화 로그, 필드 고정. **개인정보·토큰·프롬프트 전문을 남기지 않는다** |
| 11 | **Observability** | 모든 잡에 trace ID. 단계별 span |
| 12 | **Reproducibility** | 코드·데이터·모델·시드 4개가 전부 버전 관리 대상 |
| 13 | **Graceful Degradation** | 실패 시 축소된 결과라도 낸다 (가창 실패 → 인스트루멘탈) |
| 14 | **Cost Guard** | 외부 자원은 종료를 보장한다. `finally`에 teardown |

### GR-6. 추진 룰

### GR-6.1 MVP 우선

```text
동작하는 최소 → 검증 → 확장 → 최적화
```

**최적화는 측정 후에만 한다. 측정 없는 최적화는 금지한다.**

### GR-6.2 개발 순서

```text
1. 데이터 구조 정의       ← 화면보다 먼저
2. 도메인 엔티티·포트 정의
3. 엔진 최소 구현 (더미 출력 허용)
4. 파이프라인 연결 (종단간 관통)
5. 각 엔진 품질 향상
6. UI 연결
7. 통합 테스트
```

**이 프로젝트는 화면이 아니라 데이터·파이프라인이 본체이므로 데이터 구조가 먼저다.**

### GR-6.3 작업 단위

한 번에 하나. WIP 제한 2. 단위 기준은 **하나의 엔진 스테이지 / 하나의 API / 하나의 화면**.

### GR-6.4 디버깅 순서

문제 발생 시 **상류에서 하류로 순차 확인**한다. 중간부터 찍지 않는다.

```json
[인제스트]  스캔 → 태그 → 파싱 → 조회 → 디코딩 → 특징 추출 → npz
[검색]      npz → 뷰 조립 → 중심화 → 코사인 → 순위
[생성]      시드 선택 → 조건화 → 엔진 → 품질 게이트 → 산출물
```

### GR-6.5 실험 규칙

| 규칙 | 내용 |
|---|---|
| **지표 우선** | **지표를 먼저 만든다.** 지표 없이 돌린 실험은 반증 불가능한 선택만 남긴다 |
| **베이스라인 동시 투입** | 지표를 추가할 때 베이스라인을 **같이** 넣는다. 나중에 붙이면 이미 그 지표로 판단을 내린 뒤다 (D-0034) |
| **단일 변수** | 한 번에 하나만 바꾼다. 여러 개를 동시에 바꾸면 원인 규명이 불가능하다 |
| 시드 | 항상 명시. `None`이면 생성 후 기록 |
| 기록 | **실패한 실험도 남긴다.** 반증된 가설은 결정 기록에 보존한다 |
| 타임박스 | `spike/*`는 사전에 시간 상한을 정하고 초과 시 중단 |
| 아티팩트 | 오디오·MIDI·악보를 첨부한다. **지표만으로 소리를 판단할 수 없다** |

**만들어두고 보지 않는 지표는 없는 것과 같다** (D-0030에서 허브 문제를 놓친 사례).

### GR-6.6 완료 기준

**전부 충족해야 "완료"다.**

1. 기능이 정상 동작한다
2. 계층 계약을 위반하지 않는다 — `import-linter` 통과
3. 기술 원칙(GR-5)을 준수한다
4. 테스트가 있고 통과한다
5. 품질 게이트를 통과한다 (해당 시)
6. 오류 로그가 발생하지 않는다
7. Git 기록이 남아 있다 (Issue → PR → 병합)
8. **문서가 갱신되어 있다** (GR-0.1)

`make check`가 2·4를 기계로 검사하고 문서 색인 어긋남까지 잡는다 (D-0042).

## 결정 대장
